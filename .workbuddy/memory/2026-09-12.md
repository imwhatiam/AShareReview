## 开盘啦资金流：快照落库时刻规则收敛为单一函数（backend）

**背景**：用户指出库里存在 15:00 之后的时间戳（`2026-09-11 09:45 UTC` = 北京 17:45，270 行），并给出期望规则：交易日按运行时刻向前回退到 5 分钟槽（09:33→09:30、12:00 午休→11:30、盘后 16:34→15:00），非交易日归到最近交易日 15:00，同槽覆盖。

**现状排查**：默认（无参数）模式本来就用 `now.replace(minute=(minute//5)*5)` 做回退，且被 `_is_trading_session` 限制在交易时段；`--latest` 走 `last_reached_slot(上游 source_timestamp)`。真正的缺口只有一个：**非交易日会写到"当天 15:00"**（`last_reached_slot` 在当天没有任何已到槽位时返回 `slots[-1]`，即当天收盘），刷一次就是一条不可读的假收盘快照；Web 补齐路径同样能写出周六快照。17:45 那批是加夹紧之前的遗留数据，只读路径根本匹配不到，属惰性脏数据。

**改法**（`backend/kaipanla/services/intraday.py`）：删除 `last_reached_slot`，新增 `session_slot()` / `is_trading_day()` / `previous_close_slot()` / `resolve_snapshot_slot()`，三处写入路径（命令、`--latest`、`read_path` 补齐）共用 `resolve_snapshot_slot(now)`。**时刻来源从上游 `Time` 改为运行时刻**（用户规则就是以"运行命令获取到的数据"表述的），顺带去掉 `--latest` 对上游时间戳的依赖与那句 ValueError。`_can_attempt_repair()` 增加"必须是交易日"，`_repair_snapshot_time()` 先于上游请求短路。

**一个必须记住的取舍**：工作日的日期若不在 `TradingDay` 里，按"交易日"处理而不是非交易日 —— 上游日历窗口只到"它已知的最后一个交易日"，同步没跟上时今天的行本就不在，若判成非交易日就会**用当天数据覆盖上一交易日收盘**。代价是极端情况下会在节假日写一条当天槽位。

**验证**：真实日历只读推演每个规则（09:33→09:30、10:46→10:45、12:20→11:30、15:00→15:00、16:34→15:00、周六 06:41/20:00→09-11 15:00）；`--latest --dry-run` 打通真实上游（270 条）；后端 **220 测试通过**，唯一失败 `test_runtime_security_settings_are_safe_by_default` 在基线树同样失败（本地 `.env` 相关）。新增用例：`test_intraday` 11 条（槽位规则）+ `test_command` 新增盘中回退/同槽覆盖/盘后落收盘/非交易日归上一交易日/开盘前归上一交易日 5 条。

## 修复：sync_kaipanla_industry_snapshot 在非交易日必然失败（errcode 1020）

**现象**：2026-09-12（周六）09:46 运行 `python manage.py sync_kaipanla_industry_snapshot`，3.4 秒即失败，日志只有 `error=Kaipanla request was rejected.`。

**根因**：`core/integrations/kaipanla/client.py` 的 `_request_date()` 默认值是 `timezone.localdate()`，即**本地日期**。而该数据集走的是开盘啦**历史**端点（`KAIPANLA_INDUSTRY_API_URL` → `apphis`，与实时资金流的 `apphwshhq` 是两条 URL），历史端点只服务**交易日**。用真实配置发探针横向对比，因果一次坐实：

| 请求 | 结果 |
|---|---|
| `Date=2026-09-12`（周六） | `errcode 1020, errmsg 参数出错` |
| 不带 `Date` | `errcode 0` 但 `list` 为空（看着像"没数据"，实为上游敷衍，是陷阱） |

## ④ 定位并修复「日行情 15 条测试跑了 107 秒」的真正原因（`backend/env.py` 无缓存）

- 现象：15 条日行情测试 `Ran 15 tests in 107.033s`（此前全量 246 tests 仅 7.2s），每条用例 ~7.7s，且**日志里各阶段之间都是约 1 秒的整数倍**。
- 定位手段：临时用例里用 `cProfile` + `pstats.sort_stats('cumulative')` 包住一次 `call_command`。
- **真正原因**：`backend/env.py` 的 `get_setting()` 写成 `os.environ.get(name, _file_values().get(name, default))` —— ① `_file_values()` 每次调用都重新 `Path.read_text()` 解析 `.env`，完全没有缓存；② 即使 `os.environ` 已命中，作为默认值参数的 `_file_values()` **仍然会被求值**。
  - 一次 `init_stock_daily_prices` 触发 **186 次** `.env` 读取；本环境里文件 I/O 走沙箱代理（`_brokered_open` → socket），每次约 42ms，累计 **7.8 秒**，占该次运行 99%。
  - 所以这**不是业务代码慢，也不是本轮改动引入**，但它让基线树同样慢（基线全量 44 秒）。
- 修复：按路径缓存解析结果 `_PARSE_CACHE`，最多每 `ENV_CACHE_TTL_SECONDS = 5.0` 秒比对一次文件指纹（`(st_mtime_ns, st_size)`）；文件没变只刷新检查时间；`get_setting` 先查 `os.environ` 再回落到缓存，环境变量命中时完全不碰文件。
  - 结果：单次 `init` **7.889s → 0.079s**；全量测试 **44s → 7.8s**。
- 新增 `backend/tests/test_env_cache.py`（4 条）：重复取值只解析一次、改文件后按 TTL 重新解析、文件缺失不报错、环境变量优先且不读文件。

## ⑥ 用户报告：init 之后「大涨跌幅与大成交量个股」页显示旧数据 + 日期停在 09-08（**不是 bug，是预期语义**）

**只读排查结论（全链路已对账，无 bug）**：

| 事实 | 值 |
|---|---|
| `stock_moves` 库里的分析结果 | **只有 1 条**：`business_date=2026-09-08`，`source_daily_price_version=stock_daily_prices-e0e244e7…` |
| 09-08 当前最新日行情版本 | `stock_daily_prices-a6e96c94…`（今天 12:11 由 init 发布）→ **不同 → `stale=True`** |
| 09-11 的分析结果 | `_result_for_date(2026-09-11)` 返回 **None**（从没构建过） |

**因果链**（这是本项目一条重要的分层语义，务必记住）：

1. `init_stock_daily_prices` 写的是**输入**（公共日行情）；三个业务页面读的是**产物**（各模块自己构建的分析结果）。**重算输入不会自动重算产物。**
2. init 有差异 → 对受影响交易日发布**新的** `stock_daily_prices` 版本。本次 242 个交易日全部重新盖章（例：09-08 从 `e0e244e7` → `a6e96c94`）。
3. `read_stock_moves(None)`（页面初始进入，不带日期）的语义是**"取最新已有的分析结果"**（`StockMoveResult.order_by('-business_date')`），**不是"最新日行情日期"**。所以它选中 09-08 —— 09-11 从没构建过，再新的日行情也不会让它出现在页面上。
4. `_result_for_date(09-08)` 发现 `result.source_daily_price_version != _latest_public_version(09-08)` → `stale=True`。
5. 尝试 `_bounded_local_rebuild(09-08)` 自动修复 → 被 `REMOTE_REPAIR_MAX_ROWS=1000` 挡住（5571 > 1000）→ 抛 `CompleteMarketDataUnavailable` → 回退为返回旧结果 + `stale=True`。
6. 前端据此显示"正在展示旧数据 / 公共日行情版本已更新…"，日期仍是 09-08。

**用户该做的**：跑构建命令（纯本地计算、不访问上游、幂等）：

```bash

python manage.py build_sector_momentum --date 2026-09-11
python manage.py build_hundred_day --date 2026-09-11
```

**顺带解释"为什么 242 天都有差异"**：日行情用的是 `adjust=forward`（前复权），**新的分红/送转事件会重算全部历史价格**，所以时隔一段时间重跑 init 发现大量历史行与上游不同是正常的，不代表之前导入错了。反过来这也解释了为什么"无差异不发布新版本"这个设计是必要的 —— 否则下游会因版本号变化而全量重建。

### 迁移的三个坑（本轮最大的工程发现，已写进 memory 与 skill）

1. **裸 `migrate` 只作用于 `default`，而且它会撒谎。** `db_router.allow_migrate` 让业务 app 的 operation 在 `default` 上变成 no-op，可 Django **照样打印 `Applying stock_moves.0005_... OK`**，并把记录写进 `default` 库的 `django_migrations`。我第一遍就是这么跑的 —— 命令全绿，业务库里一个字段都没动。**标准姿势是逐库跑**（`docs/deployment.md` 与 `docs/manage-commands.md` 早就写了，我漏看）：`for db in default kaipanla stock_moves sector_momentum hundred_day; do manage.py migrate --database=$db; done`。
2. **Django 在 SQLite 上把 `RenameField` 编译成 `-- (no-op)`**（`sqlmigrate` 实测输出确认）—— 光写 `RenameField` 列名不会变。必须 `SeparateDatabaseAndState(database_operations=[RunSQL('ALTER TABLE t RENAME COLUMN old TO new;', reverse_sql=...)], state_operations=[RenameField(...)])`。SQLite 3.25+ 原地改名，**数据完整保留**（实测 49 行 / 662 行逐条无损失）。反之让 `makemigrations` 自动检测，非交互模式下会把改名判成 remove + add，**直接删掉整列**。
3. **`sqlmigrate` 不能预判业务库**：它默认连 `default`，对业务 app 的 operation 一律显示 `(no-op)`。验证只能真跑 + `PRAGMA table_info()` 复查列名与行数。

## 结论：三个 build 命令不能砍（只读分析，未改代码）

- 用户问：既然读路径缺数据会按需算完落库，`build_stock_moves` / `build_sector_momentum` / `build_hundred_day` 是否就不需要了。答案：**页面不依赖它们，但调度链路不能去掉。**
- 两条路径产出同一种产物（同一 analysis + writer；`business_date + source_*_version` 走 `update_or_create`；`dataset_lock` 互斥）→ 漏跑一天不会白屏。`docs/manage-commands.md` §7 已把这条写成正式约定，并明写"不要把 API 当成调度器使用"。
- 不能砍的四条理由：
  1. **失败无记录**：`_local_generate()` 只调 writer，**不调 `record_failed_run()`**。生成失败只变成 202 `DATA_PREPARING` / 404，默认入口还会静默退回旧结果；命令侧有非零退出码 + `data_command_*` 日志 + FAILED `*Run` 行（crontab 监控依赖退出码）。
  2. **成本挪进请求**：`hundred_day` 单次读 199 交易日 × 5571 只 ≈ 110 万行（`source_data.py` 注释自陈"逐对象构造 ORM 要 15 秒、批量取值不到 2 秒，这是请求内按需生成能接受的前提"）；`stock_moves` / `sector_momentum` 只读一天。
  3. **锁是非阻塞的**（`locking.py` 用 `O_CREAT|O_EXCL`）：并发请求抢不到锁 → `DatasetLocked` → `CompleteMarketDataUnavailable` → 默认入口退回旧结果并标 `stale`；命令侧抢不到就 `CommandError` 退出。
  4. **命令独有能力**：`--dry-run`、指定任意历史交易日回补；首次部署（`deployment.md` §5）与故障恢复（§10.5）路径都写的是这三个命令。
- 已把这张差异表写进项目 skill `.workbuddy/skills/backend-dataset-diagnosis`（v1.4.0 → v1.5.0，新增 §0.1）。

### 本机内存吃紧时的两个坑（重要）

- **vitest 会被 OOM 杀掉（exit 137 / SIGKILL，且无任何输出）**：本机 16GB，用户自己开着 Chrome 等应用时 swap 会跑到 ~6.7G/7.2G、空闲内存只剩 ~100–150MB，`npx vitest run` 整条命令被内核杀掉，**连 `echo` 都不执行**，看起来像"命令凭空失败"。解法：`NODE_OPTIONS="--max-old-space-size=1024" npx vitest run`（build 用 1536）。别误判成代码问题。
- **headless Chrome 截图同样会被杀**：`--screenshot` 偶尔能成（要赶在内存宽松的窗口期），`--dump-dom` 配 python 管道几乎必被杀。**更省内存的替代：先截图存盘，再用 Pillow 逐像素分析 PNG 取几何量**（面板边界、胶囊宽度、轨道间距都能算出来），比反复起浏览器可靠得多。`ps` 在本沙箱不可用（operation not permitted），查进程改用 `pgrep -fl`。
- 顺手确认：3 列版式实测 **轨道间距 178px、最宽胶囊 165px**（面板 96→1343），所以胶囊不会被压字 —— 4 倍放大后目视确认无文字越界。
