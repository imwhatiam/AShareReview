# 复杂度与过度设计专项审查

## 何时用 / 不用

**用**：用户要的是"结构性问题" —— 过度设计、重复、难读、抽象不划算、建议怎么简化。
**不用**：用户要的是缺陷审查（正确性 / 安全 / 契约 / 静默失败）。那是另一类报告，两类**不要混在一份里** ——
混在一起会让"简化建议"读起来像"必须修的 bug"，也会让有用的正确性发现被埋没。

如果仓库里已有缺陷类审查报告（如 `CODE-REVIEW-YYYY-MM-DD.md`），在报告开头**显式声明边界**：
"本报告只审复杂度与过度设计，不重复 X 报告的 A/B/C 类发现"。否则会被当成遗漏。

## 四条判定判据（先写进报告，避免主观）

抽象"值不值"只看可判定的事实，不看感觉：

1. **变体数 ≥ 2 且语义相同** → 抽出来是收益；
2. **只有 1 个生产调用方** → 抽象是负债（多一层跳转，读者要跨文件才能拼出行为）；
3. **它防御的场景在生产调用点上不可能发生** → 是负债。
4. **对一个字段 / 常量 / 导出：生产侧消费者为 0 才算死**；只有测试消费 = 半死（测试在替一个没人用的计算背书）。判定要看点号访问，不看名字出现次数。

第 2、3 条要**验证**，不能猜：
- 第 2 条：grep 该符号/组件的所有出现点，区分"生产调用"与"测试调用"，把数量写进报告；
- 第 3 条：去看每个真实调用点传的实参。例：`shared/useResource.js` 的调用方全传模块级常量，
  所以"防御调用方传内联数组"的内容指纹层前提不成立，判定为负债（四个调用方逐一核对过）。

## 重复度要量化，不要"看着像"

用 `difflib.SequenceMatcher` 数逐字相同的行，**分母取较短文件**，并**同时给出剔除空行与 import 行后的数字**
（空行和 import 会虚高占比，两个数字都给才经得起追问）。

```python
# 用项目 venv 的 python 跑；不要写临时脚本文件，用 heredoc
import difflib
def keep(lines):
    out = []
    for l in lines:
        s = l.strip()
        if not s or s.startswith(('import ', 'from ')):
            continue
        out.append(l)
    return out
A = keep(open(a).read().splitlines()); B = keep(open(b).read().splitlines())
sm = difflib.SequenceMatcher(None, A, B, autojunk=False)
same = sum(bl.size for bl in sm.get_matching_blocks())
print(f'{same} / {min(len(A), len(B))} = {same/min(len(A),len(B))*100:.0f}%')
```

报告里写清口径，例如：`read_path.py`（339 ↔ 340）相同 228 行 = 67%（剔空行/import 后 71%）。

**坑**：
- macOS 的 BSD `diff` **不支持** GNU 的 `--old-line-format` / `--unchanged-line-format`，会直接报
  `unrecognized option` 并退出，管道后面的 `grep -c` 拿到 0 —— 看起来像"完全没有重复"，极易误判。别用。
- 退而求其次的 `diff a b | grep -cE "^[<>]"` 只能得到"变动行数"，无法给出相同行数，不够用。
- BSD `grep "\|"` **不是**交替（会当字面量），一律写 `grep -E "a|b"`。

## 找"过度设计"的高产位置（按命中率排序）

1. **零消费 / 恒取默认值的 props 与参数** —— 对每个可疑 prop 单独 grep：
   `grep -rnE "<Panel[^>]*className"`、`grep -rn "headingLevel"`。常命中"传的值恰好等于默认值"这种半死代码
   （删除时要连调用处的冗余传参一起清）。注意文件注释里常留同类清理的记录，
   据此点出"这是清理漏网"比单纯列出更有说服力。
2. **只有一个调用方的"可复用"抽象** —— 组件注释常自称"供 X 类页面复用"，而生产调用方只有一个。
   但要检查**测试是否独立渲染它**：如果测试直接以 props 渲染，那"必须能独立渲染"是正当理由，
   应明确写"钩子/path 参数化合理"，只挑出其中真正多余的那一两个参数（如 `errorMessage`）。
3. **死代码与一行包装** —— grep 函数/类名，确认 0 引用。特别留意：同一个一行包装在 N 个模块各定义一次，
   而别处又直接内联实现（同一件事两种写法）。
4. **为可测试性加的可配置性泄漏到生产路径** —— 构造器里出现
   `X if X is not None else (读配置 if client is None else <魔法常量>)` 这类三分支，就说明
   "行为取决于是否注入依赖"，通常伴随"注入时用的是硬编码值，与配置里的值不同"。这是高危信号，
   要在报告里把**两个具体数值**列出来（如 100 vs 20）才够有说服力。
5. **防御不存在场景的防御层** —— 见上文判据 3。代价通常是 `eslint-disable`、双重缓存、
   额外的指纹/归一化函数。写清"删掉后 linter 也不再需要被绕过"。
6. **同一概念的多套映射/多份实现** —— 例如"上游失败 → 错误码"在一个文件里按三种键各写一张表。
   不是 bug，但要说清"读者必须同时记住三张表才能回答一个问题"。
7. **同名不同义** —— 两个模块导出同名函数但语义相反（一个做 `Math.abs()`，一个不做），
   而其中一份的注释还自称"全站唯一实现"。这类隐式耦合**没有测试会红**，风险要单独强调。

## 找"复杂/不易读"的高产位置

- **N 个兄弟模块的同一层文件**（`read_path` / `views` / `writer` / `source_versions` …）：先量重复度，
  再判断"差异是否只在 3~5 个注入点"。若是，给出模板化方案与**预计净减行数**。
- **长函数里的位置参数**：`f(0, 0, (0,), None, None, 'msg')` 连续多个 `0`/`None` 是明确信号，
  建议改关键字参数或收敛成小 dataclass。
- **遮蔽导入名的参数**：如 `def f(sleep=None)` 配 `__import__('time').sleep`。查同一模块内是否有别的函数
  已用更清晰的命名（常能发现同模块两种命名并存）。
- **超长单组件**：判断标准不是行数，而是"里面有没有不属于本组件职责的部分"（弹层定位、焦点陷阱等
  任何弹出层都要的能力）。纯函数已抽出的部分要明确判为"没问题"。
- **魔法数字**：内联的图表高度、重复出现的动画时长、无名的探活间隔。检查项目是否已有集中处
  （设计令牌文件、theme 文件），若有就说"其余的都在那里，这几处漏了"。

## 报告里必须有的两节

1. **§"明确判定不算问题"** —— 逐条给理由。没有这一节，报告会被读成"到处都要改"，
   团队要么全部忽略，要么改坏东西。判定要点：领域规则确实不同（不是重复）、复杂度换来了
   真实的性能或失败模式覆盖、有实测推导的常量、为省掉 N 个参数透传而用的上下文机制。
   还要包含"**看起来像问题但方向判断正确**"的项（例：core 不能 import 业务异常类，所以映射重复是合理的），
   并补一句"但仍可改成 core 定协议 + 模块注册来消除"。
2. **§建议改动顺序** —— 表格形式：改动 / 预计净减行数 / 风险等级 / 验证方式。
   高风险项要给出"先在一个模块试点"的具体建议。最后加一条 **"不要做的事"**
   （通常是"别为了统一而合并各模块的 models"）—— 这一条能防止团队用力过猛。

## 审慎与诚实

- **不凑数**。宁可 8 条扎实的，不要 25 条含水的。
- 凡引用代码，给 `文件:行号`。凡给结论，给**实测数字**或**具体数值对比**。
- 有些"长文件"是"长但有结构"（三种入口共用同一套辅助、多处日志是运维需要），
  要点明判为不算问题，并说明"拆开反而让某条不变式更难对齐"。
- 只读。不要改代码、不要跑构建/测试（用户要求"只生成报告"时尤其如此）。
- 结构性去重的建议要提醒：**改变的是代码形状而非行为**，验证手段是"现有测试先全绿 + 补行为不变断言"，
  不能以"测试没红"当作等价性证明。

## 落地阶段：把报告改成代码时的教训

报告被采纳后要真的动代码，下面是这类改动反复踩到的点：

1. **"逐字相同的复制粘贴"里常藏着刻意的差异，不要顺手统一。**
   例：三个前端页面外壳的代码 3 份逐字相同，但板块动量页**刻意不渲染 warnings 列表**（后端在该页只发得出
   "N 只有效股票未映射到板块"这一条，属上游覆盖度说明）。共享外壳必须留一个 `showWarnings` 开关。
   → **先跑一遍现有测试再改结构**，让断言替你发现这类差异；别凭"看着一样"下刀。
2. **`@patch` 目标可能是跨行写的，单行 grep 会漏，改了会让 patch 静默变成 no-op。**
   例：`@patch(\n  'hundred_day.views.read_hundred_day',\n  side_effect=...\n)` —— 若 `views.py` 在
   import 期就取走了读函数，patch 不生效，表现是 `AssertionError: 200 != 404`（一个与改动"无关"的断言）。
   → **改共享层前，用真 regex + 跨行模式扫出所有 patch/猴补目标**（`grep -E` 或检索工具，不要 BSD `grep "\|"`）；
   被 patch 的模块级名字必须**在调用时才解析**（包一层 lambda / 函数内查表），不能 import 期绑定。
3. **把两个"同名不同义"的函数合并前，先核对入参单位 —— 报告里的措辞可能是错的。**
   例：两处 `formatRatioPercent` 并非"只差 `Math.abs`"，而是一个收 **0~1 的比例**自己 ×100、
   另一个收**已经是百分比数值**（调用方先 ×100 了）。**不可互换**，正确处理是**改名**而不是合并。
   → 报告可以指出"存在第二份实现"，但"怎么处理"要在动手时用调用点复核。
4. **抽取共享模块时，注意它会被哪些"非打包器"消费者 import。**
   例：`shared/charts/chartTheme.js` 与从它拆出的 `features/sector-flow/flowOption.js`
   都会被**裸 Node**（ECharts SSR 脚本）直接 import，一旦它们再 import 兄弟模块（如 `chartBaseline.js`），
   specifier **必须带扩展名**（`.js`），因为 Node 的 ESM 不做后缀推断；bundler 下从来不需要，极易漏。
5. **结构性去重会把"隐式契约"变成显式的，必须写进文档串。**
   例：`envelopeErrorCodes` 必须是"**模块级常量**"（它直接进依赖数组），"随便传"会出问题；
   hook 的默认值也得是模块级常量而不是内联字面量，否则不传参的调用方每次渲染换引用 → 请求风暴。
   → 消掉防御层的同时，**把新契约写在 JSDoc 上**，否则下一个人会重新踩进去。
6. **期望值不要从生产代码里算：测试改断言时用字面量。**
   例：`integration.test.jsx` 若用页面自己的 path 构造函数算期望路径，构造函数写错也照样全绿。
   改成字面量后约束力立刻变强。
7. **验证怎么给**：后端全量测试（本仓库要先清锁与缓存，带 `CODEBUDDY_SAFE_DELETE_ENABLED=0`，
   输出重定向到文件再过滤）+ 前端全量 vitest + eslint + build。
   新增的"行为不变"断言要**做变异验证**（故意改回旧行为，确认它真的变红）——
   否则只是又一条没牙的断言，参见 `.workbuddy/skills/test-assertion-discipline/SKILL.md`。

### 动"配置语义"与"构造器默认值"时的教训

背景是收敛 `.env` 旋钮 + 让 `settings` 成为构造器的唯一真源：

8. **"标志为需用户确认"的条目，问之前先把取证做完，问的时候给可执行的选项。**
   例：两条待确认项（4 个旋钮收敛成 2 个；构造器按"是否注入 client"隐式换源）本身是**配置语义**决策，
   但"每个旋钮到底有没有用"是纯代码事实 —— 先把四个旋钮逐个定位到真实调用点、把
   "同一份参数在注入前后取到哪个值"列成表，用户看完直接就能拍板。
   → 报告里标"需产品确认"的条目，**不要在猜的前提下问**；也不要把纯事实问题包装成需要决策的问题。
9. **"参数来源会因注入了某个对象而变化"是构造函数里最值钱的一类坏味道，改法是消灭分支而不是补默认值。**
   例：`KaipanlaSectorFundFlowFetcher(client=...)` 注入后 `max_pages` 从 `.env` 的 20 变成写死的 **100**、
   `retry_delay_seconds` 变成 **0.0**、`page_size` 直接 `None.page_size` 崩。三个参数都会"看情况换源"。
   → 判据：**注入对象应只影响它负责的维度**（这里是传输），其余默认值必须与注入无关。
   做法是"显式传就用、否则一律取同一份配置"（本仓库落成 `fetch_settings(client_settings=None)` 一个入口）。
   改完**用真实 `.env` 打一行实测值出来**，比读代码更有说服力（本例：`80 / 2 / 1.0 / 20`）。
10. **把 `.env` 项降级成常量时，必须同时回答"还会有谁读到这个名字"。**
    例：一个旋钮的"删除"要动 `.env`、`.env.example`、两张运维文档表、以及 AI 记忆/技能里的引用；
    另一个"改名"要连带改语义注释（旧名 `TARGET_SECONDS` 让人以为能延长抓取时长）。
    → 先全仓检索（`grep -rn -E "A|B"`，BSD grep 的 `\|` 不成交代，务必用 `-E`），把**注释/文档/记忆**也算进爆炸半径；
    另外给"看起来像旋钮其实只是提示值"的项**在 `.env.example` 就地写清它不是旋钮**，否则下次又有人去调它。
11. **不可达的防御分支保留时，要把它变成"能被测试踩到的边界断言"。**
    例：单页行数闸门正常不可达（上游单页硬上限 `MAX_PAGE_SIZE = 80`，闸门取同一个值）。
    保留它，但补一条"恰好 N 行放行、N+1 行拒绝"的边界断言，并断言闸门常量与上游单页上限**同源**
    （都等于 `MAX_PAGE_SIZE`）—— 常量漂移会立刻被抓住。变异验证用 `>` 改成 `>=`。

### "死代码 / 重复 / 难读"复查时的教训

12. **死代码扫描会被框架的"字符串 / 发现式引用"打成筛子，必须先排除注册文件再人工核对。**
    例：`ast` 扫"模块级定义从未被名字引用"，第一遍 **100 个命中全是误报** —— Django 测试类、`ModelAdmin`
    子类、`MIDDLEWARE` / `TEMPLATES` / `DATABASE_ROUTERS` / `CSRF_FAILURE_VIEW` 这些**设置项**、
    `WSGI_APPLICATION`、URLconf 里被调用的视图。它们全靠**字符串或框架发现**被引用，名字在 Python 里一次都不出现。
    排除 `tests/`、`admin.py`、`settings.py`、`apps.py`、`urls.py`、`checks.py`、`manage.py` 后只剩 8 个候选，
    逐个核对**全部在用**。→ 结论要能写成"后端生产代码无死代码"，而不是交一份 100 条的假清单。
13. **"零外部消费的导出"要用 Node ESM namespace 证实，不能靠 ESLint，也不能靠"测试全绿"。**
    `eslint --max-warnings=0` 管的是未使用的**局部变量**，对"导出了但没人 import"**不报**（lint 干净 ≠ 无死导出）。
    最硬的证据是把真实导出面打出来：`node --input-type=module -e "console.log(Object.keys(await import('./x.js')).sort())"`
    （本例 16 → 5）。另一个陷阱：**Vite/vitest 下 import 一个不存在的导出往往只是拿到 `undefined`，而不是构建报错**，
    所以"测试全绿"根本不能证明没人用它 —— 必须全仓 grep 出所有引用点，再逐个判断是"生产消费"还是"文档 / 注释 / 记忆里的名字"。
14. **抽不抽，看判据里的"语义相同"，不看"长得像"。**
    正例：`animationDuration: 320` 三处是**同一个语义**（同一套基线的入场节奏）→ 提成常量合理；并且补的断言要
    **只断"三者一致"，不断 `320` 这个字面值**（时长可以调，漂移才是 bug）。
    反例：4 个图表的内联高度（340 / 360 / 380）虽然也是散落数字，但**各自是独立的设计取值、没有共同语义**，
    按判据①（变体数 ≥2 **且语义相同**）不成立 → 明确不动，并在报告里写出理由，省得下次再讨论一遍。
    同理 `DatePicker` 339 行：全仓只有**一个**弹层，抽 `usePopoverPlacement` / `useFocusTrap` 是**为 1 个调用方建抽象**，
    判据②直接否决。**"文件长"本身不是拆的理由。**
    附带一条：**只把标量抽成常量，不抽对象字面量** —— 同一份 option 片段被多处 spread 时，共享可变引用有被
    ECharts 就地合并的风险。
15. **收敛导出面 / 改名的爆炸半径，包含"按名字指向它的文档与记忆"。**
    例：`tokens.css` 与 `frontend-conventions.md` 都按名字指着 `chartTheme.js` 的 `CHART`；把 11 个零消费导出
    收回模块内之后，那条"图表配色只允许引用 `CHART`"的记忆就变成**不可执行**的了。
    → 与第 10 条同类：**注释 / 文档 / AI 记忆 / 技能都算进爆炸半径**，改完逐个扫一遍。

### 再审"死代码 / 重复 / 冗余"时的教训

16. **"生产读方为 0"必须看**点号访问**，不能看名字出现次数 —— 否则会把 payload 的 dict key 当成消费者。**
    例：`grep -c group_counts` 在 `read_path.py` 有命中，但那行是 `'group_counts': {...}`（读路径自己组装的**报文键**），
    不是"读取 `analysis.group_counts`"。用"名字出现次数"做判据，这条最有价值的发现会被自己的脚本判成"不算问题"。
    → 正确做法：对每个候选字段，把**所有点号访问点**打出来（`grep -rnE "(analysis|result|ranking|summary|point|flag)\.[a-z_]+"`），
    再人眼分成"读的是分析对象"与"读的是数据库行 / 报文键"。
17. **dataclass 字段只有测试读 = 半死代码，而且有一条很可靠的三角信号。**
    例（三个模块各命中）：**① 写时在 `analysis.py` 里算出来挂上 dataclass；② writer 只取明细、从不读它；
    ③ 同一个数字在 `read_path.py` 里被重算一遍**。三者同时出现，即可断定字段是死的 —— 它是"表结构简化"的未收尾另一半。
    这样的是 **8 个字段 / 约 40~50 行**，唯一消费者是 `tests/test_analysis.py` 之类的断言。
    → 报告里要预先反驳"测试在用它所以不能删"：**测试在为一个没有生产消费者的计算背书，本身就是这条发现的证据**。
    附带一个更硬的命中：某字段的唯一"用途"是用 `Dataclass(**{**x.__dict__, 'field': v})` **重建整个 frozen dataclass** ——
    为一个没人读的字段重建 N 个对象，改成 `return tuple(sorted_rankings)` 即可。
18. **"零引用的模块级赋值"扫描要单独排除 `settings.py`，否则 100% 是误报。**
    例：扫出 14 个"零引用赋值"，**全部**是 `SECRET_KEY` / `MIDDLEWARE` / `TEMPLATES` / `DATABASE_ROUTERS` / `CSRF_FAILURE_VIEW`
    这类 Django 设置项（靠字符串被框架读）。定义扫描排除 `settings.py` 已有共识，赋值扫描同样要排除。
19. **`export` 多余 ≠ 常量无用；要分开报，别把两件事混成一条。**
    例：7 处里 4 个 `*_ENVELOPE_ERROR_CODES` + 3 个 `*_ENDPOINT` 都在**定义文件内**被用（`:18` / `:22` / `:32`），
    所以常量是活的、只有 `export` 关键字是死的（1 行）。同一次扫描里另有一个**真死函数**（全仓 0 引用，同文件的兄弟函数被用 8 次）。
    → 报告分两行写："多余 export × 7" 与 "死函数 × 1"，净减行数完全不同。
20. **死 CSS 扫描会把"模板串类名"全部误报，必须人工分流。**
    例：抽 124 个类名 → 报 7 个死 → 其中 **6 个是 `className={\`ranking--${direction}\`}`** 这种动态拼接
    （另一半取值 `--up/--down/--error/--success` 也一并被标死）。真死的只有 1 个。
    → 判据：这个类名在 js/jsx 里**一次都不出现**才算死；只出现"基名 + `--`"的要去找它的 `${}` 生成处。
21. **同名不同义的异常类，最硬的证据是两行 `is` 与两行函数返回值。**
    例：`core.X is svc.X -> False`，`upstream_error_code_value(core.X('x')) -> 'UPSTREAM_RATE_LIMITED'` 而
    `upstream_error_code_value(svc.X('x')) -> None`。一条命令就把"两套类 + 映射漏一半"钉死，比读 200 行代码快得多。
    → 这类耦合**没有测试会红**，报告里要把"哪个日志字段会空"追到具体事件名（例：`data_command_failed.error_code` 恒空），
    并给严重程度定级（定为低-中：信息未丢失，另一个事件仍有 `failure_kind`）。
22. **抽配置校验，先看有没有"封闭集合"形式的测试挡路。**
    例：想把三份逐字相同的配置校验 helper 抽到公共层，发现 `backend/tests/test_source_policy.py` 有一个
    `APPROVED_REQUEST_CLIENTS` 的**相等断言**（`assertEqual(actual, {...})`）—— 新建模块文件会让它直接红。
    于是抽到**已存在的** `backend/env.py`（它本来就是配置层、三家都已 import）。**"抽到哪里"往往由测试决定，不由品味决定。**
23. **"需产品确认"的项，要给反方理由。**
    例：某张采集表有 8 个只写不读的列。它们**不是别的行的函数**（项目那条"能读时算的不落库"不适用）、
    README 已把完整字段清单写进文档（说明是有意采全）。这种项要写成"需你拍板 + 反方理由 + 若要删连带改哪份文档"，
    不要伪装成明显的 bug。

### 落地"删除与收敛"类改动时的教训

24. **"为死字段赋值而重建整个对象"是这类删除里最容易漏的形态。**
    例：某句 `Dataclass(**{**obj.__dict__, 'rank': index})` 只在一处出现，
    grep 字段名只命中一次；但读原文才知道同一段里的 `sorted(...)[:_MAX_RANKINGS]` **同时承担 top-10 截断**。
    正确改法是只删重建、保留截断（`return tuple(sorted(...)[:_MAX_RANKINGS])`）。**删字段前先确认那条 `sorted` 还有没有别的职责。**
25. **删掉写入侧的派生值后，读路径里"解释为什么算得出来"的注释会立刻过期。**
    例：某 `_warnings()` 的文档串写着"顺序跟着写入时的行情遍历顺序"——写入侧一删，这句话就成了误导。
    报告里"改代码"的清单要**连注释一起列**，否则下一个人照旧注释推理。
26. **"留空即未配置"这条口径要一路贯彻到新写的读取处。**
    `get_setting(name, default)` 只在**未设置**时给默认值；`os.environ` 里存在空串会原样返回空串。
    而运维两种写法都会用（删掉一整行 vs 写 `KEY=`）。所以凡"不配置就回落"的读取点，都要显式 `.strip() or 默认值`，
    否则会把空 `User-Agent` 之类的空值真发出去。
27. **把重复的异常类收敛成一份后，必须补 `assertIs`。**
    "抛出的异常是 `KaipanlaRateLimitError`"在两侧同名的情况下**照样能通过**（各自抛自己那个同名类）。
    唯一判别式是 `assertIs(flow.X, industry.X)`。同理，"两侧共用同一份请求头/常量"也要有断言，不能只靠代码读起来像。
28. **变异验证要"复现原缺陷取值"，不只是"变红"。**
    报告写的是"改回 `None` 必须变红"，实测时除了看 FAIL，还要看断言里的实际值确实回到了缺陷态
    （例：`AssertionError: None != 'UPSTREAM_RATE_LIMITED'`）。否则可能只是一条无关断言在挡。
29. **实现时新增的文件会撞"封闭集合"测试，落点优先选已存在的包。**
    例：上游契约放到已存在的 `core/integrations/kaipanla/` 内（与 `hithink/contracts.py` 对称），
    而不是新建顶层模块 —— 这条与第 22 条是同一件事的两面：**审查阶段判断"能不能抽"，实现阶段决定"抽到哪个文件"。**
30. **删除动作的复核是 `ls`，不是命令退出码。**
    组合删除命令可能被权限审批拦下（退出码 0、无输出，文件仍在）。
    **`exit=0` 不能证明文件消失**，必须列目录复核；`rm -v` 的 verbose 输出也可能被吞掉。
31. **测试助手含 JSX 就必须 `.jsx` 后缀。**
    vitest 按扩展名决定是否过 JSX 转换：`src/test/refreshStamp.js` 里写 JSX 是构建期硬错，不是 lint 警告。
    另外共享助手**不要在内部用生产代码推导期望值**（如自己拼 endpoint），否则构造函数写错也照样全绿 —— 期望值由调用方给字面量。

## 交付

报告写到仓库根（或用户指定位置），命名带日期与主题，如 `CODE-REVIEW-YYYY-MM-DD-simplicity.md`。
若仓库已有同日缺陷类报告，用后缀区分主题，并在两侧各加一句边界声明。
最后把报告路径交给用户查看。
