# A 股市场复盘系统合并构想

**状态：** 需求构想已确认  
**日期：** 2026年9月8日  
**目标仓库：** `/Users/lian/dev/lian-dev/a_share_market_review`

## Problem Statement

如何将 `fundflow` 的盘中板块资金流功能和 `fupan` 的盘后个股分析功能整合成一个统一产品，同时保证五个业务模块彼此零依赖、可以独立启停和下线，并通过公共基础层共享可信的市场原始数据、认证、缓存和运行状态能力。

## Recommended Direction

建立一个部署在阿里云服务器、面向个人使用的模块化 A 股盘中监控与盘后复盘系统。

系统由一个不可删除的公共基础 App 和五个可独立启用的业务 App 组成。业务 App 通过静态模块注册表接入统一的 React 产品外壳，彼此不导入模型、服务或数据库。公共基础 App 只维护市场事实数据和技术基础设施，不能包含具体分析规则。

系统以 `crontab + Django 管理命令` 预采集、预计算为正常路径；Web API 按“文件缓存、SQLite、远程数据源”顺序读取。Web 请求只同步修复轻量数据，重量级全市场采集或历史重算返回“数据准备中”，避免阻塞请求和长时间锁定 SQLite。

## Target User and Deployment

- 当前主要用户为系统所有者本人。
- 部署在单台阿里云服务器，同时保留本地开发环境。
- 使用 SQLite 和本地文件缓存。
- 需要登录认证，不开放用户自行注册。
- 用户由 Django 管理后台创建、禁用和重置密码。
- 普通登录用户可访问全部业务模块。
- 管理员可管理账号、查看采集状态和详细错误。
- 暂不需要多人协作、角色分工和模块级用户授权。

## Data Architecture

采用“公共原始数据仓库 + 独立分析数据集市”模式。

### 公共数据库

只保存一份：

- 股票基础数据
- 个股日行情
- 交易日数据
- 开盘啦父/子行业
- 行业与股票代码列表（当前快照）
- 公共数据版本和完整性状态

### 业务数据库

每个业务 App 保存自己的：

- 数据源快照
- 筛选结果
- 行业统计结果
- 历史统计序列
- 计算参数
- 所使用的公共数据版本
- 计算和采集状态
- 数据生成时间

三个个股分析 App 使用同一份公共日行情，但各自独立计算和保存分析结果。

## Sector Definition

“板块动量”和“百日新高新低占比”统一使用：

> 开盘啦父行业目录（其股票列表由下属子行业成分股去重汇总）

第一阶段约束：

- 行业—股票关系由开盘啦链路“父行业 → 子行业 → 子行业股票列表”生成；父、子行业都必须入库，但当前只有父行业可用于分析、API 和前端展示。
- 子行业记录仅用于保存完整采集快照和未来扩展；当前不得出现在用户可见的行业标签、排行、图表或明细中。
- 父行业的 `stock_codes` 由其下属子行业的股票列表去重汇总后写入；同一股票可以属于多个父行业，统计时在每个所属父行业中分别计入；不做股票到单一行业的强制归属。
- 不保留行业关系的历史有效期；当前成功同步的快照直接作为分析使用的行业关系。
- 行业—股票表固定只有四个业务字段：`industry_code`、`industry_name`、`industry_level`（`parent`/`child`）和 `stock_codes`（JSON 股票代码列表）。该表是扁平行业快照；父子链路仅用于采集，不额外增加父行业外键字段。
- 开盘啦、东方财富资金流板块体系与开盘啦行业—股票体系分别保留，不强制建立跨来源映射。

### Authentication and response contract

公开接口使用 API Key 鉴权，REST 能力通过 `X-api-key` 请求头访问。所有接口使用统一响应信封：

- `code`
- `message`

- `data`

- `5002`：上游超时
- `5003`：上游不可用

- `date_ms`

## Historical Initialization

公共个股日行情只初始化最近一年：

- 使用以初始化执行日为终点的滚动最近一年日期窗口
- 只保存区间内的交易日数据
- 固定使用前复权日 K（`adjust=forward`）作为原始事实数据
- 涨跌幅通过相邻交易日的前复权收盘价计算
- 首次部署且公共日行情为空时，手动运行一次初始化命令；初始化以执行日为终点下载最近一年历史日线
- 初始化成功后，不再运行或由任何请求触发最近一年全量初始化
- 后续每日由 `crontab` 仅同步当天的个股交易数据；重复运行必须幂等地补齐或覆盖该交易日，不能扩展为最近一年全量抓取
- 百日新高新低计算使用其中最近 100 个有效交易日

不使用全市场 dump；首次初始化先同步全量 A 股代码表，再以低并发逐只请求最近一年历史日线，失败时保留最近成功版本。Web API 只能读取缓存、数据库或进行严格受限的轻量修复，绝不调用历史初始化或全市场日行情同步。

## Market Close and Data Availability

不再使用原 `fupan` 的 18:00 规则。

统一使用 Asia/Shanghai 时区下的实际 A 股收盘时间：

> 15:00

规则：

- 交易日 15:00 前，当日盘后个股分析尚不可用，默认返回最近一个完整交易日。
- 交易日 15:00 后，当日数据进入可获取和可计算状态。
- 到达 15:00 只表示允许尝试获取当日数据，不代表远程数据源必然已经准备完成。
- 只有通过完整性校验的数据批次才能成为当日正式版本。
- 15:00 后数据仍未就绪时，返回最近完整数据并标记 `stale`，或返回“数据准备中”。

## Data Versioning

公共行情同步成功后产生明确的数据版本，至少关联：

- 交易日期
- 同步批次
- 数据来源
- 行情记录数量
- 有效股票数量
- 缺失数量
- 行业关系版本
- 完整性状态
- 完成时间
- 补录或修正原因

业务 App 根据公共数据版本判断自己的结果是否需要重新计算，不通过业务 App 之间互相通知或调用来保持一致。

## Data Retrieval and Recovery

正常路径：

> crontab → 管理命令 → 获取 → 校验 → 入库 → 计算 → 缓存

Web API 读取路径：

> 文件缓存 → 本地数据库 → 远程数据源

远程兜底要求：

- 相同业务日期和数据类型只能有一个获取任务运行。
- 获取成功后复用管理命令的校验、入库和缓存服务。
- 有旧数据时优先返回旧数据并标记 `stale`。
- 完全没有数据且远程获取失败时才返回错误。
- 开盘啦、东方财富单时间点等轻量数据可以同步修复。
- 全市场行情、历史初始化和大范围重算不得长期阻塞 HTTP 请求。
- 重量任务进入“数据准备中”状态，由前端稍后重新查询。

### Lightweight synchronous repair limit

同步修复必须尽可能小，推荐采用以下保守边界：

- 只允许预计 3 秒内完成的操作进入同步兜底。
- 同步路径总超时默认不超过 5 秒，并通过 `.env` 配置。
- 单次远程返回或写入规模原则上不超过 1,000 条。
- 同步路径不进行长时间重试，最多进行一次有界远程尝试。
- 只缺少本地派生结果、且公共原始数据已经完整时，可以在时间预算内进行本地计算。
- 预计超时、超量或需要全市场同步时，立即转为“数据准备中”，不在 HTTP 请求内继续执行。

具体阈值后续可以根据实际运行时间向下收紧，而不是逐步放宽为重量任务。

## API Contract

所有 API 以 `/api/` 开头，并按模块分发。

统一响应外壳表达：

- 请求状态
- 业务日期
- 数据生成时间
- 数据版本
- 是否过期
- 数据来源
- 数据准备状态
- 警告信息
- 错误代码和错误信息
- 业务数据正文

统一的是响应外壳，不强制五个模块使用相同的业务正文结构。

## Lightweight Operations Center

模块状态中心放在 Django 管理后台，不增加独立的前端业务页面。

至少展示：

- 模块和数据类型
- 最新业务日期
- 最新成功时间
- 最近运行状态
- 是否正在运行
- 数据完整性
- 数据版本
- 是否正在返回旧数据
- 连续失败次数
- 简短错误摘要

各业务 App 自己保留详细错误和执行记录。第一阶段不建设完整任务调度平台。

## Backup, Retention and Notifications

- SQLite 数据库备份由系统所有者手动处理。
- 文件缓存备份、保留和清理由系统所有者手动处理。
- 项目不提供自动备份、自动归档或自动清理功能。
- 连续采集失败时不发送邮件、短信、企业微信或其他外部通知。
- 失败状态只记录在日志、对应业务 App 的运行记录和 Django 管理后台中。

## Key Assumptions to Validate

- [x] **REST 契约可用**：已验证同花顺 REST 鉴权、股票列表、交易日历和最近一年单股票前复权日线；无需 Python SDK。
- [x] **当前 API Key capability 足够**：已验证代码表、交易日历和单股票历史日线；行业—股票关系不使用同花顺 API。
- [x] **开盘啦父/子行业链路可用**：已实测父行业、子行业和子行业股票列表；层级以开盘啦响应确定。
- [ ] **实际额度可控**：以低频、有限重试和失败恢复应对未公开的 REST 与开盘啦 QPS、并发和每日额度。
- [ ] **数据完整性可以判断**：定义每个交易日预期股票范围、缺失容忍度和完整版本标准。
- [ ] **SQLite 可以承载目标负载**：验证 crontab、Web 请求和兜底写入不会产生不可接受的锁竞争。
- [ ] **模块零依赖可以被自动验证**：设计单模块启用测试和禁止跨业务 App 导入的检查方式。

## Not Doing

- 不实现在线安装或卸载插件。
- 不实现动态下载前端模块。
- 不引入微服务。
- 不引入 Celery、Redis 或消息队列。
- 不迁移到 PostgreSQL 或 MySQL。
- 不开放用户注册。
- 不实现多人协作和复杂角色体系。
- 不实现按用户控制模块访问。
- 不分析概念板块和地域板块。
- 不保留开盘啦行业—股票关系的历史有效期。
- 不强制统一开盘啦行业—股票关系与开盘啦、东方财富资金流板块体系。
- 不保留 `fupan` 的上交所和深交所下载流程。
- 不将 BlueStacks、ADB、mitmproxy 纳入生产链路。
- 不迁移未被正式业务使用的历史离线工具。
- 不建设独立的前端运维状态页面。
- 不自动备份或清理 SQLite 和文件缓存。
- 不发送连续采集失败的外部通知。
- 不为了未来可能性设计完整插件框架。

## Success Criteria

- 登录后默认进入开盘啦板块资金流。
- 四个一级模块均保留原有核心功能。
- 全站 UI 样式和颜色语义一致。
- 所有业务 API 均要求登录。
- 个股数据全部来自同花顺 REST API。
- 公共个股日行情只保存最近一年且只保存一份。
- 板块统计使用可验证的开盘啦父行业—股票关系；父行业股票列表由子行业成分股去重汇总，子行业仅保存不展示。
- 五个业务 App 之间不存在代码和数据库依赖。
- 删除任意四个业务 App 后，剩余模块仍能迁移、采集、计算、测试并提供 API。
- 管理命令失败时，已有数据仍然可以访问。
- 轻量缺失数据可以在严格时间和数据量预算内修复。
- 重量任务不会长期阻塞 Web 请求。
- 交易日 15:00 后才允许生成当日盘后分析结果。
- 某个模块或数据源失败不会导致其他模块不可用。
- 管理员可以在 Django 管理后台查看数据日期、版本、完整性和最近运行状态。
