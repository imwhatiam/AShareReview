# A 股市场复盘系统整合规格

**目标仓库：** `<repo>`

> 本文是系统的产品与技术规格，只描述系统的行为、边界和验收方式。

## 0. 已确认前提与规格解释

下列前提是本规格其余部分的基础。

### 0.1 已确认前提

1. 产品是部署在阿里云服务器、主要由系统所有者个人使用的 Web 应用。
2. 前端采用统一产品外壳，通过 Tab 进入四个一级功能模块。
3. 后端由不可删除的 `core` 和四个可插拔业务 Django App 组成。
4. 四个业务 App 彼此零依赖，但都允许依赖 `core` 提供的稳定公共契约。
5. 使用 Django Session 登录认证，不开放注册，不设计多人协作和复杂权限。
6. 使用 SQLite 和本地文件缓存，不引入 Redis、Celery、消息队列或微服务。
7. 正常数据链路是 `crontab → Django 管理命令 → SQLite/文件缓存 → Web API`。
8. Web 请求**不访问上游**：读取链路只有「文件缓存 → 本地库 → 本地按需生成」三步，没有"请求内回源"这回事。只读本地已落库公共数据、为单个交易日生成派生结果的本地计算是允许的请求内工作，它不接触上游、也不扩大数据获取范围（见 5.8(a)）。
9. 个股公共数据只允许通过同花顺正式 REST API 获取：股票列表和单股票历史日线；不使用 Python SDK。**交易日不是上游数据**，不通过任何 REST 端点获取，只由本地 `chinese-calendar` 推导。
10. 开盘啦板块资金流继续使用 `fundflow` 已验证的上游 URL、参数和解析语义。
11. 盘后当日数据从交易日北京时间 15:00 起具备“可以生成”的时间资格，但仍须通过完整性校验；15:00 不等于上游数据必然已全部可取到。
12. 公共日行情首次初始化使用以执行日为终点的滚动最近一年窗口。系统只向业务模块承诺最近一年的公共日行情可用范围；备份、归档和文件缓存清理由系统所有者手动处理。
13. 行业关系同步并保存当前开盘啦行业关系，不保留历史有效期；分析与展示使用同一份行业快照。

### 0.2 本规格采用的解释性假设

以下细节在已确认需求中没有逐项命名，本规格为形成可测试契约采用如下解释：

- “上证/深证四组”按 `core` 的交易所元数据判断。北京证券交易所股票不冒充深证股票：它们不进入上证/深证的涨跌四组，但在 `stock_moves` 中单独构成「北交所上涨」「北交所下跌」两组对外展示并计入「全部复制」（按涨跌方向拆成两组，以匹配"行=市场、列=方向"的看板版式）；它们也可进入全市场成交额、板块动量和百日指标的有效股票集合。
- “全市场涨幅前5%”按涨幅降序取 `max(1, floor(当日有效股票数 × 5%))` 只股票；同涨幅跨越边界时仍按稳定次级排序截断，不扩展样本数。
- 显式无效 API 参数返回 `400`，不得静默截断或回退。
- 百日新高新低的历史缺失（上市前、停牌日）填 `0`，目标日不填，详见 3.1.5。
- “最近一年”指首次初始化和对业务承诺的可查询窗口；数据库备份、归档和文件缓存清理仍由系统所有者手动处理。

### 0.3 外部条件与实施约束

已批准数据源的实际能力边界见 `docs/data-sources/web-api.md` §6：

- 股票列表和单股票最近一年历史日线走 REST 端点；日线使用 `interval=1d`、`adjust=forward`。交易日历不由上游提供（见 §5.2.2）。
- 开盘啦可取得“行业 → 行业股票列表”的完整链路；同一股票可属于多个行业。
- 当前设计不使用同花顺行业目录、行业成分、全市场历史导出或 Python SDK，**唯一例外**是北交所行业归属的增量补齐（见 §5.2.3）。
- 开盘啦资金流接口不提供历史快照时间参数；相应管理命令不提供 `--date`、`--snapshot-time` 或其他显式历史时间参数，只采集上游当前或最近快照。
- 上游未公布固定 QPS、并发和每日额度，连续调用会触发 HTTP 429；实现必须采用可配置低并发、请求间隔、有限退避和失败保留旧版本。

若已批准端点、开盘啦链路或实际额度无法满足最近一年逐股票同步，不得静默改用个股爬虫、浏览器自动化或其他未批准数据源；应先更新规格或获得用户确认。

## 1. 背景和目标

### 1.1 背景

系统把四类盘中/盘后分析能力整合到一个 Web 应用中：开盘啦板块资金流、大涨跌幅与大成交量个股、板块动量、百日新高新低占比。四者共用同一套页面外壳、数据来源、数据库、缓存、初始化方式和 API 路径。

个股数据统一走同花顺 REST API，行业—股票关系统一走开盘啦。整合的目标是在保留核心业务功能的同时建立可长期维护的模块边界，使任何一个业务模块的失败、停用或删除都不影响其他业务模块。

### 1.2 产品目标

构建一个统一的 A 股盘中监控与盘后复盘系统，提供四个一级入口：

1. 板块资金流
   - 开盘啦
2. 大涨跌幅与大成交量个股
3. 板块动量
4. 百日新高新低占比

登录后默认进入“板块资金流 → 开盘啦”。

### 1.3 架构目标

- 建立一个不可删除的公共基础 App：`core`。
- 建立四个相互独立的业务 App：`kaipanla`、`stock_moves`、`sector_momentum`、`hundred_day`。
- 每个业务 App 独立拥有模型、迁移、数据库、URL、视图、服务、管理命令、缓存命名空间和测试。
- 业务 App 只通过 `core` 的公开服务接口和稳定标识访问公共数据。
- 禁止业务 App 之间直接调用、导入或查询彼此的数据。
- 删除任意三个业务 App 后，`core` 与剩余 App 仍能启动、迁移、采集、计算、测试并提供 API。

### 1.4 数据目标

- `core` 保存一份公共个股原始日行情，供三个盘后分析 App 使用。
- `core` 保存股票基础信息，以及当前开盘啦行业—股票快照（`industry_code`、`industry_name`、`stock_codes`）。交易日不落库，由本地 `chinese-calendar` 按需推导（见 §5.2.2）。
- 业务 App 保存自己的上游快照或派生分析结果，不复制公共原始日行情。
- 派生结果用业务日期引用它所依赖的公共数据，而不是依赖另一个业务 App 的执行结果。公共数据每天以「股票 + 交易日期」整批 upsert 覆盖，所以同一天不会有第二套口径；派生结果按 `business_date` 唯一，同一天重跑是覆盖。（本项目**没有**独立的版本号层：重算公共数据后要跟着重跑那一天的 `build_*`，见 §5.2.5。）
- 管理命令失败时，系统优先继续提供已有缓存或数据库数据，并明确标识数据是否过期。

### 1.5 成功定义

系统成功整合后，用户在一个登录入口和统一界面中完成原有盘中、盘后分析工作；模块边界可通过自动测试证明；数据缺失和上游故障不会导致整个站点不可用，也不会在 Web 请求中触发无边界的重任务。

## 2. 能力地图和依赖边界

本项目包含多个可独立验收的能力。以下模块 ID 在后续规格、计划和测试中保持稳定。

| 模块 ID | 类型 | 职责 | 允许依赖 |
|---|---|---|---|
| `core` | 基础能力 | 认证、模块注册、公共市场事实数据、缓存工具、锁 | Django、同花顺正式 REST API 受控适配层 |
| `kaipanla` | 业务能力 | 开盘啦板块资金流采集、快照、排行和分时/多日查询 | `core` |
| `stock_moves` | 业务能力 | 大涨跌幅与大成交量个股分析（仅板块标签） | `core` |
| `sector_momentum` | 业务能力 | 开盘啦板块动量分析 | `core` |
| `hundred_day` | 业务能力 | 百日新高新低及板块占比分析 | `core` |
| `frontend-shell` | 产品外壳 | 登录态、一级/二级 Tab、统一视觉、模块装载和通用状态展示 | `core` 和各已启用业务 API 的公开契约 |

依赖方向必须始终为：

```text
frontend-shell → core
frontend-shell → enabled business API contracts
kaipanla       → core
 stock_moves   → core
 sector_momentum → core
 hundred_day   → core
```

禁止形成业务模块之间的依赖边：

```text
kaipanla/stock_moves/sector_momentum/hundred_day
    ──X──> 任意其他业务 App
```

推荐的后续实现顺序是：先建立 `core` 的配置、数据和接口契约；随后四个业务 App 可按公共数据就绪情况并行迁移；统一前端外壳在 API 契约确定后接入各模块；最后进行单模块删除测试和端到端整合验收。该顺序仅用于说明依赖。

## 3. 范围与非目标

### 3.1 本期范围

#### 3.1.1 统一产品外壳

- 登录页面、退出入口和登录态检查。
- 四个一级 Tab，只显示文字标签，不显示左侧图标（见 AC-UI-003）。
- 默认路由为开盘啦板块资金流。
- 统一页面宽度、字体、间距、卡片、按钮、日期控件、看板、排行列表、图表和提示样式。
- 日期控件使用自绘的日历弹层（触发器沿用输入框的边框 / 圆角 / 字号尺度，弹层使用品牌色选中态与轻阴影），不呈现浏览器原生 `input[type=date]` 的日历弹层，以保持各页面视觉一致。
- 统一颜色语义：A 股上涨为红色、下跌为绿色；状态色与涨跌色分离。
- 统一加载、空数据、过期数据、数据准备中、请求失败和无权限状态。
- 四个页面共用同一条日期回填规则（`shared/businessDate.js`）：未手选日期时日期控件显示后端返回的业务日期。否则控件只会显示占位文案「最新交易日」，用户看不到自己在看哪一天。
- 根据静态模块注册表和启用开关显示或隐藏模块入口。

#### 3.1.2 开盘啦板块资金流

保留 `fundflow` 的以下核心行为：

- 采集开盘啦全量分页板块排行。
- 保存交易日内板块资金流快照。
- 快照落库时刻由运行时刻决定，且必须落在标准 5 分钟槽上（交易日为 09:30–11:30、13:00–15:00 共 50 个槽）：盘中向前回退到所在槽（09:33 → 09:30，10:46 → 10:45，14:22 → 14:20）；午休 11:30–13:00 回退到 11:30；收盘后（含 16:34 等盘后运行）一律落在 15:00。
- 非交易日采集归到最近一个交易日的 15:00；交易日开盘前采集同理归到上一交易日的 15:00（那时最新完整数据仍是上一交易日收盘），不得伪造成当天收盘快照。
- 同一 `sector_code` + `snapshot_time` 重复写入为覆盖（upsert），因此同一槽位内多次采集只保留最后一次；盘后重复运行只会刷新当日 15:00 收盘快照，不新增快照时间。
- 落库时刻的判定统一由 `kaipanla.services.intraday.resolve_snapshot_slot()` 提供，管理命令、`--latest` 与 Web 请求触发的补齐共用同一函数。
- 默认模式只在交易日的连续竞价时段（09:30–11:30、13:00–15:00）采集，闸门由 `core/services/calendar.is_trading_session()` 提供（交易日判定与时段定义同源）。时段比较按整分钟进行：四个边界整点（09:30、11:30、13:00、15:00）所在的整一分钟都算盘中，11:31 与 15:01 起才是盘外。这一分钟不是宽限而是必需 —— 调度是"到点拉起一个进程"，cron 在整点触发，Django 读到时钟时已晚一秒多，只认 `11:30:00.000000` 这一微秒会让 11:30 槽永远采不到。落在时段外（午休、盘前、盘后、周末、节假日）时命令直接跳过：不访问上游、不写库、不记失败日志，以退出码 0 结束 —— 调度器拿到的是"本轮无需采集"，不是故障。只有显式 `--latest` 才绕过该闸门。
- 交易日判定分层：**周末（含调休上班的周末）一律不是交易日**；工作日的法定节假日用第三方库 `chinese-calendar` 判定。系统没有任何上游交易日历，也不存在 `TradingDay` 表；历史交易日与窗口计算同样由 `core/services/calendar.py` 用 `chinese-calendar` 推导。`chinese-calendar` 无该年数据时（按年内置节假日表），该年退化为「工作日即交易日」，并对每个未覆盖年份记一次 WARNING，不中断采集。
- 计算"最近一个交易日收盘"同样只用 `chinese-calendar`，因此没有「日历为空则写入失败」这一分支；交易日永远可推导，不存在「猜测交易日」的问题。
- 图表在上、流入 / 流出排行在下的页面结构；单日模式展示固定交易时间轴上的资金流入和流出排行曲线。
- 折线图不设顶部图例，板块名与当前资金净额常驻在每条折线右端（净额带正负号、单位亿元）。
- 分时横轴刻度取整半点（09:30 / 10:00 / … / 11:30 / 13:00 / … / 15:00 共 10 个），上午 09:30 起、末刻度 15:00；不按索引等间隔抽稀（午休两侧槽位数不等，按索引抽稀会使下午首个刻度错位到 13:05）。午休两侧的 11:30 与 13:00 **两个时刻都会有数据，两个刻度都必须显示**，但它们只隔一个 5 分钟槽、标签会叠字，所以这一对各自贴着自己刻度朝外对齐（11:30 右对齐、13:00 左对齐）：既不合并成一条（等于少一个刻度），也不交给防重叠抽稀丢掉其中一个。
- 日期与统计窗口控件不带外层背景边框，分段按钮与日期控件上下边缘对齐。
- 每侧最多请求 30 条，页面按每侧 10 条展示排行并默认勾选前 5 条。
- 支持用户勾选和取消具体板块曲线。
- 支持当日、5日、10日、20日切换。
- 所有统计窗口都以最近一个已有快照的交易日为终点：点任一窗口按钮都会清空手选日期，按最新交易日往回取 1/5/10/20 个交易日。
- 用户显式选择的日期会成为窗口终点（当日即该日，多日即截止该日）。
- 多日模式使用各交易日 15:00 快照进行汇总和排序。
- 默认勾选跟着**每一次取数结果**走：点「更新于 HH:MM」刷新、切换日期、切换统计窗口后，都按该次响应的榜单重新勾选前 5 名 —— 榜单、勾选与折线图必须来自同一份数据。用户的手动勾选只在当前这份数据内有效（无关的重渲染不得重置它）。
- 展示加载、空数据、错误和过期状态。

#### 3.1.3 大涨跌幅与大成交量个股

- 按交易日查看结果。
- 筛选涨幅 `>= 8%` 且成交额 `>= 8亿元` 的股票。
- 筛选跌幅 `<= -8%` 且成交额 `>= 8亿元` 的股票。
- 按「行 = 市场、列 = 方向」的看板展示：行为上证、深证、北交所，列为上涨、下跌，共六组（`sse_rise`、`sse_fall`、`szse_rise`、`szse_fall`、`bse_rise`、`bse_fall`）。
- 上涨组按涨幅降序、下跌组按涨幅升序（北交所两组同口径）。
- 满足同样阈值的北京证券交易所股票不并入上证/深证四组，而是在两个交易所之后单独占一行，并按涨跌方向拆成「北交所上涨」「北交所下跌」两栏。该行两侧均无股票时不渲染。
- 每只股票渲染为一枚圆角胶囊，只展示名称、涨跌幅和成交额；股票代码不上屏，开盘啦行业标签改由悬浮提示承载。
- 每个交易所半区内的胶囊固定为 3 列（不随窗口宽度在 2~3 列之间浮动）；网格项铺满各自轨道，因此所有胶囊等宽、文字在框内左对齐，右侧留出余量。三列要放得下最长的一条（实测 165.4px 文字 + 左内边距 6px + 边框 1px，轨道需 ≥172.4px 才不压边框，留出完整右内边距需 ≥178.4px），按「轨道宽 =（窗口与 82rem 容器上限取小 − 90px 页面与面板内边距 − 116px 轨道骨架）/ 6」换算约需 1276px 窗口，故 `≤80rem` 退回 2 列、`≤40rem` 退回 1 列。
- 涉及股票总数由复制按钮承载（文案为"共 N 只股票，全部复制"），不单独渲染统计块。总数包含北交所两组的股票。该按钮是纯文字动作：无边框、无底色（`.btn--ghost`），复制图标位于"复制"文字之后。
- 支持一键复制全部涉及股票代码：以英文逗号分隔（不是换行），顺序与页面看板一致（上证涨/跌 → 深证涨/跌 → 北交所涨/跌，组内按排名）。日期控件与复制按钮同处一行并纵向居中对齐，按钮无边框、无底色（`.btn--ghost`），不使用实心品牌蓝，也不用白底描边。

#### 3.1.4 板块动量

- 按交易日分析当前开盘啦行业，并允许同一股票分别计入多个行业。
- 保留“涨幅超过 5%”股票的行业聚集分析。
- 保留“全市场涨幅前 5%”股票的行业聚集分析，样本数为 `max(1, floor(当日有效股票数 × 5%))`。
- 每种口径展示综合评分前 10 的行业。
- 每个行业展示股票数量、平均涨幅、行业成交额占全市场成交额比例、综合评分和涉及股票。
- 综合评分保持原有业务口径：`股票数量 × 平均涨幅 × 行业成交额占比`。
- 两种口径并排在同一行展示（窄屏回到单列），便于左右对照同一批行业。
- 每个口径的图表为竖排分组柱状图：类目轴按名次从左到右排列，评分最高的行业落在最左边；每个行业一组三根子柱，依次表示股票个数、平均涨幅、成交占比。
- 三根子柱量纲不同（只 / 涨幅百分比 / 成交额占比百分比），各占一根数值轴：股票个数在左轴，平均涨幅在右轴，成交占比在右轴的偏移轴上；单位写进图例，避免三套分隔线叠在一起。
- 行业股票明细展开后，在一行内列出该行业全部入选个股，写法为「股票名称（涨幅，成交额）」，不展示股票代码。
- 日期控件与"全市场成交额"同处一行并纵向居中对齐；该指标为纯文字，不带边框与底色。
- 页面不渲染"未映射到开盘啦板块"告警：未映射数量属于上游行业映射的覆盖度说明，用户无法处理且每次都会出现；数量仍保留在接口数据 `unmapped_stock_count` 中（见 §5.5.4）。

#### 3.1.5 百日新高新低占比

- 按交易日计算个股相对前 99 个全市场交易日位置中历史收盘价的百日新高和百日新低。
- 当日收盘价不进入历史比较窗口。
- 当日无有效行情的股票不参与当日判断。
- 缺失值口径：在计算历史滚动窗口前，将新上市前和停牌日的历史缺失收盘价填充为 `0`；目标日收盘价保持原值，不填充。
- 使用 `shift(1).rolling(99)`，要求目标日在全市场交易日序列中已有 99 个历史位置；由于历史缺失已填 `0`，单只股票实际上市不足 99 日时也可参与判断。
- 按开盘啦行业统计新高和新低数量，并展示行业内股票明细；同一股票可显示在多个所属行业。
- 展示当日有效股票总数、新高数量和新低数量；日期控件与这三个指标同处一行并纵向居中对齐。三个指标为纯文字、不带边框与底色，新高用涨色、新低用跌色（文字颜色区分，不用底色块）。
- 展示近期最多 100 个交易日的新高占比和新低占比走势。
- 为生成完整的 100 日趋势，计算输入最多需要目标日前后合计 199 个交易日位置，最近一年公共日行情应覆盖该窗口。

上述历史缺失填 `0` 的行为与严格金融时间序列语义不同，是有意保留的业务算法，由回归样例固化；若调整，应单独修改规格并新增回归样例。

#### 3.1.6 公共基础数据

- A 股股票代码、名称、交易所和有效状态。
- 以执行日为终点的滚动最近一年内前复权个股日行情（`adjust=forward`）。
- 交易日推导与最近交易日计算（`chinese-calendar`，不落库、不访问上游）。
- 当前开盘啦行业目录。
- 当前股票与行业—股票映射，不保留历史有效期。
- 公共数据同步批次标识（`source_batch_id`）与业务日期。
- Django 用户、Session、CSRF、模块注册和后台状态管理。

## 4. 用户流程

### 4.1 登录与首次进入

1. 未登录用户访问产品页面。
2. 系统跳转到登录页面，不加载任何业务数据。
3. 用户输入由管理员创建的账号和密码。
4. 登录成功后，前端获取当前用户和已启用模块列表。
5. 前端进入“板块资金流”一级 Tab，直接打开开盘啦资金流页面。
6. 开盘啦页面在未指定日期时请求最新可用交易日数据。
7. 页面在返回旧数据时显示对应状态提示；`partial` 不单独用 chip 标注（它等价于"存在 warnings"，与紧随其后的告警列表是同一件事），由告警文案直接呈现。

失败行为：

- 登录失败时只提示通用账号或密码错误，不暴露账号是否存在。
- Session 过期时，API 返回未认证状态，前端清理页面数据并回到登录页。
- `kaipanla` 被禁用时，默认入口顺延到第一个已启用业务模块；若没有业务模块启用，则显示“暂无已启用模块”。

### 4.2 浏览板块资金流

1. 用户进入板块资金流页面。
2. 页面不预置浏览器日期：未手选日期时按本模块最近一个已存快照日取数（该日就是页面显示的"最新交易日"），日期控件显示该交易日。当天快照已落库时首屏即为当天，不等待公共日行情，也不被它拖回上一个交易日。
3. 单日模式展示固定交易时间轴；图表下方并排展示各 10 条资金流入排行和资金流出排行。折线图不渲染顶部图例，每条曲线右端常驻板块名与资金净额。
4. 用户勾选排行中的板块，图表即时增加或移除对应曲线。
5. 用户选择 5日、10日或20日时，窗口以最近一个已有快照的交易日为终点，按交易日序列往回取固定交易日窗口，并使用每日 15:00 快照汇总；点任一窗口按钮都会清空手选日期。
6. 用户切回“当日”时恢复单日完整时间轴，同样以最近一个已有快照的交易日为准，日期控件同步显示该交易日。
7. 用户显式选择日期时，该日期成为当前窗口的终点：当日即该日数据，多日即截止该日的窗口。

数据状态行为：

- 缓存命中：直接返回缓存数据。
- 缓存未命中、数据库命中：从数据库构建结果并回写缓存。
- 当天快照还没落库：收盘前返回"数据准备中"（`202`，该日仍在采集窗口内，等 crontab 下一轮），收盘后返回已有旧数据并显示"数据可能已过期"。**读路径不会自己去抓一次**（见 5.8(b)）。
- 该模块采集失败（上游拒绝/缺页）时：页面只把图表和两张排行替换为“数据暂不可用”状态，日期与统计窗口控件保留在原位，不影响其他一级模块。失败只在命令日志里留痕，不会因为一次页面请求而重试上游。
- 任何数据状态下日期与统计窗口控件始终可见：切换日期或统计窗口后若无数据，用户仍可直接改回有数据的条件。

### 4.3 查看大涨跌幅与大成交量个股

1. 用户进入对应一级 Tab。
2. 页面默认请求该模块最新完整交易日。
3. 用户通过日期控件选择其他交易日。
4. 页面以「行 = 市场、列 = 方向」的看板展示上证、深证的上涨和下跌四栏，每只股票是一枚胶囊（名称、涨跌幅、成交额），悬浮显示开盘啦板块；每个交易所半区内的胶囊固定排成 3 列。
5. 有满足阈值的北京证券交易所股票时，在两个交易所之后追加「北交所」一行，同样按涨跌分两栏；两侧都没有股票时不显示该行。
6. 用户点击“复制全部”，复制当日全部涉及股票代码，以英文逗号分隔。
7. 某组无结果时展示空组，不把整个页面视为失败。

如果指定日期缺少可用的本地输入：

- 本地已有该日期的派生结果时，直接返回它。
- 公共日行情可用、只缺派生结果时，用本地已有公共数据当场生成该日期的结果（见 5.8(a)），不发起上游请求。
- 该日期没有公共日行情时，不生成；显式指定日期返回 `404 DATA_NOT_AVAILABLE`，未指定日期则回退到最近可用结果并标识 `stale=true`。
- 需要全市场远程同步时返回“数据准备中”，不得在请求中执行全量同步。

### 4.4 查看板块动量

1. 用户进入“板块动量”。
2. 页面默认显示最新完整交易日。
3. 页面把“涨幅超过5%”和“全市场涨幅前5%”两套结果并排在同一行展示（窄屏回到单列）。
4. 每套结果展示前10行业、三指标分组柱状图和行业股票明细。
5. 用户展开行业后，在一行内看到该行业全部入选个股，每只写作「股票名称（涨幅，成交额）」。
6. 用户切换日期后重新加载对应日期的数据。

如果股票缺少当前行业—股票映射，该股票可以计入全市场成交额和涨幅分位计算，但不能被错误归入任意行业；响应必须给出未映射股票数量警告。

如果该日期已有完整的本地公共日行情但缺派生排名，当场生成该日期的排名（见 5.8(a)），不发起上游请求；没有该日期公共日行情时不生成。

### 4.5 查看百日新高新低占比

1. 用户进入“百日新高新低占比”。
2. 页面默认显示最新具有足够历史窗口的完整交易日。
3. 页面显示有效股票总数、新高数量和新低数量。
4. 页面分别展示新高行业排行和新低行业排行，两个排行并排一行、各显示前 10 个行业。
5. 用户展开行业查看对应股票；明细按当日涨跌幅排序（新高排行降序、新低排行升序即跌得多的在前），写作"名称（涨幅，成交额）"。
6. 页面以柱状图展示近期每日新高占比（横轴上方）和新低占比（横轴下方）走势。
7. 用户切换日期时，图表终点和行业结果同步变化。

当目标日期之前的全市场交易日位置不足 99 个时，页面显示“历史数据不足，无法计算百日指标”，不输出伪造的全零结果。

如果该日期缺派生结果但本地已有足够的公共日行情窗口，当场生成该日期的指标（见 5.8(a)）。该模块是三个按需生成模块中唯一需要跨多交易日读取本地数据的，因此生成耗时最长；它仍然只读本地数据、不访问上游。

### 4.6 管理员查看数据

1. 管理员进入 Django 管理后台。
2. 管理员查看公共数据（股票主数据、行业快照、公共日行情）与四个业务模块的结果数据。
3. 后台**只读**：不提供在线启动、停止或重跑管理命令的入口。
4. 后台**不展示运行状态**。本项目没有运行表，也没有数据集版本表（见 §5.2.5）："上一次跑成功了吗"由命令日志回答（`data_command_started` / `_progress` / `_finished` / `_failed`），运维去 `backend/logs/` 看，库里没有这个答案。
5. 管理员不得在后台或业务页面看到凭据或上游原始敏感响应。

### 4.7 crontab 采集与计算

1. 系统所有者在本地或阿里云通过 crontab 执行 Django 管理命令。
2. 命令获取互斥锁，避免相同数据集重复执行。
3. 命令在日志里记录开始、进度、结束与失败，并留下本次运行的批次标识。
4. 命令采集或计算数据，先写数据库，再生成或失效文件缓存。
5. 全部成功后在**一个事务里整批提交**——写行即发布，库里不另留"已发布"状态位。
6. 数据不完整时按模块规则处理，不存在"半份数据被当成完整结果发布"的状态：公共行情与派生命令整批事务写、不全就整体失败；开盘啦快照不全则一行都不写。
7. 失败时保留旧数据，在日志里记下失败详情，以非零退出码结束。
8. 一个模块命令失败不得中断其他模块的独立 crontab 任务。
9. 调度分三段：**盘中链路**（`refresh_intraday_quotes` 每 30 分钟、`fetch_kaipanla_sector_fund_flow` 每 5 分钟）只刷新当天公共行情与资金流快照，让页面在收盘前就能跟随当天；**盘后定稿**（`refresh_intraday_quotes --latest`，15:35）取已结算的收盘快照并连锁重建三个 `build_*`；**每周日全量校正**（`init_stock_daily_prices --years 1`）重跑最近一年逐只历史行情，补齐历史缺口与复牌股昨收。三段共用同一套数据集与字段语义，因此可以相互覆盖而不产生歧义。

## 5. 数据和接口变化

### 5.1 数据库布局

| 数据库别名/文件 | 所有者 | 内容 |
|---|---|---|
| `core.sqlite3` | `core` | Django 认证、模块注册、公共市场数据 |
| `kaipanla.sqlite3` | `kaipanla` | 开盘啦板块及资金流快照（单表） |
| `stock_moves.sqlite3` | `stock_moves` | 大涨跌幅与大成交量个股派生结果与明细 |
| `sector_momentum.sqlite3` | `sector_momentum` | 行业动量派生结果与排名明细 |
| `hundred_day.sqlite3` | `hundred_day` | 百日新高新低派生结果与个股/行业/趋势明细 |

约束：

- 不允许跨 SQLite 数据库建立数据库外键。
- 业务结果通过股票代码、行业代码和业务日期引用公共事实（**板块资金流例外**：它的快照是上游采集来的原始事实，不引用公共事实；见 5.8(b)）。公共数据每天整批 upsert 覆盖，"同一天"就是唯一的口径边界，没有版本号可对准。
- **业务 App 只读写自己的数据库。** 三个盘后模块通过 `core` 的服务读公共数据（`core.services.market_data` 等），但既不 import `core.models` 也不写 `default` 库。板块资金流更彻底：**完全不碰 `default` 库**，读取链路也不依赖它。
- 业务 App 迁移只作用于自己的数据库。
- `core` 不导入业务 App 模型。
- **`core` 没有数据集版本表，也没有运行状态表**。"这一天是否有数据"就是唯一需要回答的问题，它由"这天的行在不在库里"回答；"上次跑成功了吗"由命令日志回答。
- 业务 App 被移除后，`core` 无需清理任何历史状态记录。

### 5.2 `core` 逻辑数据集

#### 5.2.1 股票基础信息

最小字段：

- `thscode`
- 六位股票代码
- 股票名称
- 交易所
- 资产类型
- 是否当前有效
- 数据更新时间

股票代码在所有模块中必须使用同一标准格式，禁止同一股票同时以带交易所和不带交易所的不同主键保存。

#### 5.2.2 交易日判定

交易日**不落库、也不来自上游**，由 `core/services/calendar.py` 基于 `chinese-calendar` 在本地推导：

- 时区固定 `Asia/Shanghai`；周末（含调休上班的周末）一律不是交易日。
- 工作日的法定节假日由 `chinese-calendar` 判定。该包按年内置节假日表；未覆盖年份退化为「工作日即交易日」，并对每个未覆盖年份记一次 WARNING。
- 对上层暴露的公共 API：`is_trading_day(day)`、`latest_trading_day_on_or_before(day)`、`previous_trading_day(day)`、`recent_trading_days(end_date, *, count)`、`trading_days_between(start, end)`、`latest_trading_date()`、`latest_eligible_trading_day()`。
- 交易日判断必须来自该模块，不允许四个业务 App 各自维护周末/节假日逻辑。

每年国务院放假安排公布后升级 `chinese-calendar` 并重启服务，是例行运维动作（见 `docs/ops/deployment.md`）。该包的发布节奏是**每年只发一个覆盖次年的版本，时间固定在 10 月底至 11 月中**，紧随国务院公布次年安排之后。

覆盖边界必须可观测，不能靠人去记。该包按年校验（`chinese_calendar.utils._validate_date`），所以覆盖是年粒度的：某一年要么整年可用，要么整年不可用。`core/services/calendar.py` 另外暴露：

- `covered_year_range()`：返回假期表覆盖的闭区间年份 `(first_year, last_year)`；
- `calendar_coverage()`：把覆盖情况转成报告（`covered_from`、`covered_through`、`covered_through_date`、`current_year`、`current_year_covered`、`next_year_covered`），随 `GET /api/core/health/` 的 `data.trading_calendar` 返回，用于在跨年退化发生前预警；
- `core/tests/test_calendar_services.py::HolidayTableCoverageTests`：依赖覆盖守卫。当前年份一旦不被覆盖就变红，它要求的动作是升级 `requirements.txt` 里的依赖，而不是改断言。

跨年退化的方向偏宽松（法定假日被当成交易日提交给只服务交易日的上游），且已经没有第二层兜底，所以提前预警比事后从被拒绝的请求里发现更重要。

#### 5.2.3 当前开盘啦行业和股票映射

行业—股票关系使用开盘啦的行业 → 行业股票列表链路采集，并作为当前快照整批写入。表只包含以下三个业务字段：

- `industry_code`：行业代码；
- `industry_name`：行业名称；
- `stock_codes`：JSON 股票代码数组。

每条行业记录只保存行业代码、行业名称和股票代码列表，不额外持久化层级或历史有效期。相同股票可出现在多个行业的 `stock_codes` 中，派生分析按每个行业分别统计。

**北交所归属的增量补齐（唯一的同花顺行业来源）**：开盘啦 881xxx 行业族对北京证券交易所仍使用旧代码（43/83/87），无法表达本项目 `core_stock` 中的 920xxx，因此只靠开盘啦会让北交所股票全部无法归入任何行业。同步流程在开盘啦采集完成之后、写入之前，用同花顺行业目录与成分股接口补齐这一部分：

- **开盘啦仍是权威**。补齐是纯增量：只往开盘啦已有的行业里追加它没有的成员，绝不删除、绝不替换开盘啦的成员或行业。
- **只补同花顺也有对应行业的那些代码**（881xxx 与开盘啦 881xxx 同族同名的部分），以及本地 `core_stock` 中确实存在的股票。
- **只用于北交所归属**，不承担其他任何行业—股票关系的正式来源职责；同花顺 884xxx 等其它分类不参与。
- 由 `.env` 的 `HITHINK_INDUSTRY_BACKFILL_ENABLED` 控制，默认开启；关闭时不访问同花顺。补齐失败会使整次同步失败，不会静默退回"北交所无归属"的状态。
- 补齐数量记录在同步结果中（`backfilled_stock_count`）。

#### 5.2.4 公共个股日行情

最小字段：

- 业务日期
- 股票标准代码/`thscode`
- 前收盘价
- 开盘价
- 最高价
- 最低价
- 收盘价
- 涨跌幅
- 成交量
- 成交额
- 是否有有效交易
- 来源批次标识（`source_batch_id`）

约束：

- 使用固定 `adjust=forward` 的前复权日 K 作为公共原始事实。
- 唯一键为“股票 + 业务日期”。同一天的写入是整批 upsert 覆盖 `trade_date` 等于该日的全部行，所以同一天不会同时留着两套新旧不同的行——这是"没有版本号"仍然安全的前提。
- 首次初始化只处理以执行日为终点的滚动最近一年内交易日。`init_stock_daily_prices --years 1` 可重复执行：每次都重新抓取整年窗口并与本地逐条比对，只更新与上游不一致的行、补齐缺失的行；与上游逐条一致时不改写任何行。
- 日常 `refresh_intraday_quotes` 只处理**当天**（业务日期恒为服务器 Asia/Shanghai 的今天，**没有 `--date`**）：盘中每 30 分钟、盘后 15:35 各刷一轮，每次在一个事务里覆盖该日记录，重复执行通过“股票 + 交易日期”唯一键幂等覆盖。要补历史某一天走上面那条 `init_stock_daily_prices`。
- 单个股票在成功上游请求中没有该日期日线时，保存 `has_valid_trade=false` 的非交易记录；若某个待写入交易日所有股票均无有效成交记录，则视为上游数据异常，整批不写入。
- 涨跌幅优先使用经验证的同花顺字段；若需本地计算，统一由 `core` 按前一有效交易日收盘价计算。
- 业务 App 不复制整张日行情表。

#### 5.2.5 完整性与写入语义（没有版本号）

公共数据集、业务结果都不记录版本号、运行状态或完整性字段。**“这一天的行在不在库里”就是唯一需要问的问题。**

完整性在**写入前**校验，而不是写入后登记：

- 同步命令先取全量并与本地比对，确认覆盖度合格才在**一个事务里**整批提交；提交即可读，没有“写入完成但尚未发布”的中间态。
- 只有 `expected == actual && missing == 0` 才允许提交；不满足则整批不写，命令非零退出，并在日志里留下 `data_command_failed`。
- 文件缓存不参与发布。它的身份来自它所缓存的那批数据（三个盘后模块取结果行 `published_at`，采集快照取当天采集槽），数据一换身份就变，因此不存在“缓存指向尚未提交的数据”。
- 运行账目（起止时间、预期/实际行数、缺失行数、失败原因）是**命令日志**的字段，不落库。这些数字只在日志里，运维据此判断“上次跑成功了吗”（见 §8.3 AC-CORE-008）。

派生结果同理：按 `business_date` 唯一，读路径只问“这一天有没有结果行”。**没有版本号就没有“输入变了产物自动失效”这回事**——重算公共数据后要跟着重跑那一天的 `build_*`。这是刻意的取舍：版本过滤能省掉“忘记重跑”这一类人为疏漏，但代价是每个读请求都要额外查核心库、每条增量路径都要维护版本改挂，而且漏跑时页面会变成难解释的空页面，而不是更正确的数字。

### 5.4 文件缓存

- 缓存根目录、TTL、开关和单项大小限制必须来自根目录 `.env`。
- 缓存按 `module_id / endpoint / 参数摘要 / 缓存身份` 命名。**缓存身份就是它所缓存的那批数据本身**：派生结果取结果行的 `created_at`，开盘啦取当天最新采集槽（`kaipanla:<date>T<HH:MM>`）。数据一换身份就变，旧键自然不再命中，因此不需要"发布成功后主动失效旧缓存"这一步。
- 缓存内容包含生成时间、业务日期、缓存身份和过期时间；信封（`generated_at`、`data_updated_at`）每次从库里重建，不随载荷一起缓存。
- 业务 App 只能清理或失效自己的缓存命名空间；`core` 可管理公共缓存工具，但不能解释业务正文。
- 缓存损坏、JSON 无法解析或缓存身份不匹配时视为未命中，不能导致 500。
- 自动备份、长期归档和定期清理由本期排除；运行时可以安全覆盖同一个缓存键。

#### 5.5.2 板块资金流 API

`kaipanla` 使用以下路径形状：

- `GET /api/<module>/sectors/?date=YYYY-MM-DD`
- `GET /api/<module>/sectors/intraday/?date=YYYY-MM-DD&inflow_top=5&outflow_top=5`
- `GET /api/<module>/sectors/intraday/history/?date=YYYY-MM-DD&days=5&inflow_top=5&outflow_top=5`
- `GET /api/<module>/dates/`

参数约束：

- `date` 为可选 ISO 日期；省略时使用模块最新可用日期。
- 显式提供无效日期格式时返回 `400`，不得静默回退。
- `days` 只允许 `1`、`5`、`10`、`20`；其他值返回 `400`。
- `inflow_top` 和 `outflow_top` 范围为 `0..30`。

`/api/<module>/sectors/intraday/` 的正文语义：

- `time_points` **始终是完整交易时段的五分钟轴**（09:30–11:30 与 13:00–15:00 各 25 个槽，共 50 个），与请求时刻无关 —— 上午 10:00、午休或收盘后打开页面看到的是同一条刻度，否则"上午只剩半条轴、下午的刻度凭空出现"。当天尚未走完由每条曲线自己表达：`series[].data` 只覆盖到最后一个已采集的时点，其后的槽不带值，前端按缺失渲染而不是补零或复制末值。
- 后端只提供五分钟原始轴，刻度密度（当前为每半小时一个）与显示文本是前端的渲染决策，不回写契约。
- 一条快照都没有的交易日返回空 `time_points` 与空 `series`（走空态），**不返回一张只有刻度的空图**。
- 该正文是（业务日期 + 该日已落库快照）的纯函数：查询时刻不进 payload，因此同一批快照的缓存结果在盘中不会被"时钟"改写。

### 5.6 统一响应外壳

所有 JSON API 使用以下语义一致的响应外壳；各 App 的 `data` 结构独立：

```json
{
  "status": "ok",
  "business_date": "2026-09-08",
  "generated_at": "2026-09-08T15:05:00+08:00",
  "data_updated_at": "2026-09-08T15:03:12.337914+08:00",
  "stale": false,
  "source": "cache",
  "preparation": {
    "state": "ready",
    "retry_after_seconds": null
  },
  "warnings": [],
  "error": null,
  "data": {}
}
```

字段约束：

- `status`：`ok`、`partial`、`preparing`、`error`。
- `business_date`：响应正文对应的实际交易日，不得用请求日冒充。
- `generated_at`：服务端拼出这个响应体的时刻。**它每次请求都会前进，包括命中文件缓存的那次**，因此不能拿来当"数据有多新"。
- `data_updated_at`：**这份数据写进数据库的时刻**（无数据时为 `null`，不得用 `generated_at` 或当前时间顶替）。页面工具栏的「更新于 HH:MM」只读它。三个盘后模块取所服务结果行的 `created_at`；板块资金流取当天最新采集槽那批行的 `created_at`（见 §6.1）。命中文件缓存时同样要带上 —— 缓存只存载荷，信封每次重建。
- `stale`：是否退回了一个更早的业务日期。它只在**默认入口**（未显式带 `date`）出现：解析到的那一天算不出来时退回最近可用的结果并置 `true`；显式点名某天时不退回（只能是 404）。
- `source`：`cache`、`database`、`computed` 中之一。
- `preparation.state`：`ready`、`preparing`、`syncing`、`insufficient_history`、`unavailable`。（`repairing` 随 Web 侧远程修复一起删除，见 §5.8。）
- `warnings`：非致命问题，例如部分榜单失败、股票缺少行业映射、返回旧数据。
- `error`：失败时包含稳定错误码和面向用户的安全消息。

| HTTP 状态 | 场景 |
|---|---|

### 5.8 Web API 读取顺序

每次业务查询按以下顺序执行：

1. 读取与请求参数及缓存身份匹配的文件缓存。
2. 缓存未命中时读取本 App 的 SQLite 派生结果或快照。
3. 如果数据库已有结果，构建响应并回写文件缓存。
4. 数据缺失时，评估是否满足本地生成条件。
5. 符合条件时用已经落库的公共数据生成该日期的派生结果，持久化数据库后再写缓存并返回。
6. 本地生成不可用（公共数据缺失、历史不足等）时：已有旧数据则返回旧数据并标识 `stale`；无旧数据时返回 `404 DATA_NOT_AVAILABLE`（显式指定日期）或 `202 DATA_PREPARING`（未指定日期）。

**Web 请求永不访问上游。** 这是本节的硬约束：读取链路里没有抓取步骤，任何"请求内回源"的设计都视为违规。抓取只发生在 crontab 拉起的 `sync_*` / `fetch_*` 命令里。

**(a) 本地生成派生结果 —— 受保护的本地计算**

- 只读取本 App 已落库的公共数据（`stock_daily_prices`、`industry_snapshot` 等），**绝不发起任何上游请求**。
- 因此没有行数门槛：一次全市场单日生成天然涉及数千行（实测全市场约 5,500 只股票），行数上限对它不适用，也不应据此拒绝生成。
- 用 `dataset_lock(module, dataset)` 保护：同一数据集只有一个请求在生成，其余请求立刻返回旧数据或 `202`，不排队。
- 未指定日期时，三个盘后模块以最新有公共日行情的日期为读取目标（而不是最新派生结果日期），保证首屏跟随实际已有数据；板块资金流是独立采集链路，锚点见 §6.1。
- 显式指定日期且该日期无公共日行情时，不生成、不返回其他日期冒充结果，按第 6 条返回错误。

**(b) 板块资金流：不生成、不回源**

板块资金流的分时快照无法由公共日行情派生（它是从上游按 5 分钟槽采来的原始事实），因此它不走 (a)：

- 读路径只回答两种"还没有当天数据"的话：收盘前 `202 DATA_PREPARING`（当天仍在采集窗口内，客户端稍后重试），收盘后返回最近一次可用快照并标 `stale`。
- 显式 `?date=` 而该日无快照 → `404 DATA_NOT_AVAILABLE`，绝不返回其他业务日期。
- 该模块的缓存身份是当天最新采集槽（`kaipanla:<date>T<HH:MM>`），新槽一到键就变，因此缓存永不会比它对应的行活得更久。
- 信封的 `data_updated_at` 取**最新采集槽那批行**的 `created_at`（一槽一个事务，正常同值）：页面上的资金流来自最新槽，时刻就必须来自它，而不是这一天里最早或最晚写入的行。
- 采集不全（缺页、任一页失败、行数为 0）时命令**一行都不写**，只在 `backend/logs/kaipanla.log` 留下 `kaipanla_collection_incomplete`（上游声称行数 / 实际行数 / 缺失行数 / 页进度 / 失败页偏移 / 失败种类）。

建议的命令契约：

```bash

python manage.py sync_kaipanla_industry_snapshot
# 全量校正：重跑最近一年逐只历史行情，补齐历史缺口与复牌股昨收。
# 可安全重跑：抓取整年窗口后与本地逐条比对，只更新与上游不一致的行、
# 补齐缺失的行，无差异时不改写任何行。crontab 里每周日跑一次。
python manage.py init_stock_daily_prices --years 1
# 盘中链路（建议每 30 分钟）+ 盘后定稿（15:35 带 --latest）：
# 用全市场实时快照刷新「今天」的公共日行情，让页面在收盘前就能跟随当天。
# 业务日期恒为 Asia/Shanghai 的今天，刻意没有 --date。
python manage.py refresh_intraday_quotes [--latest]

# kaipanla
python manage.py fetch_kaipanla_sector_fund_flow [--latest] [--dry-run]

python manage.py build_sector_momentum [--date YYYY-MM-DD]

# hundred_day
python manage.py build_hundred_day [--date YYYY-MM-DD]
```

所有采集/计算命令共同要求：

- `init_stock_daily_prices --years 1` 是**全量校正**命令：抓取整年窗口并与本地逐条比对，只写入有差异的行，无差异时不改写任何行。它由 crontab 每周日执行一次，也可手动重跑以按上游校正与补齐；它是唯一能补历史某一天、也是唯一能补上复牌股昨收缺口的手段。它不得由 Web API 触发，也不得改为每日任务。
- `refresh_intraday_quotes` 是**唯一的日常日行情写入者**（盘中每 30 分钟 + 盘后 15:35 带 `--latest` 定稿）。业务日期恒为 `Asia/Shanghai` 的今天，**没有 `--date`** —— 快照端点没有日期参数、永远回答"此刻"，留日期参数只会制造"把今天的行情写到别的日期上"这个入口。它不抓取历史、不生成任何派生结果。两道闸门：非交易日一律跳过（即使带 `--latest`），交易日时段外跳过（带 `--latest` 放行）。当快照覆盖的股票数低于 `INTRADAY_QUOTE_MIN_COVERAGE_RATIO` × 当前活跃股票数时整体失败，不写入。
- 三个 `build_*` 的 `--date` 是**可选**的：省略时取「库里最新有公共日行情的那天」（`latest_complete_stock_price_date()`），与页面默认入口是同一个锚点。显式传入时该日必须有已落库的公共日行情，否则失败而非产出部分结果。
- 其他公共数据和盘后分析命令支持 `--date` 或明确日期范围；盘中资金流命令保留无参数交易时段模式和 `--latest` 模式。
- 盘中资金流命令的落库时刻由运行时刻按标准 5 分钟槽向前回退（盘中、午休、盘后与非交易日的具体落点见 §3.1.2）；交易日判定、历史交易日与"最近一个交易日收盘"全部用 `chinese-calendar`（周末与法定节假日都不是交易日）。系统没有上游日历，因此也不存在「日历为空则命令失败」这一分支。
- 盘中资金流命令的**页数由上游 `Count` 决定**（`ceil(Count / page_size)`），不是写死的一页；`page_size` 的上界是上游单页硬上限 80 行（`client.MAX_PAGE_SIZE`）。当前 881xxx 行业族恒为 104 行 ⇒ 2 页，必须能被一次采集完整取回并写入；页数超过 `KAIPANLA_FLOW_MAX_PAGES` 即按"未完成"处理（一行不写，退出码非零）。
- 盘中资金流命令与另外三个 `build_*` 一样**不写任何运行表**：它对本模块库只做一次事务性的 `INSERT ... ON CONFLICT DO UPDATE`（写行即发布），采集不全时一行都不写。失败账目（上游声称行数 / 实际行数 / 缺失行数 / 页进度 / 失败页偏移 / 失败种类）是命令日志的字段，事件名 `kaipanla_collection_incomplete`。
- 开盘啦资金流 URL 不提供历史快照时间参数。因此资金流命令不得声明或实现 `--snapshot-time`、`--date` 等显式历史时间参数。开盘啦的 `KPL_DEVICE_ID`、`KPL_USER_ID`、`KPL_TOKEN` 均为可选请求字段：空值必须省略，非空值才附带。
- 所有命令支持 `--dry-run`，且不得写数据库或缓存。
- 参数无效、上游失败、完整性校验失败或数据库写入失败时返回非零退出码。
- 日志包含模块、数据集、业务日期、批次 ID 和耗时，不输出密钥、Token、Device ID 或完整敏感上游响应。
- 同一模块同一数据集的并发执行必须被互斥锁阻止。
- 写入是**整批事务**的：要么整天/整批可见，要么一行不可见。因此不存在"读到一个写了一半的结果"，也没有"写入成功后还要再发布一次"这一步——提交即可读；失败时库里什么都没变，最近一次成功的数据自然完好。

### 5.10 `.env` 配置契约

所有开发、测试和生产配置从项目根目录 `.env` 加载，并在 `.env.example` 使用安全占位符说明。至少包括：

- Django `SECRET_KEY`、`DEBUG`、`ALLOWED_HOSTS`。
- Session、CSRF、CORS/可信来源和安全 Cookie 配置。
- 五个 SQLite 数据库路径。
- 文件缓存根目录、TTL、开关和大小限制。
- 时区，固定默认 `Asia/Shanghai`。
- 模块启用开关。
- 同花顺 REST API 的 `HITHINK_FINANCE_API_KEY`、超时、低并发、请求间隔和有限重试参数。
- 开盘啦的两条独立 URL：板块资金流使用 `KAIPANLA_API_URL`（实时 `apphwshhq`），行业—股票快照使用 `KAIPANLA_INDUSTRY_API_URL`（历史 `apphis`）；两者各自的请求参数、超时、重试以及可选的 `KPL_DEVICE_ID`、`KPL_USER_ID`、`KPL_TOKEN` 均从 `.env` 读取；空凭据配置不发送对应字段。
- 行业—股票快照的 `Date` 参数必须落在交易日上：历史端点对周末、节假日等无交易的日期返回 `errcode 1020 参数出错`，因此默认值由 `core.services.calendar.latest_trading_date()` 解析为最近一个交易日，而不是本地日期；`KAIPANLA_INDUSTRY_DATE` 留空即启用该默认值，显式赋值用于回补指定交易日。写入的 `business_date` 记录实际请求的交易日。
- 本地生成派生结果不消耗上游配额，因此没有预算类配置。
- 北交所行业归属增量补齐的开关 `HITHINK_INDUSTRY_BACKFILL_ENABLED`（默认 `1`；设 `0` 时整段跳过且不访问同花顺），见 §5.2.3。
- 开盘啦 `RealRankingInfo` 的族群选择：`KAIPANLA_INDUSTRY_PARENT_ZS_TYPE` 与 `KAIPANLA_FLOW_ZS_TYPE` 必须同族（当前为 `4`，即 881xxx 行业），配套 `Type=1`；换族会与既有快照混族，需清理并重算。
- 股票主数据同步的下界保护 `STOCK_MASTER_MIN_COVERAGE_RATIO`（默认 `0.9`）：上游返回的股票数低于「当前活跃股票数 × 该比例」时整体失败，避免把未出现的股票静默停用。
- 陈旧数据集锁的回收阈值 `LOCK_STALE_SECONDS`（默认 `21600`，即 6 小时）：持有者已死或锁文件超过该时长即回收；设 `0` 时只允许"同主机且持有者已死"这一种回收条件。
- 盘中行情刷新（`refresh_intraday_quotes`）的分页大小 `INTRADAY_QUOTE_PAGE_SIZE`（默认 `1000`，有效范围 1–10000）与覆盖率门槛 `INTRADAY_QUOTE_MIN_COVERAGE_RATIO`（默认 `0.95`，有效范围 `(0, 1]`）：快照覆盖的股票数低于「当前活跃股票数 × 该比例」时整体失败，避免用一份不完整的实时快照覆盖当天行情。

代码、测试、fixture 和命令中不得硬编码凭据、生产 URL、密钥、超时或功能开关。

## 6. 异常及边界场景

### 6.1 日期和交易时间

- 所有交易时间判断使用 `Asia/Shanghai`，不使用服务器本地默认时区推断。
- 周末和休市日不生成伪造的当日盘后分析。
- 未指定日期时，各模块返回自己的最新可用业务日期。三个派生模块（个股异动、板块动量、百日新高）的**读写日期锚点是「最新有公共日行情的日期」**：它通常等于最近一个已收盘交易日，但当天已由盘中刷新写入时即为当天（见 §5.9 的 `refresh_intraday_quotes`）。"当日是否已收盘"仍是盘后管线的判定口径（`latest_eligible_trading_day`），两者不要混用。
- **板块资金流的锚点是它自己的最新已存快照日，与公共日行情日期无关**：该快照只能从上游采集、无法由公共数据派生，盘中每 5 分钟落库一次，因此通常比 `stock_daily_prices` 更早到达当天。锚定公共日行情会让页面上演"明明手里有当天快照却显示上一个交易日"。
- 板块资金流另有一个时钟口径：它的"最新交易日"指该有快照的最新交易日 —— 交易日 09:30 起为当天，开盘前与非交易日为最近一个已收盘交易日。最新快照已达该日时直接返回；落后时按时间分岔：当天仍在采集窗口内（收盘前）回 `202`，否则按旧数据返回并置 `stale=true`。**读路径不会为此发起任何抓取**（§5.8(b)）。
- 显式指定日期时，不得静默替换为另一个日期：该日期没有数据就是 `404`，不能返回其他业务日期冒充结果。默认入口（未指定日期）才允许退回最近可用结果并置 `stale=true`。
- "交易日 15:00 前不生成当天盘后结果"这条只约束盘后定稿（`refresh_intraday_quotes --latest`，15:35）与三个 `build_*` 命令，以及显式指定当天的请求：未指定日期的默认入口在当天已有公共行情（盘中刷新写入）时会跟随当天，否则回落到上一个交易日。当天还没有任何公共行情时，查看当天需显式带日期，此时返回 `202 DATA_PREPARING`。
- 交易日 15:00 后只有在公共日行情完整性校验通过时才写入当天盘后结果。
- 15:00 快照缺失时，多日板块资金流不能把其他时刻伪装为 15:00；可以按原有规则沿用前一交易日累计值，但必须在响应中警告缺失日期。

### 6.2 缓存异常

- 缓存文件不存在：回退 SQLite。
- 缓存过期：可先保留为旧数据候选，再查询 SQLite 当前数据。
- 缓存内容损坏：记录错误、忽略文件并回退 SQLite。
- 缓存身份与库里那批数据对不上（数据被重写、采集槽前进）：按未命中处理，用数据库数据重建缓存。
- 缓存目录不可写：仍可返回数据库数据，不得使业务查询整体失败。

### 6.3 SQLite 异常和并发

- 数据库被短暂锁定：在严格短重试预算内重试；超出预算后返回旧缓存或明确错误。
- 命令写入必须使用事务：一旦失败，库里不该留下"写了一半"的结果。
- Web 请求不得持有跨远程请求的数据库写事务。
- 一个业务数据库损坏或不可用时，其他业务数据库和 `core` 仍能工作。
- 不允许通过跨数据库 JOIN 实现业务查询。

### 6.4 上游数据源异常

- 网络超时、连接失败、非预期状态码和响应结构变化必须转换为稳定内部错误。
- 上游限流不得触发无边界重试。
- 开盘啦任一必要分页最终失败时，这一轮一行都不写。
- 同花顺行情不完整时不得写入该批数据。
- 同花顺权限不足、额度耗尽或开盘啦行业无法识别时，保留库里已有数据，并在日志中记录可行动错误。
- 对用户返回的错误不得包含 API Key、Token、Device ID、请求签名或敏感响应正文。

### 6.5 公共数据缺失

- 股票缺少名称或交易所：不应阻止原始行情保存，但相关业务结果需警告或排除。
- 股票缺少行业映射：不得随机分配；板块动量和行业聚合给出未映射数量。
- 当日停牌或无有效收盘价：不参与当日涨跌和新高新低判断。
- 新上市股票在上市前的历史位置按现有算法填 `0`；只要全市场日期窗口已有 99 个历史位置，该股票可参与判断。
- 目标日期不是交易日：不得把普通工作日当成交易日推断，也不得伪造数据；应返回数据未准备或明确的日期校验错误（交易日由 `core` 本地推导，不存在「日历缺失」这一状态）。
- 日行情存在重复股票日期：完整性校验失败，整批不写入。

### 6.6 模块启停和删除

- 模块被禁用时，前端不显示入口，根 URL 不挂载其 API。
- 直接访问被禁用模块 API 时返回 `404` 或稳定的 `MODULE_DISABLED`，不得导入模块后再运行时判断。
- 删除某业务 App 后，设置、URL、模块注册表和前端注册中移除对应静态条目即可。
- 其余 App 的迁移、测试和启动不得导入已删除 App。
- `core` 不保存任何按模块归属的状态记录。

### 6.7 公共数据变化后

- 公共日行情或行业映射被重写后，基于旧口径算出的业务派生结果**不会自动失效**：结果表按 `business_date` 唯一，读路径找到结果行就返回（没有版本号可比，见 §5.2.5）。
- 因此"重算公共数据"之后必须跟着重跑受影响日期的 `build_*`。这不是可选项，而是流程的一部分：漏跑的表现不是报错，而是页面继续展示旧口径的数字。
- 派生结果落库走同一个 `business_date` 的唯一键，重跑即覆盖，不会堆出第二行；重算失败时库里仍是上一次的结果，不会被半成品覆盖。
- 业务 App 不通过调用另一个业务 App 判断"是否需要更新"。
- 三个派生模块彼此之间没有依赖：任一模块没有重跑，只影响它自己的页面。

### 6.8 前端边界

- 单个模块请求失败只影响当前模块内容区，不清空全局导航和其他模块状态。
- 快速切换 Tab 或日期时，过期请求响应不得覆盖新选择的页面状态。
- 复制股票代码失败时给出可见提示，不伪报成功。
- 空列表、部分列表和请求失败必须使用不同状态展示。
- 图表缺失个别点时不得把缺失值默认画为 0，除非业务契约明确该值就是 0。
- 页面必须在常用桌面宽度和窄屏下保持可操作，不要求原生移动 App 体验。
- **页面外壳（日期控件、统计窗口按钮、刷新入口「更新于 HH:MM」）在任何数据状态下都必须保持挂载**：数据状态只替换内容区（表格 / 看板 / 图表 / 排行榜），不得整页替换。否则切换日期时控件被卸载重建，用户失去正在操作的弹层、焦点与滚动位置。四个页面共用同一套状态判定（`shared/dataStateName.js`）。
- **页面不自己发请求**：数据只在三种时机取一次 —— 挂载、改日期 / 改统计窗口、以及用户点击工具栏那颗「更新于 HH:MM」（它是刷新当前页面数据的唯一入口，`<button>`、鼠标悬停为手型、点击后按当前条件重取一次）。**没有定时轮询，也没有交易时段判定**（前端不判断"现在是否盘中"）。刷新由用户主动触发，失败必须显示错误态，不得把旧数据留在页面上假装一切正常。
- **「更新于 HH:MM」显示的是数据自己的时刻**：它只读 `data_updated_at`（那份数据写进数据库的时刻），**不得**用浏览器时钟或 `generated_at` 顶替 —— 结果行落库后一直躺在库里，页面随时打开，两者可以差几个小时。信封没有这个时刻时（首次加载中、请求失败、以及该日期确实没有数据的空态）胶囊整个不渲染，不得显示「更新于 --:--」之类的占位。
- 图表数据必须以稳定引用传给图表组件：选中集合不变时不得重建 series 数组，否则 ECharts 会在每次无关重渲染时全量重绘并重播动画。
- `DATA_PREPARING`（202）与 `SYNC_IN_PROGRESS`（409）都是"稍后会有"，必须渲染为「数据准备中」而不是加载失败；只有真正的传输失败或 5xx 才显示错误态。

## 7. 安全和兼容性要求

### 7.1 认证和授权

- 除最小健康检查和登录所需端点外，所有业务 API 必须要求已登录。
- 使用 Django Session 和 CSRF 防护；修改状态的请求必须通过 CSRF 校验。
- 不提供注册 API。
- Django 管理后台只允许 `is_staff` 用户访问。
- 普通登录用户可访问全部已启用业务模块，不实现模块级授权。
- 登录失败信息不得用于枚举账号。

### 7.2 生产安全配置

生产环境必须：

- `DEBUG=False`。
- 从 `.env` 加载强随机 `SECRET_KEY`。
- 配置准确的 `ALLOWED_HOSTS` 和可信 CSRF 来源。
- 通过 HTTPS 提供服务。
- 启用 `Secure`、`HttpOnly` 和合理 `SameSite` 的 Session Cookie。
- 限制跨域来源为实际前端地址；同域部署时不开放不必要 CORS。
- 不在日志、缓存、数据库错误字段或前端响应中保存凭据。
- 对外部响应做类型和字段校验，不信任上游数据结构。

### 7.3 输入与输出安全

- 日期、整数范围、枚举值和排序参数必须显式校验。
- 数据库访问优先使用 Django ORM 或参数化查询。
- 股票名称、行业名称和上游错误作为纯文本输出，前端不得使用未净化的 HTML 注入。
- 不接受用户提供的服务器文件路径。
- 不提供文件上传接口，从而移除任意文件名和落盘路径风险。
- 管理命令日志对 Token、API Key 和 Device ID 进行遮蔽。

### 7.4 上游访问安全和合规

- 开盘啦访问只限板块资金流用途。
- 个股公共数据只通过同花顺 REST API；行业—股票公共数据只通过开盘啦行业列表和成分股接口；唯一的补充来源是同花顺行业目录与成分股接口，且仅用于北交所归属的增量补齐（见 §5.2.3），不得用于其他行业—股票关系。
- 所有上游 URL、参数、凭据、超时和开关从 `.env` 读取。
- 不绕过限流、访问控制或服务端能力约束。
- 不把抓包数据、上游完整响应样本或真实凭据提交到仓库。

### 7.5 兼容性

- 保留用户可见的核心筛选、排行、日期选择、图表、展开和复制功能。
- 统一 UI 可以改变布局和视觉细节，但不能删除核心操作。
- 内部 API 使用 `/api/<app>/` 路径，不作为向后兼容契约。
- 个股数据源为同花顺 REST，盘后时间资格为交易日 15:00。
- 行业以开盘啦行业为准，同一股票在多个行业中分别计入。
- 公共响应外壳统一，但模块业务正文可不同；前端不得假设所有模块共享同一数据结构。
- 同花顺 REST API 或上游字段变化时，应通过适配层隔离，业务服务不得直接散落 REST 字段名。

### 7.6 配置兼容和可部署性

- 本地和阿里云使用相同代码，通过 `.env` 区分配置。
- 路径不能依赖某个开发者的绝对目录。
- SQLite、缓存和日志目录必须可配置并在启动时校验可写性。
- Django 时区固定为 `Asia/Shanghai`，避免服务器 UTC 配置改变业务日期。
- 依赖版本必须记录，保证本地和生产可重复安装。

## 8. 可测试的验收标准

以下验收标准均需能够通过自动测试或明确的人工检查重复验证。

### 8.1 产品与用户流程

- **AC-UI-001**：给定未登录用户访问任意业务页面，系统不请求业务数据并跳转登录页。
- **AC-UI-002**：给定有效账号登录成功，首次进入显示“板块资金流 → 开盘啦”。
- **AC-UI-003**：四个一级 Tab 名称分别为“板块资金流”“大涨跌幅与大成交量个股”“板块动量”“百日新高新低占比”；四个 Tab 只显示文字标签，不显示左侧图标。
- **AC-UI-004**：板块资金流一级 Tab 直接展示开盘啦资金流内容，不提供数据源切换控件。
- **AC-UI-005**：禁用一个模块后，其导航入口和 URL 挂载均消失，其他模块可正常使用。
- **AC-UI-006**：单个模块 API 返回错误时，其他 Tab 的导航和已加载数据不受影响。
- **AC-UI-007**：所有模块都能区分展示加载、空数据、过期、准备中、部分成功和失败状态。
- **AC-UI-008**：全站上涨数据使用统一红色语义，下跌数据使用统一绿色语义，错误状态不与涨跌颜色混淆。
- **AC-UI-009**：四个页面**不设定时器**：数据只在挂载、改日期 / 改统计窗口、以及用户点击工具栏「更新于 HH:MM」时各取一次（页面开着不动不会产生任何请求）。该胶囊必须是 `<button>`（可聚焦、可回车触发、鼠标悬停为手型），点击后按当前条件重取同一个 URL；刷新失败按与首次加载相同的规则渲染（调用方列出的 4xx 走空态 / 准备中，其余走错误态），不得静默保留旧数据。
- **AC-UI-010**：胶囊上的时刻等于响应信封的 `data_updated_at`，即**服务这份数据的那一行写进数据库的时刻**，与请求发出的时刻（浏览器时钟）和 `generated_at` 都无关。命中文件缓存时仍须给出同一个时刻（缓存只存载荷，信封每次重建）；信封没有这个时刻时不渲染胶囊。

### 8.2 模块独立性

- **AC-MOD-001**：四个业务 App 之间不存在 Python import 依赖。
- **AC-MOD-002**：四个业务 App 不查询其他业务 App 的数据库或模型。
- **AC-MOD-003**：每个业务 App 有自己的 SQLite、URL、视图、服务、管理命令、迁移和测试。
- **AC-MOD-004**：逐一执行“只保留 `core` + 一个业务 App”的配置测试，`python manage.py check` 成功。
- **AC-MOD-005**：在上述四种单模块配置下，对应 App 的迁移、管理命令 dry-run、测试和 API 路由均可独立工作。
- **AC-MOD-006**：删除任意业务模块的状态历史不会导致 `core` 管理后台导入失败。
- **AC-MOD-007**：数据库中不存在指向另一个业务 SQLite 的外键或跨数据库 JOIN。

### 8.3 公共数据

- **AC-CORE-001**：首次初始化只请求和保存以执行日为终点的滚动最近一年范围内公共日行情。
- **AC-CORE-002**：同一股票和交易日期最多存在一条公共日行情。
- **AC-CORE-003**：三个盘后业务 App 不保存公共日行情的完整复制表。
- **AC-CORE-004**：交易日判断由 `core` 统一提供，业务 App 不包含独立节假日算法；`chinese-calendar` 的覆盖年份范围通过 `GET /api/core/health/` 的 `data.trading_calendar` 可见，并有测试守卫当前年份必须被覆盖。
- **AC-CORE-005**：行业—股票快照只表示当前开盘啦关系，不包含历史有效期，且仅含 `industry_code`、`industry_name` 和 `stock_codes`（JSON 数组）三个业务字段。
- **AC-CORE-006**：同步以开盘啦行业列表与行业股票列表接口的实际响应为准；同一股票可出现在多个行业的 `stock_codes` 中；无成分股的行业必须以空 `stock_codes` 持久化，不得阻断整批写入。
- **AC-CORE-007**：公共数据写入中途失败时，事务回滚，库里保持上一次成功的数据，不留下半份结果。
- **AC-CORE-008**：公共数据的完整性在**写入前**校验：预期数、实际数、缺失数不满足 `expected == actual && missing == 0` 时整批不写入；这些数字作为命令日志事件的字段留档（`data_command_failed` 带 `error`，`data_command_finished` 带耗时），**不落库**（见 §5.2.5）。

### 8.4 数据源约束

- **AC-SRC-000**：同花顺市场数据客户端只访问已批准的 REST 端点：`/api/meta/tickers/list`、`/api/a-share/prices/historical`、`/api/a-share/prices/snapshot`，以及北交所行业补齐用的 `/api/a-share-index/catalog/ths-index-list` 与 `/api/a-share-index/constituents/ths-stock-list`；请求使用 `X-api-key`，密钥仅从根目录 `.env` 的 `HITHINK_FINANCE_API_KEY` 读取。交易日历不由上游提供（见 §5.2.2）。
- **AC-SRC-000A**：日线同步先分页取得 A 股股票表，再逐股票请求最近一年 `interval=1d`、`adjust=forward` 历史数据；客户端具有可配置低并发、请求间隔和有限退避。
- **AC-SRC-000B**：行业—股票同步以开盘啦行业 → 行业股票列表链路为权威来源；端点、参数、分页、超时、重试与可选 `KPL_*` 凭据均从 `.env` 读取。三项凭据任何一项为空时，请求不得发送该字段。
- **AC-SRC-000C**：北交所行业归属由同花顺行业目录与成分股接口增量补齐（`HITHINK_INDUSTRY_BACKFILL_ENABLED`，默认开启）：只往开盘啦已有的行业追加它缺少的成员，不删除、不替换开盘啦的任何成员或行业；只补同花顺也存在对应行业、且存在于本地 `core_stock` 的股票；关闭开关时不同花顺发起任何请求且同步正常完成；补齐失败时整次同步失败，不得静默写入"北交所无归属"的快照。补齐数量以 `backfilled_stock_count` 记录。

- **AC-SRC-001**：代码扫描和测试证明个股数据路径不包含上交所/深交所下载、Baostock、个股爬虫或浏览器自动化；同花顺 REST HTTP 只允许存在于 `core` 的受控适配层。
- **AC-SRC-002**：同花顺凭据和配置只从根目录 `.env` 读取，仓库中没有真实值。
- **AC-SRC-003**：开盘啦使用批准的板块资金流以及行业—股票 URL、分页参数和凭据规则，所有可变值来自 `.env`；`KPL_DEVICE_ID`、`KPL_USER_ID`、`KPL_TOKEN` 非空时附带，空值时省略。
- **AC-SRC-005**：日志和 API 响应不包含 API Key、Token、Device ID 或完整敏感请求参数。
- **AC-SRC-006**：模拟上游限流时，系统最多执行配置允许的有限尝试，并返回旧数据或稳定错误。
- **AC-SRC-007**：股票主数据同步在写入前校验本次结果的行数下界——低于「当前活跃股票数 × `STOCK_MASTER_MIN_COVERAGE_RATIO`（默认 0.9）」时整体失败（整批不写入、任何股票都不被停用）；首次同步（库中无活跃股票）不做该校验；`--dry-run` 同样执行校验。

### 8.5 板块资金流

- **AC-FLOW-001**：单日接口返回固定交易时间轴、板块序列、实际业务日期和 `stale` 状态。**"固定"的口径**：`time_points` 始终是完整交易时段的五分钟轴（09:30–11:30 与 13:00–15:00 各 25 个槽，共 50 个），与请求时刻无关；当天尚未走完由每条曲线自己表达 —— `series[].data` 只覆盖到最后一个已采集的时点，其后的槽不带值（不得补零或复制末值充数）。
- **AC-FLOW-002**：`inflow_top`、`outflow_top` 小于 0 或大于 30 时返回 `400`。
- **AC-FLOW-003**：历史接口只接受 1、5、10、20 个交易日窗口。
- **AC-FLOW-004**：多日汇总严格使用交易日序列和每日 15:00 快照。
- **AC-FLOW-005**：窗口内某日缺少 15:00 数据时，响应能识别缺失，不把其他时间快照冒充 15:00。
- **AC-FLOW-006**：开盘啦任一必要分页失败时，这一轮一行都不写。
- **AC-FLOW-009**：**默认勾选按每次取数结果重算**：点「更新于 HH:MM」刷新、切换日期、切换统计窗口后，都按该次响应的榜单重新勾选前 5 名，保证榜单、勾选与折线图来自同一份数据 —— 否则旧勾选的板块掉出新榜单时，两个榜单的勾选框会全部空着、折线图也一条线都不画。用户的手动勾选在同一份数据内有效，**无关的重渲染不得重置它**（只有取数结果变化才重算）。
- **AC-FLOW-010**：默认入口（未手选日期）以本模块最新已存快照日为业务日期，与公共日行情日期无关 —— 当天快照已落库时首屏必须显示当天，即使 `stock_daily_prices` 当天还没有任何行；只有在该快照日落后于"该有快照的最新交易日"（交易日 09:30 起即为当天，开盘前与休市日为最近一个已收盘交易日）时才退回最近一次快照并置 `stale=true`，绝不静默换回旧日期。当天快照尚未落库时按时间分岔：收盘前回 `202 DATA_PREPARING`（当天采集窗口还没走完），收盘后回最近一次快照 + `stale=true`（缺失就是缺失，不再谎称"准备中"）。读路径**不访问上游**，因此上游限流/不可用只体现在命令日志里，不会变成本次请求的状态码。
- **AC-FLOW-011**：读路径**没有任何回源能力**：`kaipanla/services/read_path.py` 不得 import 上游客户端或抓取器（`KaipanlaSectorFundFlowClient` / `KaipanlaSectorFundFlowFetcher` / `flow_client_settings`）。缓存身份为当天最新采集槽 `kaipanla:<date>T<HH:MM>`：新槽落库后同一参数的下一次请求必须重新查库（返回 `source='database'`，`cache_identity` 变为新槽），不得命中旧槽的缓存载荷。

### 8.6 大涨跌幅与大成交量个股

- **AC-MOVE-001**：涨幅恰好 `8.00%` 且成交额恰好 `8亿元` 的股票被纳入上涨组。
- **AC-MOVE-002**：跌幅恰好 `-8.00%` 且成交额恰好 `8亿元` 的股票被纳入下跌组。
- **AC-MOVE-003**：不满足涨跌幅或成交额任一阈值的股票不被纳入。
- **AC-MOVE-004**：结果按市场（上证/深证/北交所）和方向（上涨/下跌）分为六组，排序符合规格。
- **AC-MOVE-005**：六组数量和全部去重股票数量与明细一致。
- **AC-MOVE-006**：复制全部得到当日全部去重股票代码，以英文逗号分隔且顺序与页面看板一致（上证涨/跌 → 深证涨/跌 → 北交所涨/跌）；复制失败时页面不显示成功。
- **AC-MOVE-007**：一组为空时返回空数组和数量0，不返回整个接口错误。
- **AC-MOVE-008**：北京证券交易所股票不被归入上证/深证四组，而是作为独立的 `bse_rise`/`bse_fall` 两组返回，并计入 `stock_codes` 与 `distinct_stock_count`；不返回“已排除 N 只”这类排除数量警告。
- **AC-MOVE-009**：个股结果如带行业标签，只返回开盘啦行业标签；前端不展示股票代码，行业标签通过悬浮提示呈现。
- **AC-MOVE-010**：北交所上涨组按涨幅降序、下跌组按涨幅升序，同涨幅按代码升序；该行两侧均为空时页面不渲染该行，其余两组市场不受影响。
- **AC-MOVE-011**：每个交易所半区内的胶囊固定为 3 列（`repeat(3, minmax(0, 1fr))`），所有胶囊等宽（网格项铺满轨道）且文字在框内左对齐，右括号不与右边框重合；`≤80rem` 退回 2 列、`≤40rem` 退回 1 列。复制按钮无边框无底色，图标渲染在"全部复制"文字之后。

### 8.7 板块动量

- **AC-MOM-001**：涨幅大于 `5%` 的口径不包含恰好 `5.00%` 的股票。
- **AC-MOM-002**：全市场涨幅前5%按 `max(1, floor(当日有效股票数 × 5%))` 取样；同涨幅边界使用稳定次级排序，结果可重复。
- **AC-MOM-003**：综合评分等于“股票数量 × 平均涨幅 × 行业成交额占全市场成交额比例”。
- **AC-MOM-004**：每个口径最多返回评分前10行业，按评分降序。
- **AC-MOM-005**：行业股票明细、股票数量和聚合值一致。
- **AC-MOM-006**：缺少开盘啦行业—股票映射的股票不被错误分组，响应包含未映射数量；存在多个行业时分别计入每个所属行业。
- **AC-MOM-007**：业务结果按 `business_date` 唯一（一天最多一行），同一天重跑是覆盖而不是追加。
- **AC-MOM-008**：行业动量排行、图表和股票明细只使用并返回开盘啦行业。
- **AC-MOM-009**：柱状图为竖排分组柱，类目轴按名次从左到右排列（评分最高在最左）；每个行业三根子柱依次表示股票个数、平均涨幅、成交占比，并各占一根数值轴。展开明细在一行内列出该行业全部入选个股，写作「股票名称（涨幅，成交额）」，不展示股票代码。
- **AC-MOM-010**：两种口径并排一行展示；窄屏（宽度不超过 64rem）回到单列。

### 8.8 百日新高新低

- **AC-HD-001**：目标日收盘价不参与前99个全市场交易日位置的最大/最小值计算。
- **AC-HD-002**：目标日收盘价大于或等于前99日最大值时标记新高。
- **AC-HD-003**：目标日收盘价小于或等于前99日最小值时标记新低。
- **AC-HD-004**：目标日无有效行情的股票不标记新高或新低。
- **AC-HD-005**：历史停牌日和上市前缺失值在滚动窗口中填 `0`，但目标日缺失值不填充。
- **AC-HD-006**：行业聚合数量与股票级标志数量一致；一个股票属于多个行业时分别贡献给每个所属行业。
- **AC-HD-007**：每日占比等于当日标志数量除以当日有效股票数，分母为0时返回空值而不是除零错误。
- **AC-HD-008**：结构化趋势数据能够由前端渲染，不依赖服务器生成 Base64 图片才能使用。
- **AC-HD-009**：业务结果按 `business_date` 唯一（一天最多一行），同一天重跑是覆盖而不是追加。
- **AC-HD-010**：百日新高新低的行业排行和股票明细只使用并返回开盘啦行业。
- **AC-HD-011**：展开的股票明细按当日涨跌幅排序 —— 新高行业排行降序（涨幅大的在前），新低行业排行升序（**跌得多的在前**，如 -18.33% 排在 -8.37% 之前）；两个排行都写作"名称（涨幅，成交额）"，当日无行情的股票（`change_percent` 为空）排在最后且不被丢弃，同涨跌幅按代码升序保证顺序稳定。

### 8.9 缓存、兜底和性能边界

- **AC-FALL-001**：缓存命中时不访问数据库和远程数据源。
- **AC-FALL-002**：缓存损坏时自动回退数据库并重建缓存，不返回500。
- **AC-FALL-003**：缓存缺失而数据库有数据时，从数据库返回并回写文件缓存（缓存身份取所服务结果行的 `created_at`）。
- **AC-FALL-004**：数据库缺失但有可用旧缓存时，返回旧数据并设置 `stale=true`。
- **AC-FALL-005**：任何 Web 请求都不访问上游——四个模块的读路径都不得 import 上游客户端或抓取器。请求内唯一允许的写操作是只读本地公共数据的派生结果生成（5.8(a)），它由数据集锁保护，且失败不得破坏已有结果。
- **AC-FALL-006**：需要全市场同步或大量上游请求的工作一律不在 HTTP 请求中执行，返回 `202 DATA_PREPARING` 或旧数据；该限制不适用于仅读本地公共数据的派生结果生成（见 5.8(a)），后者没有行数门槛。
- **AC-FALL-007**：管理命令失败后，库里上一次成功的数据及其缓存仍可通过 API 访问。
- **AC-FALL-008**：命令写入中途失败时，旧数据的缓存仍然有效——缓存身份取自已落库的数据本身，没有被改写的行就不会有新的身份。
- **AC-FALL-009**：同一数据集并发到达时只有一个获得锁，其他请求返回旧数据、`202` 或 `409`。
- **AC-FALL-010**：请求某日期时若本地已有该日公共日行情但缺派生结果，当场生成该日期结果并返回，不发起上游请求。
- **AC-FALL-011**：未指定日期的请求以最新有公共日行情的日期为读取目标（板块资金流例外，它的锚点是自己的最新已存快照日，见 AC-FLOW-010）；该日无法生成且存在任何旧结果时，返回旧结果并设置 `stale=true`。
- **AC-FALL-012**：显式指定日期时不得返回其他业务日期的结果；无本地公共数据即返回 `404 DATA_NOT_AVAILABLE`。

### 8.10 时间边界

- **AC-TIME-001**：所有日期和收盘判断使用 `Asia/Shanghai`。
- **AC-TIME-002**：交易日 14:59:59 请求当天盘后模块（显式带当天日期）时，不生成当天结果，返回 `202 DATA_PREPARING`；未指定日期的默认入口此时解析到上一个交易日，除非当天已由盘中刷新写入公共行情。
- **AC-TIME-003**：交易日 15:00:00 后，只有当天的公共数据已经落库时才允许生成当天结果。
- **AC-TIME-004**：15:00 后上游尚未提供完整数据时返回旧数据或准备中，不写入空结果。
- **AC-TIME-005**：周末或休市日默认展示最近一个有数据的交易日并明确实际业务日期。

### 8.11 API 契约

- **AC-API-001**：所有业务 API 路径均以 `/api/` 开头并按 App 子路径分发。
- **AC-API-002**：所有业务响应包含统一外壳字段，业务正文位于 `data`。
- **AC-API-003**：无效日期格式返回 `400 INVALID_DATE`，不静默回退。
- **AC-API-004**：未登录访问业务 API 返回 `401 AUTH_REQUIRED`。
- **AC-API-005**：数据准备中且无旧数据时返回 `202 DATA_PREPARING`。
- **AC-API-006**：返回旧数据时 HTTP 可为200，但必须设置 `stale=true` 并包含警告。
- **AC-API-007**：`business_date` 始终等于正文数据的实际日期。
- **AC-API-008**：禁用模块后其 API 不挂载，不能通过猜测 URL 访问。

### 8.12 安全与部署

- **AC-SEC-001**：生产配置检查证明 `DEBUG=False`、`ALLOWED_HOSTS` 非空且 `SECRET_KEY` 来自 `.env`。
- **AC-SEC-002**：所有修改状态的 Session API 通过 CSRF 测试。
- **AC-SEC-003**：非管理员无法访问 Django 管理后台。
- **AC-SEC-004**：仓库扫描不包含真实凭据、SQLite、缓存、日志、`.env`、虚拟环境或构建产物。
- **AC-SEC-005**：恶意日期、超大整数、未知枚举和脚本字符串不会导致 SQL 注入、路径访问或 HTML 注入。
- **AC-SEC-006**：本地和阿里云环境只通过 `.env` 切换，不需要修改源代码。

### 8.13 运维可观测性

- **AC-OPS-001**：管理员可在 Django 管理后台查看公共数据与每个启用模块已落库的结果数据（只读，不提供在线重跑）。
- **AC-OPS-002**：库内**没有**运行状态表，也没有数据集版本表；"上一次跑成功了吗"只由命令日志回答——每次运行至少留下一行开始事件与一行结束/失败事件（`data_command_started` / `_finished` / `_failed`），失败事件带稳定错误信息。
- **AC-OPS-003**：同一数据集不可并发执行：第二个执行者拿到锁失败并报 `SYNC_IN_PROGRESS`，不排队；失败不改变库里已有数据。
- **AC-OPS-004**：不做任何外部通知。
- **AC-OPS-005**：本期不存在自动备份、自动归档或定时清理任务。
- **AC-OPS-006**：数据集锁记录持有者（主机、PID、创建时间、唯一令牌）。获取失败时：同主机且持有者进程已不存在即回收该锁；无法判定持有者（跨主机、主机名缺失、锁文件损坏或只写了一半）时，锁文件超过 `LOCK_STALE_SECONDS` 才回收；同主机且持有者进程仍存活时一律不回收。回收必须原子（两个进程同时判定为陈旧时只有一个取得回收权），释放时校验令牌，不得删除已被他人重建的锁。回收记 `dataset_lock_reaped` 警告日志。

## 9. 规格边界：Always / Ask First / Never

### Always

- 始终先通过完整性校验，再在一个事务里写入 SQLite，写入成功后才回写文件缓存。
- 始终从根目录 `.env` 读取配置。
- 始终使用同花顺 REST API 获取个股公共数据，并使用开盘啦接口获取行业—股票公共数据。
- 始终保持四个业务 App 的代码、数据库和运行失败相互隔离。
- 始终在 API 中返回实际业务日期、数据写入时刻（`data_updated_at`）和过期状态。
- 始终使用 `Asia/Shanghai` 判断交易日和15:00边界。
- 始终为错误、空数据、旧数据和警告提供可区分状态（`partial` 由告警列表体现，不另外用 chip 标注）。

### Ask First

出现以下情况必须先更新规格或询问用户：

- 同花顺 REST API 无法在额度内支持最近一年逐股票前复权日线初始化。
- 开盘啦接口无法提供可验证的行业或股票列表。
- 需要将个股数据改用爬虫或浏览器自动化。
- 需要改变已批准的 REST 或开盘啦数据源。
- 需要引入 Redis、Celery、消息队列或替换 SQLite。
- 需要让一个业务 App 调用另一个业务 App。
- 需要改变大涨跌幅、成交额、板块动量或百日新高新低算法口径。
- 需要为内部 API、文件上传接口或 18:00 行为保留兼容层。
- 需要增加自动备份、自动清理或外部通知。

### Never

- 永不把真实凭据、Token、Device ID 或 `.env` 提交到仓库。
- 永不从 Web 请求启动无边界的全市场采集或历史重算（**只读本地公共数据、生成单个交易日派生结果的本地计算不属于此列**，见 5.8(a)）。
- 永不把不完整的数据批量写入。
- 永不跨业务 App 导入模型、服务或查询数据库。
- 永不伪造上游未提供的字段或用0替代未知数据。
- 永不因一个业务模块失败而使其他模块 API 不可用。
- 永不将同花顺 REST 行业目录或成分接口作为行业—股票关系的**正式来源**；它只被允许用于 §5.2.3 定义的北交所归属增量补齐（只增不删、开盘啦仍是权威、可由 `HITHINK_INDUSTRY_BACKFILL_ENABLED` 关闭）。
