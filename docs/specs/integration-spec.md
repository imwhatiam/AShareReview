# A 股市场复盘系统整合规格

**规格状态：** 已确认；后续计划已批准\
**版本：** 1.1\
**日期：** 2026年9月8日  
**目标仓库：** `<repo>`  
**需求来源：** `docs/ideas/integration.md`

> 本文是实现前的产品与技术规格，只描述目标行为、边界和验收方式，不包含实施计划，也不授权修改代码。

## 0. 已确认前提与规格解释

本规格基于前期访谈和构想收敛结果，不再重新讨论已经确认的产品方向。

### 0.1 已确认前提

1. 产品是部署在阿里云服务器、主要由系统所有者个人使用的 Web 应用。
2. 前端采用统一产品外壳，通过 Tab 进入四个一级功能模块。
3. 后端由不可删除的 `core` 和四个可插拔业务 Django App 组成。
4. 四个业务 App 彼此零依赖，但都允许依赖 `core` 提供的稳定公共契约。
5. 使用 Django Session 登录认证，不开放注册，不设计多人协作和复杂权限。
6. 使用 SQLite 和本地文件缓存，不引入 Redis、Celery、消息队列或微服务。
7. 正常数据链路是 `crontab → Django 管理命令 → SQLite/文件缓存 → Web API`。
8. Web 请求中的远程同步修复必须是有严格预算的轻量兜底，不能替代正常采集任务；与之相对，**只读本地已落库公共数据、为单个交易日生成派生结果的本地计算是允许的请求内工作，不受该预算限制**，它不接触上游、也不扩大数据获取范围（见 5.8(a)）。
9. 个股公共数据只允许通过同花顺正式 REST API 获取：股票列表、交易日历和单股票历史日线；不使用 Python SDK。
10. 开盘啦板块资金流继续使用 `fundflow` 已验证的上游 URL、参数和解析语义。
11. 盘后当日数据从交易日北京时间 15:00 起具备“可以生成”的时间资格，但仍须通过完整性检查；15:00 不等于上游数据必然已全部发布。
12. 公共日行情首次初始化使用以执行日为终点的滚动最近一年窗口。系统只向业务模块承诺最近一年的公共日行情可用范围；备份、归档和文件缓存清理由系统所有者手动处理。
13. 行业关系同步并保存当前开盘啦行业关系，不保留历史有效期；分析与展示使用同一份行业快照。

### 0.2 本规格采用的解释性假设

以下细节在已确认需求中没有逐项命名，本规格为形成可测试契约采用如下解释；用户评审规格时可以调整：

- “上证/深证四组”按 `core` 的交易所元数据判断。北京证券交易所股票不冒充深证股票：它们不进入上证/深证的涨跌四组，但在 `stock_moves` 中单独构成「北交所上涨」「北交所下跌」两组对外展示并计入「全部复制」（早期版本只返回一条排除数量警告，2026-09-12 改为直接列出；同日进一步按涨跌方向拆成两组，以匹配"行=市场、列=方向"的看板版式）；它们也可进入全市场成交额、板块动量和百日指标的有效股票集合。
- “全市场涨幅前5%”按涨幅降序取 `max(1, floor(当日有效股票数 × 5%))` 只股票；同涨幅跨越边界时仍按稳定次级排序截断，不扩展样本数。
- 显式无效 API 参数返回 `400`，不采用旧接口的静默截断或回退。
- 百日新高新低保留旧项目已记录的历史缺失填 `0` 算法，详见 3.1.5。
- “最近一年”指首次初始化和对业务承诺的可查询窗口；数据库备份、归档和文件缓存清理仍由系统所有者手动处理。

### 0.3 已完成验证与实施时持续观测的外部条件

2026年9月8日的最小只读验证已记录在 `docs/data-sources/hithink-and-kaipanla-capability.md`：

- 当前 API Key 可使用股票列表、交易日历和单股票最近一年历史日线 REST 端点；日线使用 `interval=1d`、`adjust=forward`。
- 开盘啦可取得“行业 → 行业股票列表”的完整链路；同一股票可属于多个行业。
- 当前设计不使用同花顺行业目录、行业成分、全市场历史导出或 Python SDK，**唯一例外**是北交所行业归属的增量补齐（见 §5.2.3）。
- 开盘啦资金流接口未获得经实际请求验证的历史快照时间参数支持；相应管理命令不提供 `--date`、`--snapshot-time` 或其他显式历史时间参数，只采集上游当前或最近快照。
- 上游未公布固定 QPS、并发和每日额度，且连续调用曾遇到 HTTP 429；实现必须采用可配置低并发、请求间隔、有限退避和失败保留旧版本。

若已批准端点、开盘啦链路或实际额度无法满足最近一年逐股票同步，不得静默改用个股爬虫、浏览器自动化或其他未批准数据源；应先更新规格或获得用户确认。

## 1. 背景和目标

### 1.1 背景

现有能力分散在两个项目中：

- `fundflow` 提供开盘啦板块资金流的采集、保存、查询和图表展示能力。
- `fupan` 提供大涨跌幅与大成交量个股、行业分析、百日新高/新低三类盘后分析能力。

两个项目在页面外观、数据来源、数据库、缓存、初始化方式、API 路径和运行管理方面不一致。`fupan` 现有个股数据链路依赖上交所、深交所下载文件和人工行业文件，不符合新系统使用同花顺 REST API 获取个股数据、使用开盘啦获取行业—股票关系的要求。

本次整合需要在保留核心业务功能的同时，建立可长期维护的模块边界，使任何一个业务模块的失败、停用或删除都不影响其他业务模块。

### 1.2 产品目标

构建一个统一的 A 股盘中监控与盘后复盘系统，提供四个一级入口：

1. 板块资金流
   - 开盘啦
2. 大涨跌幅与大成交量个股
3. 板块动量
4. 百日新高新低占比

登录后默认进入“板块资金流 → 开盘啦”。

### 1.3 架构目标

- 建立一个不可删除的公共基础 App：`core`。
- 建立四个相互独立的业务 App：`kaipanla`、`stock_moves`、`sector_momentum`、`hundred_day`。
- 每个业务 App 独立拥有模型、迁移、数据库、URL、视图、服务、管理命令、缓存命名空间和测试。
- 业务 App 只通过 `core` 的公开服务接口、数据版本和稳定标识访问公共数据。
- 禁止业务 App 之间直接调用、导入或查询彼此的数据。
- 删除任意三个业务 App 后，`core` 与剩余 App 仍能启动、迁移、采集、计算、测试并提供 API。

### 1.4 数据目标

- `core` 保存一份公共个股原始日行情，供三个盘后分析 App 使用。
- `core` 保存股票基础信息、交易日历，以及当前开盘啦行业—股票快照（`industry_code`、`industry_name`、`stock_codes`）。
- 业务 App 保存自己的上游快照或派生分析结果，不复制公共原始日行情。
- 派生结果记录所依赖的公共数据版本，而不是依赖另一个业务 App 的执行结果。
- 管理命令失败时，系统优先继续提供已有缓存或数据库数据，并明确标识数据是否过期。

### 1.5 成功定义

系统成功整合后，用户在一个登录入口和统一界面中完成原有盘中、盘后分析工作；模块边界可通过自动测试证明；数据缺失和上游故障不会导致整个站点不可用，也不会在 Web 请求中触发无边界的重任务。

## 2. 能力地图和依赖边界

本项目包含多个可独立验收的能力。以下模块 ID 在后续规格、计划和测试中保持稳定。

| 模块 ID | 类型 | 职责 | 允许依赖 |
|---|---|---|---|
| `core` | 基础能力 | 认证、模块注册、公共市场事实数据、数据版本、缓存工具、锁、公共状态 | Django、同花顺正式 REST API 受控适配层 |
| `kaipanla` | 业务能力 | 开盘啦板块资金流采集、快照、排行和分时/多日查询 | `core` |
| `stock_moves` | 业务能力 | 大涨跌幅与大成交量个股分析（仅板块标签） | `core` |
| `sector_momentum` | 业务能力 | 开盘啦板块动量分析 | `core` |
| `hundred_day` | 业务能力 | 百日新高新低及板块占比分析 | `core` |
| `frontend-shell` | 产品外壳 | 登录态、一级/二级 Tab、统一视觉、模块装载和通用状态展示 | `core` 和各已启用业务 API 的公开契约 |

依赖方向必须始终为：

```text
frontend-shell → core
frontend-shell → enabled business API contracts
kaipanla       → core
 stock_moves   → core
 sector_momentum → core
 hundred_day   → core
```

禁止形成业务模块之间的依赖边：

```text
kaipanla/stock_moves/sector_momentum/hundred_day
    ──X──> 任意其他业务 App
```

推荐的后续实现顺序是：先建立 `core` 的配置、数据和接口契约；随后四个业务 App 可按公共数据就绪情况并行迁移；统一前端外壳在 API 契约确定后接入各模块；最后进行单模块删除测试和端到端整合验收。该顺序仅用于说明依赖，不属于本轮实施任务。

## 3. 范围与非目标

### 3.1 本期范围

#### 3.1.1 统一产品外壳

- 登录页面、退出入口和登录态检查。
- 四个一级 Tab，只显示文字标签，不显示左侧图标（见 AC-UI-003）。
- 默认路由为开盘啦板块资金流。
- 统一页面宽度、字体、间距、卡片、按钮、日期控件、看板、排行列表、图表和提示样式。
- 日期控件使用自绘的日历弹层（触发器沿用输入框的边框 / 圆角 / 字号尺度，弹层使用品牌色选中态与轻阴影），不呈现浏览器原生 `input[type=date]` 的日历弹层，以保持各页面视觉一致。
- 统一颜色语义：A 股上涨为红色、下跌为绿色；状态色与涨跌色分离。
- 统一加载、空数据、过期数据、数据准备中、请求失败和无权限状态。
- 四个页面共用同一条日期回填规则（`shared/businessDate.js`）：未手选日期时日期控件显示后端返回的业务日期。否则控件只会显示占位文案「最新交易日」，用户看不到自己在看哪一天。
- 根据静态模块注册表和启用开关显示或隐藏模块入口。

#### 3.1.2 开盘啦板块资金流

保留 `fundflow` 的以下核心行为：

- 采集开盘啦全量分页板块排行。
- 保存交易日内板块资金流快照。
- 快照落库时刻由**运行时刻**决定，且必须落在标准 5 分钟槽上（交易日为 09:30–11:30、13:00–15:00 共 50 个槽）：盘中向前回退到所在槽（09:33 → 09:30，10:46 → 10:45，14:22 → 14:20）；午休 11:30–13:00 回退到 11:30；收盘后（含 16:34 等盘后运行）一律落在 15:00。
- 非交易日采集归到**最近一个交易日**的 15:00；交易日开盘前采集同理归到上一交易日的 15:00（那时最新完整数据仍是上一交易日收盘），不得伪造成当天收盘快照。
- 同一 `sector_code` + `snapshot_time` 重复写入为覆盖（upsert），因此同一槽位内多次采集只保留最后一次；盘后重复运行只会刷新当日 15:00 收盘快照，不新增快照时间。
- 落库时刻的判定统一由 `kaipanla.services.intraday.resolve_snapshot_slot()` 提供，管理命令、`--latest` 与 Web 请求触发的补齐**共用同一函数**。
- 交易日判定分层：**周末（含调休上班的周末）一律不是交易日**；工作日的法定节假日用第三方库 `chinese-calendar` 判定，因此不依赖同花顺交易日历是否已同步到当天；`chinese-calendar` 无该年数据时（按年内置节假日表）退回同花顺交易日历。同花顺 `TradingDay` 日历仍是历史交易日与窗口计算的权威来源，两者在 2025-09 至 2026-09 的逐日核对中完全一致（0 冲突）。
- 计算"最近一个交易日收盘"仍需要 `TradingDay` 日历；日历为空时写入失败并报错，不得猜测交易日。
- 图表在上、流入 / 流出排行在下的页面结构；单日模式展示固定交易时间轴上的资金流入和流出排行曲线。
- 折线图不设顶部图例，板块名与当前资金净额常驻在每条折线右端（净额带正负号、单位亿元）。
- 分时横轴刻度落在整十分钟上：上午 09:30 起、下午 13:00 起，末刻度为 15:00；不按索引等间隔抽稀（午休两侧槽位数不等，按索引抽稀会使下午首个刻度错位到 13:05）。
- 日期与统计窗口控件不带外层背景边框，分段按钮与日期控件上下边缘对齐。
- 每侧最多请求 30 条，页面按每侧 10 条展示排行并默认勾选前 5 条。
- 支持用户勾选和取消具体板块曲线。
- 支持当日、5日、10日、20日切换。
- 所有统计窗口都以最近一个已发布交易日为终点：点任一窗口按钮都会清空手选日期，按最新交易日往回取 1/5/10/20 个交易日。
- 用户显式选择的日期会成为窗口终点（当日即该日，多日即截止该日）。
- 多日模式使用各交易日 15:00 快照进行汇总和排序。
- 同一交易日内保留用户选择；切换交易日后恢复默认选择。
- 展示加载、空数据、错误和过期状态。

#### 3.1.3 大涨跌幅与大成交量个股

- 按交易日查看结果。
- 筛选涨幅 `>= 8%` 且成交额 `>= 8亿元` 的股票。
- 筛选跌幅 `<= -8%` 且成交额 `>= 8亿元` 的股票。
- 按「行 = 市场、列 = 方向」的看板展示：行为上证、深证、北交所，列为上涨、下跌，共六组（`sse_rise`、`sse_fall`、`szse_rise`、`szse_fall`、`bse_rise`、`bse_fall`）。
- 上涨组按涨幅降序、下跌组按涨幅升序（北交所两组同口径）。
- 满足同样阈值的北京证券交易所股票不并入上证/深证四组，而是在两个交易所之后单独占一行，并按涨跌方向拆成「北交所上涨」「北交所下跌」两栏。该行两侧均无股票时不渲染。
- 每只股票渲染为一枚圆角胶囊，只展示名称、涨跌幅和成交额；股票代码不上屏，开盘啦行业标签改由悬浮提示承载。
- 每个交易所半区内的胶囊固定为 **3 列**（不随窗口宽度在 2~3 列之间浮动）；网格项铺满各自轨道，因此**所有胶囊等宽**、文字在框内左对齐，右侧留出余量。三列要放得下最长的一条（实测 165.4px 文字 + 左内边距 6px + 边框 1px，轨道需 ≥172.4px 才不压边框，留出完整右内边距需 ≥178.4px），按「轨道宽 =（窗口与 82rem 容器上限取小 − 90px 页面与面板内边距 − 116px 轨道骨架）/ 6」换算约需 1276px 窗口，故 `≤80rem` 退回 2 列、`≤40rem` 退回 1 列。
- 涉及股票总数由复制按钮承载（文案为"共 N 只股票，全部复制"），不再单独渲染统计块。总数包含北交所两组的股票。该按钮是纯文字动作：无边框、无底色（`.btn--ghost`），复制图标位于"复制"文字之后。
- 支持一键复制全部涉及股票代码：以**英文逗号**分隔（不是换行），顺序与页面看板一致（上证涨/跌 → 深证涨/跌 → 北交所涨/跌，组内按排名）。日期控件与复制按钮同处一行并纵向居中对齐，按钮**无边框、无底色**（`.btn--ghost`），不使用实心品牌蓝，也不用白底描边。

#### 3.1.4 板块动量

- 按交易日分析当前开盘啦行业，并允许同一股票分别计入多个行业。
- 保留“涨幅超过 5%”股票的行业聚集分析。
- 保留“全市场涨幅前 5%”股票的行业聚集分析，样本数为 `max(1, floor(当日有效股票数 × 5%))`。
- 每种口径展示综合评分前 10 的行业。
- 每个行业展示股票数量、平均涨幅、行业成交额占全市场成交额比例、综合评分和涉及股票。
- 综合评分保持原有业务口径：`股票数量 × 平均涨幅 × 行业成交额占比`。
- 两种口径并排在同一行展示（窄屏回到单列），便于左右对照同一批行业。
- 每个口径的图表为竖排分组柱状图：类目轴按名次从左到右排列，评分最高的行业落在最左边；每个行业一组三根子柱，依次表示股票个数、平均涨幅、成交占比。
- 三根子柱量纲不同（只 / 涨幅百分比 / 成交额占比百分比），各占一根数值轴：股票个数在左轴，平均涨幅在右轴，成交占比在右轴的偏移轴上；单位写进图例，避免三套分隔线叠在一起。
- 行业股票明细展开后，在一行内列出该行业全部入选个股，写法为「股票名称（涨幅，成交额）」，不展示股票代码。
- 日期控件与"全市场成交额"同处一行并纵向居中对齐；该指标为纯文字，不带边框与底色。
- 页面不渲染"未映射到开盘啦板块"告警：未映射数量属于上游行业映射的覆盖度说明，用户无法处理且每次都会出现；数量仍保留在接口数据 `unmapped_stock_count` 中（见 §5.5.4）。

#### 3.1.5 百日新高新低占比

- 按交易日计算个股相对前 99 个全市场交易日位置中历史收盘价的百日新高和百日新低。
- 当日收盘价不进入历史比较窗口。
- 当日无有效行情的股票不参与当日判断。
- 保留旧项目的缺失值口径：在计算历史滚动窗口前，将新上市前和停牌日的历史缺失收盘价填充为 `0`；目标日收盘价保持原值，不填充。
- 使用 `shift(1).rolling(99)`，要求目标日在全市场交易日序列中已有 99 个历史位置；由于历史缺失已填 `0`，单只股票实际上市不足 99 日时也可参与判断。
- 按开盘啦行业统计新高和新低数量，并展示行业内股票明细；同一股票可显示在多个所属行业。
- 展示当日有效股票总数、新高数量和新低数量；日期控件与这三个指标同处一行并纵向居中对齐。三个指标为纯文字、不带边框与底色，新高用涨色、新低用跌色（文字颜色区分，不再用底色块）。
- 展示近期最多 100 个交易日的新高占比和新低占比走势。
- 为生成完整的 100 日趋势，计算输入最多需要目标日前后合计 199 个交易日位置，最近一年公共日行情应覆盖该窗口。

上述历史缺失填 `0` 的行为可能与严格金融时间序列语义不同，但属于现有 `fupan` 已明确记录的业务算法。本次以“功能不变”为优先，必须通过回归样例固化；若未来调整，应单独修改规格和数据版本。

#### 3.1.6 公共基础数据

- A 股股票代码、名称、交易所和有效状态。
- 以执行日为终点的滚动最近一年内前复权个股日行情（`adjust=forward`）。
- 最近一年的交易日历及最近交易日计算。
- 当前开盘啦行业目录。
- 当前股票与行业—股票映射，不保留历史有效期。
- 公共数据同步批次、业务日期、数据版本和完整性状态。
- Django 用户、Session、CSRF、模块注册和后台状态管理。

## 4. 用户流程

### 4.1 登录与首次进入

1. 未登录用户访问产品页面。
2. 系统跳转到登录页面，不加载任何业务数据。
3. 用户输入由管理员创建的账号和密码。
4. 登录成功后，前端获取当前用户和已启用模块列表。
5. 前端进入“板块资金流”一级 Tab，直接打开开盘啦资金流页面。
6. 开盘啦页面在未指定日期时请求最新可用交易日数据。
7. 页面在返回旧数据时显示对应状态提示；`partial` 不再单独用 chip 标注（它等价于"存在 warnings"，与紧随其后的告警列表是同一件事），改由告警文案直接呈现。

失败行为：

- 登录失败时只提示通用账号或密码错误，不暴露账号是否存在。
- Session 过期时，API 返回未认证状态，前端清理页面数据并回到登录页。
- `kaipanla` 被禁用时，默认入口顺延到第一个已启用业务模块；若没有业务模块启用，则显示“暂无已启用模块”。

### 4.2 浏览板块资金流

1. 用户进入板块资金流页面。
2. 页面不预置浏览器日期：未手选日期时按最近一个已发布交易日取数，日期控件显示该交易日。
3. 单日模式展示固定交易时间轴；图表下方并排展示各 10 条资金流入排行和资金流出排行。折线图不渲染顶部图例，每条曲线右端常驻板块名与资金净额。
4. 用户勾选排行中的板块，图表即时增加或移除对应曲线。
5. 用户选择 5日、10日或20日时，窗口以最近一个已发布交易日为终点，按交易日历往回取固定交易日窗口，并使用每日 15:00 快照汇总；点任一窗口按钮都会清空手选日期。
6. 用户切回“当日”时恢复单日完整时间轴，同样以最近一个已发布交易日为准，日期控件同步显示该交易日。
7. 用户显式选择日期时，该日期成为当前窗口的终点：当日即该日数据，多日即截止该日的窗口。

数据状态行为：

- 缓存命中：直接返回缓存数据。
- 缓存未命中、数据库命中：从数据库构建结果并回写缓存。
- 当日数据缺失且轻量修复符合预算：执行一次受控修复，然后返回结果。
- 修复预计超过预算：返回“数据准备中”或已有旧数据，不阻塞页面。
- 只有旧数据可用：返回旧数据并显示“数据可能已过期”。
- 上游拒绝请求且没有旧数据时：该页面只把图表和两张排行替换为“数据暂不可用”状态，日期与统计窗口控件保留在原位，不影响其他一级模块。
- 任何数据状态下日期与统计窗口控件始终可见：切换日期或统计窗口后若无数据，用户仍可直接改回有数据的条件。

### 4.3 查看大涨跌幅与大成交量个股

1. 用户进入对应一级 Tab。
2. 页面默认请求该模块最新完整交易日。
3. 用户通过日期控件选择其他交易日。
4. 页面以「行 = 市场、列 = 方向」的看板展示上证、深证的上涨和下跌四栏，每只股票是一枚胶囊（名称、涨跌幅、成交额），悬浮显示开盘啦板块；每个交易所半区内的胶囊固定排成 3 列。
5. 有满足阈值的北京证券交易所股票时，在两个交易所之后追加「北交所」一行，同样按涨跌分两栏；两侧都没有股票时不显示该行。
6. 用户点击“复制全部”，复制当日全部涉及股票代码，以英文逗号分隔。
7. 某组无结果时展示空组，不把整个页面视为失败。

如果指定日期的公共日行情未完整：

- 已有该日期旧版本派生结果时，返回旧版本并标识过期。
- 公共数据完整且只缺派生结果时，用本地已有公共数据当场生成该日期的结果（见 5.8(a)），不发起上游请求。
- 该日期没有公共日行情时，不生成；显式指定日期返回 `404 DATA_NOT_AVAILABLE`，未指定日期则回退到最近可用结果并标识过期。
- 需要全市场远程同步时返回“数据准备中”，不得在请求中执行全量同步。

### 4.4 查看板块动量

1. 用户进入“板块动量”。
2. 页面默认显示最新完整交易日。
3. 页面把“涨幅超过5%”和“全市场涨幅前5%”两套结果并排在同一行展示（窄屏回到单列）。
4. 每套结果展示前10行业、三指标分组柱状图和行业股票明细。
5. 用户展开行业后，在一行内看到该行业全部入选个股，每只写作「股票名称（涨幅，成交额）」。
6. 用户切换日期后重新加载对应数据版本。

如果股票缺少当前行业—股票映射，该股票可以计入全市场成交额和涨幅分位计算，但不能被错误归入任意行业；响应必须给出未映射股票数量警告。

如果该日期已有完整的本地公共日行情但缺派生排名，当场生成该日期的排名（见 5.8(a)），不发起上游请求；没有该日期公共日行情时不生成。

### 4.5 查看百日新高新低占比

1. 用户进入“百日新高新低占比”。
2. 页面默认显示最新具有足够历史窗口的完整交易日。
3. 页面显示有效股票总数、新高数量和新低数量。
4. 页面分别展示新高行业排行和新低行业排行，两个排行并排一行、各显示前 10 个行业。
5. 用户展开行业查看对应股票；明细按当日涨跌幅排序（新高排行降序、新低排行升序即跌得多的在前），写作"名称（涨幅，成交额）"。
6. 页面以柱状图展示近期每日新高占比（横轴上方）和新低占比（横轴下方）走势。
7. 用户切换日期时，图表终点和行业结果同步变化。

当目标日期之前的全市场交易日位置不足 99 个时，页面显示“历史数据不足，无法计算百日指标”，不输出伪造的全零结果。

如果该日期缺派生结果但本地已有足够的公共日行情窗口，当场生成该日期的指标（见 5.8(a)）。该模块是三个按需生成模块中唯一需要跨多交易日读取本地数据的，因此生成耗时最长；它仍然只读本地数据、不访问上游。

### 4.6 管理员查看运行状态

1. 管理员进入 Django 管理后台。
2. 管理员查看公共数据和四个业务模块的状态摘要。
3. 状态至少包含：模块、数据集、最新业务日期、最新成功时间、是否运行中、完整性、数据版本、是否正在返回旧数据、连续失败次数和错误摘要。
4. 管理员可进入对应业务 App 的详细运行记录查看完整错误，但不能在普通业务页面看到凭据或上游原始敏感响应。
5. 本期不要求从后台直接启动、停止或重跑管理命令。

### 4.7 crontab 采集与计算

1. 系统所有者在本地或阿里云通过 crontab 执行 Django 管理命令。
2. 命令获取互斥锁，避免相同数据集重复执行。
3. 命令记录开始状态和输入参数。
4. 命令采集或计算数据，先写数据库，再生成或失效文件缓存。
5. 全部成功后发布新的完整数据版本。
6. 部分成功时按模块规则保存可用数据并标记 `partial`，不得错误发布为完整版本。
7. 失败时保留旧版本，记录失败和连续失败次数，以非零退出码结束。
8. 一个模块命令失败不得中断其他模块的独立 crontab 任务。
9. 调度分两组：**盘中链路**（`refresh_intraday_quotes` 每 30 分钟、`fetch_kaipanla_sector_fund_flow` 每 5 分钟）只刷新当天公共行情与资金流快照，让页面在收盘前就能跟随当天；**盘后管线**（`sync_stock_daily_prices` + 三个 `build_*`，15:00 后）才发布当天的权威版本。两组共用同一套数据集与字段语义，因此可以相互覆盖而不产生歧义。

## 5. 数据和接口变化

### 5.1 数据库布局

| 数据库别名/文件 | 所有者 | 内容 |
|---|---|---|
| `core.sqlite3` | `core` | Django 认证、模块注册、公共市场数据、公共版本和状态摘要 |
| `kaipanla.sqlite3` | `kaipanla` | 开盘啦板块及资金流快照、完整性和详细运行记录 |
| `stock_moves.sqlite3` | `stock_moves` | 大涨跌幅与大成交量个股派生结果和详细运行记录 |
| `sector_momentum.sqlite3` | `sector_momentum` | 行业动量派生结果和详细运行记录 |
| `hundred_day.sqlite3` | `hundred_day` | 百日新高新低派生结果和详细运行记录 |

约束：

- 不允许跨 SQLite 数据库建立数据库外键。
- 业务结果通过股票代码、行业代码、业务日期和 `source_data_version` 引用公共事实。
- 业务 App 迁移只作用于自己的数据库。
- `core` 不导入业务 App 模型；公共状态表用稳定的 `module_id` 字符串记录来源。
- 业务 App 被移除后，`core` 中残留的历史状态记录不得阻止系统启动。

### 5.2 `core` 逻辑数据集

#### 5.2.1 股票基础信息

最小字段：

- `thscode`
- 六位股票代码
- 股票名称
- 交易所
- 资产类型
- 是否当前有效
- 数据更新时间

股票代码在所有模块中必须使用同一标准格式，禁止同一股票同时以带交易所和不带交易所的不同主键保存。

#### 5.2.2 交易日历

最小字段：

- 交易日期
- 是否交易日
- 时区：`Asia/Shanghai`
- 来源版本和同步时间

交易日判断必须来自公共交易日历，不允许四个业务 App 各自维护周末/节假日逻辑。

#### 5.2.3 当前开盘啦行业和股票映射

行业—股票关系使用开盘啦的行业 → 行业股票列表链路采集，并作为当前快照整批发布。表只包含以下三个业务字段：

- `industry_code`：行业代码；
- `industry_name`：行业名称；
- `stock_codes`：JSON 股票代码数组。

每条行业记录只保存行业代码、行业名称和股票代码列表，不额外持久化层级或历史有效期。相同股票可出现在多个行业的 `stock_codes` 中，派生分析按每个行业分别统计。

**北交所归属的增量补齐（唯一的同花顺行业来源）**：开盘啦 881xxx 行业族对北京证券交易所仍使用旧代码（43/83/87），无法表达本项目 `core_stock` 中的 920xxx，因此只靠开盘啦会让北交所股票全部无法归入任何行业。同步流程在开盘啦采集完成之后、发布之前，用同花顺行业目录与成分股接口补齐这一部分：

- **开盘啦仍是权威**。补齐是**纯增量**：只往开盘啦已有的行业里追加它没有的成员，绝不删除、绝不替换开盘啦的成员或行业。
- **只补同花顺也有对应行业的那些代码**（881xxx 与开盘啦 881xxx 同族同名的部分），以及本地 `core_stock` 中确实存在的股票。
- **只用于北交所归属**，不承担其他任何行业—股票关系的正式来源职责；同花顺 884xxx 等其它分类不参与。
- 由 `.env` 的 `HITHINK_INDUSTRY_BACKFILL_ENABLED` 控制，默认开启；关闭时不访问同花顺。补齐失败会使整次同步失败，不会静默退回"北交所无归属"的状态。
- 补齐数量记录在同步结果中（`backfilled_stock_count`）。

#### 5.2.4 公共个股日行情

最小字段：

- 业务日期
- 股票标准代码/`thscode`
- 前收盘价
- 开盘价
- 最高价
- 最低价
- 收盘价
- 涨跌幅
- 成交量
- 成交额
- 是否有有效交易
- 来源批次和数据版本

约束：

- 使用固定 `adjust=forward` 的前复权日 K 作为公共原始事实。
- 唯一键为“股票 + 业务日期”。
- 首次初始化只处理以执行日为终点的滚动最近一年内交易日。`init_stock_daily_prices --years 1` 可重复执行：每次都重新抓取整年窗口并与本地逐条比对，只更新与上游不一致的行、补齐缺失的行；与上游逐条一致时不发布新数据版本。它仍不得由 Web API 调用。
- 日常 `sync_stock_daily_prices --date YYYY-MM-DD` 只处理交易日历中的一个指定日期；每次成功同步为该日期创建独立的完整数据版本，重复执行通过“股票 + 交易日期”唯一键幂等覆盖该日期记录。
- 单个股票在成功上游请求中没有该日期日线时，保存 `has_valid_trade=false` 的非交易记录；若某个待发布交易日所有股票均无有效成交记录，则视为上游数据异常，整批不得发布为完整版本。
- 涨跌幅优先使用经验证的同花顺字段；若需本地计算，统一由 `core` 按前一有效交易日收盘价计算。
- 业务 App 不复制整张日行情表。

#### 5.2.5 数据版本和完整性

每个公共数据集至少记录：

- `dataset_key`
- `business_date` 或覆盖日期范围
- `version`
- 状态：`running`、`complete`、`partial`、`failed`
- 预期记录数
- 实际记录数
- 缺失记录数
- 开始时间和结束时间
- 最近成功时间
- 错误摘要

一个新版本只有在数据库写入完成且完整性检查通过后才能标记为 `complete`。文件缓存不得指向尚未发布的版本。

### 5.3 业务 App 数据集

#### 5.3.1 `kaipanla`

保留板块代码、板块名称、业务日期、对齐后的快照时间、涨跌幅、主力净流入、主力买入、主力卖出、大单净额、量比、成交额、流通市值和总市值等上游实际提供字段。

每次分页抓取必须记录完整性。任一必要页面最终失败时，不得把不完整分页结果发布为完整快照。

#### 5.3.2 `stock_moves`

派生结果至少保存：

- 业务日期

### 5.4 文件缓存

- 缓存根目录、TTL、开关和单项大小限制必须来自根目录 `.env`。
- 缓存按 `module_id / endpoint / 参数摘要 / data_version` 命名。
- 缓存内容包含生成时间、业务日期、数据版本和过期时间。
- 业务 App 只能清理或失效自己的缓存命名空间；`core` 可管理公共缓存工具，但不能解释业务正文。
- 数据库新版本写入并发布成功后才允许失效旧查询缓存。
- 缓存损坏、JSON 无法解析或版本不匹配时视为未命中，不能导致 500。
- 自动备份、长期归档和定期清理由本期排除；运行时可以安全覆盖同一个缓存键。

### 5.6 统一响应外壳

所有 JSON API 使用以下语义一致的响应外壳；各 App 的 `data` 结构独立：

```json
{
  "status": "ok",
  "business_date": "2026-09-08",
  "generated_at": "2026-09-08T15:05:00+08:00",
  "data_version": "daily-price:2026-09-08:v1",
  "stale": false,
  "source": "cache",
  "preparation": {
    "state": "ready",
    "retry_after_seconds": null
  },
  "warnings": [],
  "error": null,
  "data": {}
}
```

字段约束：

- `status`：`ok`、`partial`、`preparing`、`error`。
- `business_date`：响应正文对应的实际交易日，不得用请求日冒充。
- `generated_at`：当前业务结果生成时间。
- `data_version`：可用于缓存失效和问题定位的稳定版本字符串。
- `stale`：是否返回旧于当前应有业务日期或旧于最新公共数据版本的结果。
- `source`：`cache`、`database`、`remote`、`computed` 中之一。
- `preparation.state`：`ready`、`repairing`、`preparing`、`unavailable`。
- `warnings`：非致命问题，例如部分榜单失败、股票缺少行业映射、返回旧数据。
- `error`：失败时包含稳定错误码和面向用户的安全消息。

### 5.7 HTTP 状态和错误码

| HTTP 状态 | 场景 |
|---|---|
| `200` | 返回完整、部分或过期但仍可使用的数据 |
| `202` | 无可用旧数据，任务超出同步预算，数据正在准备或需运行管理命令 |
| `400` | 日期、天数、排行数量等请求参数无效 |
| `401` | 未登录或 Session 已失效 |
| `403` | CSRF 校验失败或访问管理员能力时权限不足 |
| `404` | 显式请求的业务日期不是可提供的数据日期，且不能修复 |
| `409` | 同一数据集已有互斥任务运行，当前请求不能重复触发 |
| `503` | 无缓存和数据库数据，远程数据源又不可用 |

稳定错误码至少包括：

- `AUTH_REQUIRED`
- `TOO_MANY_ATTEMPTS`
- `INVALID_DATE`
- `INVALID_PARAMETER`
- `CSRF_FAILED`
- `DATA_NOT_AVAILABLE`
- `DATA_PREPARING`
- `INSUFFICIENT_HISTORY`
- `DATA_INCOMPLETE`
- `SYNC_IN_PROGRESS`
- `UPSTREAM_RATE_LIMITED`
- `UPSTREAM_UNAVAILABLE`
- `CACHE_CORRUPTED`
- `MODULE_DISABLED`

### 5.8 Web API 读取和轻量修复顺序

每次业务查询按以下顺序执行：

1. 读取与请求参数及数据版本匹配的文件缓存。
2. 缓存未命中时读取本 App 的 SQLite 派生结果或快照。
3. 如果数据库已有结果，构建响应并回写文件缓存。
4. 数据缺失或派生结果落后于公共数据版本时，评估是否满足本地生成条件。
5. 符合条件时用**已经落库的公共数据**生成该日期的派生结果，持久化数据库后再写缓存并返回。
6. 本地生成不可用（公共数据不完整、历史不足等）时：已有旧数据则返回旧数据并标识 `stale`；无旧数据时返回 `404 DATA_NOT_AVAILABLE`（显式指定日期）或 `202 DATA_PREPARING`（未指定日期）。

必须区分两类"请求内工作"，二者预算规则不同：

**(a) 本地生成派生结果 —— 受保护的本地计算，不是远程修复**

- 只读取本 App 已落库的公共数据（`stock_daily_prices`、`industry_snapshot` 等），**绝不发起任何上游请求**。
- 因此**没有行数门槛**：一次全市场单日生成天然涉及数千行（实测全市场约 5,500 只股票），行数上限对它不适用，也不应据此拒绝生成。
- 用 `dataset_lock(module, dataset)` 保护：同一数据集只有一个请求在生成，其余请求立刻返回旧数据或 `202`，不排队。
- 未指定日期时以**最新完整公共日行情日期**为读取目标（而不是最新派生结果日期），保证首屏跟随实际已有数据。
- 显式指定日期且该日期无公共日行情时，不生成、不返回其他日期冒充结果，按第 6 条返回错误。

**(b) 远程同步修复 —— 有界预算，默认不启用**

- 预期正常完成时间不超过 3 秒。
- 硬超时默认不超过 5 秒，并可通过 `.env` 向下调整。
- 单次远程获取或数据库写入通常不超过 1,000 行。
- 最多一次有边界的远程尝试，不在请求内进行多轮长重试。
- 不允许执行全市场历史初始化、全量日行情同步或跨多日重算；尤其不得调用 `init_stock_daily_prices`。
- 板块资金流正常采集存在长等待时，不符合 Web 同步修复预算，应返回旧数据或准备中。
- 目前只有板块资金流模块保留了这条路径；个股异动、板块动量、百日新高均只做 (a)。

### 5.9 管理命令契约

最终命令名称可在实现前做一次一致性检查，但必须按 App 归属，不能由一个业务 App 代替其他 App 执行。

建议的命令契约：

```bash
# core：公共基础数据
python manage.py sync_stock_master
python manage.py sync_trading_calendar
python manage.py sync_kaipanla_industry_snapshot
# 首次部署时用于导入最近一年公共日行情；可安全重跑：抓取整年窗口后与本地逐条比对，
# 只更新与上游不一致的行、补齐缺失的行，无差异时不发布新版本
python manage.py init_stock_daily_prices --years 1
# 日常 crontab：仅同步指定当天；重复执行幂等，绝不扩大为全量历史抓取
python manage.py sync_stock_daily_prices --date YYYY-MM-DD
# 盘中链路（建议每 30 分钟）：用全市场实时快照刷新目标交易日（默认今天）
# 的公共日行情，让页面在收盘前就能跟随当天；与 sync_stock_daily_prices 同一数据集、
# 同一字段语义，收盘后仍以历史接口为权威来源
python manage.py refresh_intraday_quotes [--date YYYY-MM-DD]

# kaipanla
python manage.py fetch_kaipanla_sector_fund_flow [--latest] [--dry-run]

# stock_moves
python manage.py build_stock_moves --date YYYY-MM-DD

# sector_momentum
python manage.py build_sector_momentum --date YYYY-MM-DD

# hundred_day
python manage.py build_hundred_day --date YYYY-MM-DD
```

所有采集/计算命令共同要求：

- `init_stock_daily_prices --years 1` 用于首次部署导入最近一年公共日行情，之后也可手动重跑以按上游校正与补齐；它每次都会重新抓取整年窗口并与本地逐条比对，只写入有差异的行，无差异时不发布新数据版本。它不得由 Web API、日常 crontab 或其他管理命令间接调用。
- `sync_stock_daily_prices --date YYYY-MM-DD` 是日常 crontab 命令，仅下载、校验并幂等写入该交易日；不得扩展为最近一年范围同步。
- `refresh_intraday_quotes [--date YYYY-MM-DD]` 是盘中链路命令（建议每 30 分钟执行，`--date` 默认取 `Asia/Shanghai` 的今天）：它用同花顺全市场实时快照刷新**目标交易日**的公共日行情，与 `sync_stock_daily_prices` 使用同一数据集与同一字段语义，因此盘中刷新出的当天版本对读路径与盘后模块完全透明。它不抓取历史、不生成任何派生结果，收盘后当天行情仍由 `sync_stock_daily_prices` 以历史接口为准覆盖。当快照覆盖的股票数低于 `INTRADAY_QUOTE_MIN_COVERAGE_RATIO` × 当前活跃股票数时整体失败，不发布版本。
- 其他公共数据和盘后分析命令支持 `--date` 或明确日期范围；盘中资金流命令保留无参数交易时段模式和 `--latest` 模式。
- 盘中资金流命令的落库时刻由运行时刻按标准 5 分钟槽向前回退（盘中、午休、盘后与非交易日的具体落点见 §3.1.2）；交易日判定用 `chinese-calendar`（周末与法定节假日都不是交易日），历史交易日与"最近一个交易日收盘"仍以同花顺交易日历为准，日历为空时命令以非零退出码失败。
- 截至 **2026 年 9 月 9 日**，开盘啦资金流 URL 仍未获得经实际请求验证的历史快照时间参数支持；旧 `fundflow` 参考实现也未向该类资金流请求传递历史日期。因此当前资金流命令不得声明或实现 `--snapshot-time`、`--date` 等显式历史时间参数；未来只有在以真实请求确认上游契约后，才可另行扩展。开盘啦的 `KPL_DEVICE_ID`、`KPL_USER_ID`、`KPL_TOKEN` 均为可选请求字段：空值必须省略，非空值才附带。
- 所有命令支持 `--dry-run`，且不得写数据库或缓存。
- 参数无效、上游失败、完整性失败或数据库写入失败时返回非零退出码。
- 日志包含模块、数据集、业务日期、批次 ID 和耗时，不输出密钥、Token、Device ID 或完整敏感上游响应。
- 同一模块同一数据集的并发执行必须被互斥锁阻止。
- 成功写入后再发布新数据版本；失败不得破坏最近成功版本。

### 5.10 `.env` 配置契约

所有开发、测试和生产配置从项目根目录 `.env` 加载，并在 `.env.example` 使用安全占位符说明。至少包括：

- Django `SECRET_KEY`、`DEBUG`、`ALLOWED_HOSTS`。
- Session、CSRF、CORS/可信来源和安全 Cookie 配置。
- 五个 SQLite 数据库路径。
- 文件缓存根目录、TTL、开关和大小限制。
- 时区，固定默认 `Asia/Shanghai`。
- 模块启用开关。
- 同花顺 REST API 的 `HITHINK_FINANCE_API_KEY`、超时、低并发、请求间隔和有限重试参数。
- 开盘啦的两条独立 URL：板块资金流使用 `KAIPANLA_API_URL`（实时 `apphwshhq`），行业—股票快照使用 `KAIPANLA_INDUSTRY_API_URL`（历史 `apphis`）；两者各自的请求参数、超时、重试以及可选的 `KPL_DEVICE_ID`、`KPL_USER_ID`、`KPL_TOKEN` 均从 `.env` 读取；空凭据配置不发送对应字段。
- 行业—股票快照的 `Date` 参数必须落在交易日上：历史端点对周末、节假日等无交易的日期返回 `errcode 1020 参数出错`，因此默认值由 `core.services.calendar.latest_trading_date()` 解析为最近一个交易日，而不是本地日期；`KAIPANLA_INDUSTRY_DATE` 留空即启用该默认值，显式赋值用于回补指定交易日。发布的 `business_date` 记录实际请求的交易日。
- Web 远程同步修复的时间、数据量和远程尝试次数预算；本地生成派生结果不受这些预算约束（见 5.8）。
- 北交所行业归属增量补齐的开关 `HITHINK_INDUSTRY_BACKFILL_ENABLED`（默认 `1`；设 `0` 时整段跳过且不访问同花顺），见 §5.2.3。
- 开盘啦 `RealRankingInfo` 的族群选择：`KAIPANLA_INDUSTRY_PARENT_ZS_TYPE` 与 `KAIPANLA_FLOW_ZS_TYPE` 必须同族（当前为 `4`，即 881xxx 行业），配套 `Type=1`；换族会与既有快照混族，需清理并重算。
- 股票主数据同步的下界保护 `STOCK_MASTER_MIN_COVERAGE_RATIO`（默认 `0.9`）：上游返回的股票数低于「当前活跃股票数 × 该比例」时整体失败，避免把未出现的股票静默停用。
- 陈旧数据集锁的回收阈值 `LOCK_STALE_SECONDS`（默认 `21600`，即 6 小时）：持有者已死或锁文件超过该时长即回收；设 `0` 时只允许"同主机且持有者已死"这一种回收条件。
- 盘中行情刷新（`refresh_intraday_quotes`）的分页大小 `INTRADAY_QUOTE_PAGE_SIZE`（默认 `1000`，有效范围 1–10000）与覆盖率门槛 `INTRADAY_QUOTE_MIN_COVERAGE_RATIO`（默认 `0.95`，有效范围 `(0, 1]`）：快照覆盖的股票数低于「当前活跃股票数 × 该比例」时整体失败，避免用一份不完整的实时快照覆盖当天行情。

代码、测试、fixture 和命令中不得硬编码凭据、生产 URL、密钥、超时或功能开关。

## 6. 异常及边界场景

### 6.1 日期和交易时间

- 所有交易时间判断使用 `Asia/Shanghai`，不使用服务器本地默认时区推断。
- 周末和休市日不生成伪造的当日盘后分析。
- 未指定日期时，各模块返回自己的最新可用业务日期。**读写日期锚点是「最新完整公共日行情日期」**：它通常等于最近一个已收盘交易日，但当天已由盘中刷新发布 complete 版本时即为当天（见 §5.9 的 `refresh_intraday_quotes`）。"当日是否已收盘"仍是盘后管线的判定口径（`latest_eligible_trading_day`），两者不要混用。
- 显式指定日期时，不得静默替换为另一个日期；只允许返回该日期的旧数据版本并标识 `stale`，不能返回其他业务日期冒充结果。
- "交易日 15:00 前不生成当天盘后结果"这条只约束**盘后管线**（`sync_stock_daily_prices` + 三个 `build_*` 命令）与显式指定当天的请求：未指定日期的默认入口在当天已有 complete 公共版本（盘中刷新发布）时会跟随当天，否则回落到上一个交易日。当天还没有任何 complete 版本时，查看当天需显式带日期，此时返回 `202 DATA_PREPARING`。
- 交易日 15:00 后只有在公共日行情完整性通过时才发布当天盘后结果。
- 15:00 快照缺失时，多日板块资金流不能把其他时刻伪装为 15:00；可以按原有规则沿用前一交易日累计值，但必须在响应中警告缺失日期。

### 6.2 缓存异常

- 缓存文件不存在：回退 SQLite。
- 缓存过期：可先保留为旧数据候选，再查询 SQLite 新版本。
- 缓存内容损坏：记录错误、忽略文件并回退 SQLite。
- 缓存版本与数据库发布版本不一致：以已发布数据库版本为准并重建缓存。
- 缓存目录不可写：仍可返回数据库数据，不得使业务查询整体失败。

### 6.3 SQLite 异常和并发

- 数据库被短暂锁定：在严格短重试预算内重试；超出预算后返回旧缓存或明确错误。
- 命令写入必须使用事务，避免只写入部分结果却发布完整版本。
- Web 请求不得持有跨远程请求的数据库写事务。
- 一个业务数据库损坏或不可用时，其他业务数据库和 `core` 仍能工作。
- 不允许通过跨数据库 JOIN 实现业务查询。

### 6.4 上游数据源异常

- 网络超时、连接失败、非预期状态码和响应结构变化必须转换为稳定内部错误。
- 上游限流不得触发无边界重试。
- 开盘啦任一必要分页最终失败时，不发布完整快照。
- 同花顺行情不完整时不得发布 `complete` 公共数据版本。
- 同花顺权限不足、额度耗尽或开盘啦行业无法识别时，保留旧版本并在后台记录可行动错误。
- 对用户返回的错误不得包含 API Key、Token、Device ID、请求签名或敏感响应正文。

### 6.5 公共数据缺失

- 股票缺少名称或交易所：不应阻止原始行情保存，但相关业务结果需警告或排除。
- 股票缺少行业映射：不得随机分配；板块动量和行业聚合给出未映射数量。
- 当日停牌或无有效收盘价：不参与当日涨跌和新高新低判断。
- 新上市股票在上市前的历史位置按现有算法填 `0`；只要全市场日期窗口已有 99 个历史位置，该股票可参与判断。
- 交易日历缺失目标日期：不得仅按工作日推断，应返回数据未准备或运行日历同步命令。
- 日行情存在重复股票日期：完整性检查失败，新版本不得发布。

### 6.6 模块启停和删除

- 模块被禁用时，前端不显示入口，根 URL 不挂载其 API。
- 直接访问被禁用模块 API 时返回 `404` 或稳定的 `MODULE_DISABLED`，不得导入模块后再运行时判断。
- 删除某业务 App 后，设置、URL、模块注册表和前端注册中移除对应静态条目即可。
- 其余 App 的迁移、测试和启动不得导入已删除 App。
- `core` 状态中残留的已删除模块历史记录只作为历史文本，不触发模型导入。

### 6.7 数据版本变化

- 公共日行情或行业映射发布新版本后，相关业务派生结果可能变为过期。
- 业务 API 可以继续返回旧派生结果，但必须设置 `stale=true` 并指出依赖版本已变化。
- 业务 App 根据版本字符串判断是否重算，不调用另一个业务 App 获取“是否需要更新”。
- 重算失败时继续保留最后成功结果，不覆盖为半成品。

### 6.8 前端边界

- 单个模块请求失败只影响当前模块内容区，不清空全局导航和其他模块状态。
- 快速切换 Tab 或日期时，过期请求响应不得覆盖新选择的页面状态。
- 复制股票代码失败时给出可见提示，不伪报成功。
- 空列表、部分列表和请求失败必须使用不同状态展示。
- 图表缺失个别点时不得把缺失值默认画为 0，除非业务契约明确该值就是 0。
- 页面必须在常用桌面宽度和窄屏下保持可操作，不要求原生移动 App 体验。
- **页面外壳（日期控件、统计窗口按钮、刷新时间戳）在任何数据状态下都必须保持挂载**：数据状态只替换内容区（表格 / 看板 / 图表 / 排行榜），不得整页替换。否则切换日期时控件被卸载重建，用户失去正在操作的弹层、焦点与滚动位置。四个页面共用同一套状态判定（`shared/dataStateName.js`）。
- **交易时段的自动重取是"静默"的**：成功才替换数据，失败不得把已经渲染好的页面打回错误态；页面不可见（后台标签页）时不重取。默认入口的重取节奏与采集命令一致 —— 板块资金流 5 分钟、其余三页 30 分钟；用户手选日期后不重取。
- 图表数据必须以稳定引用传给图表组件：选中集合不变时不得重建 series 数组，否则 ECharts 会在每次无关重渲染时全量重绘并重播动画。
- `DATA_PREPARING`（202）与 `SYNC_IN_PROGRESS`（409）都是"稍后会有"，必须渲染为「数据准备中」而不是加载失败；只有真正的传输失败或 5xx 才显示错误态。

## 7. 安全和兼容性要求

### 7.1 认证和授权

- 除最小健康检查和登录所需端点外，所有业务 API 必须要求已登录。
- 使用 Django Session 和 CSRF 防护；修改状态的请求必须通过 CSRF 校验。
- 不提供注册 API。
- Django 管理后台只允许 `is_staff` 用户访问。
- 普通登录用户可访问全部已启用业务模块，不实现模块级授权。
- 登录失败信息不得用于枚举账号。

### 7.2 生产安全配置

生产环境必须：

- `DEBUG=False`。
- 从 `.env` 加载强随机 `SECRET_KEY`。
- 配置准确的 `ALLOWED_HOSTS` 和可信 CSRF 来源。
- 通过 HTTPS 提供服务。
- 启用 `Secure`、`HttpOnly` 和合理 `SameSite` 的 Session Cookie。
- 限制跨域来源为实际前端地址；同域部署时不开放不必要 CORS。
- 不在日志、缓存、数据库错误字段或前端响应中保存凭据。
- 对外部响应做类型和字段校验，不信任上游数据结构。

### 7.3 输入与输出安全

- 日期、整数范围、枚举值和排序参数必须显式校验。
- 数据库访问优先使用 Django ORM 或参数化查询。
- 股票名称、行业名称和上游错误作为纯文本输出，前端不得使用未净化的 HTML 注入。
- 不接受用户提供的服务器文件路径。
- 不保留旧文件上传接口，从而移除任意文件名和落盘路径风险。
- 管理命令日志对 Token、API Key 和 Device ID 进行遮蔽。

### 7.4 上游访问安全和合规

- 开盘啦访问只限板块资金流用途。
- 个股公共数据只通过同花顺 REST API；行业—股票公共数据只通过开盘啦行业列表和成分股接口；**唯一的补充来源**是同花顺行业目录与成分股接口，且仅用于北交所归属的增量补齐（见 §5.2.3），不得用于其他行业—股票关系。
- 所有上游 URL、参数、凭据、超时和开关从 `.env` 读取。
- 不绕过限流、访问控制或服务端能力约束。
- 不把抓包数据、上游完整响应样本或真实凭据提交到仓库。

### 7.5 兼容性

- 保持用户可见的核心筛选、排行、日期选择、图表、展开和复制功能。
- 统一 UI 可以改变布局和视觉细节，但不能删除核心操作。
- 旧项目的内部 API URL 不作为向后兼容契约；新前端必须使用新 `/api/<app>/` 路径。
- 旧 `fupan` 数据源、上传接口和 18:00 判断不兼容，明确由同花顺数据源和 15:00 时间资格替代。
- 行业统一改为开盘啦行业后，分析结果允许与旧人工/Baostock 行业结果不同；同一股票在多个行业中分别计入属于预期数据语义变化。
- 公共响应外壳统一，但模块业务正文可不同；前端不得假设所有模块共享同一数据结构。
- 同花顺 REST API 或上游字段变化时，应通过适配层隔离，业务服务不得直接散落 REST 字段名。

### 7.6 配置兼容和可部署性

- 本地和阿里云使用相同代码，通过 `.env` 区分配置。
- 路径不能依赖某个开发者的绝对目录。
- SQLite、缓存和日志目录必须可配置并在启动时校验可写性。
- Django 时区固定为 `Asia/Shanghai`，避免服务器 UTC 配置改变业务日期。
- 依赖版本必须记录，保证本地和生产可重复安装。

## 8. 可测试的验收标准

以下验收标准均需能够通过自动测试或明确的人工检查重复验证。

### 8.1 产品与用户流程

- **AC-UI-001**：给定未登录用户访问任意业务页面，系统不请求业务数据并跳转登录页。
- **AC-UI-002**：给定有效账号登录成功，首次进入显示“板块资金流 → 开盘啦”。
- **AC-UI-003**：四个一级 Tab 名称分别为“板块资金流”“大涨跌幅与大成交量个股”“板块动量”“百日新高新低占比”；四个 Tab 只显示文字标签，不显示左侧图标。
- **AC-UI-004**：板块资金流一级 Tab 直接展示开盘啦资金流内容，不提供数据源切换控件。
- **AC-UI-005**：禁用一个模块后，其导航入口和 URL 挂载均消失，其他模块可正常使用。
- **AC-UI-006**：单个模块 API 返回错误时，其他 Tab 的导航和已加载数据不受影响。
- **AC-UI-007**：所有模块都能区分展示加载、空数据、过期、准备中、部分成功和失败状态。
- **AC-UI-008**：全站上涨数据使用统一红色语义，下跌数据使用统一绿色语义，错误状态不与涨跌颜色混淆。

### 8.2 模块独立性

- **AC-MOD-001**：四个业务 App 之间不存在 Python import 依赖。
- **AC-MOD-002**：四个业务 App 不查询其他业务 App 的数据库或模型。
- **AC-MOD-003**：每个业务 App 有自己的 SQLite、URL、视图、服务、管理命令、迁移和测试。
- **AC-MOD-004**：逐一执行“只保留 `core` + 一个业务 App”的配置测试，`python manage.py check` 成功。
- **AC-MOD-005**：在上述四种单模块配置下，对应 App 的迁移、管理命令 dry-run、测试和 API 路由均可独立工作。
- **AC-MOD-006**：删除任意业务模块的状态历史不会导致 `core` 管理后台导入失败。
- **AC-MOD-007**：数据库中不存在指向另一个业务 SQLite 的外键或跨数据库 JOIN。

### 8.3 公共数据

- **AC-CORE-001**：首次初始化只请求和保存以执行日为终点的滚动最近一年范围内公共日行情。
- **AC-CORE-002**：同一股票和交易日期最多存在一条公共日行情。
- **AC-CORE-003**：三个盘后业务 App 不保存公共日行情的完整复制表。
- **AC-CORE-004**：交易日判断由 `core` 统一提供，业务 App 不包含独立节假日算法。
- **AC-CORE-005**：行业—股票快照只表示当前开盘啦关系，不包含历史有效期，且仅含 `industry_code`、`industry_name` 和 `stock_codes`（JSON 数组）三个业务字段。
- **AC-CORE-006**：同步以开盘啦行业列表与行业股票列表接口的实际响应为准；同一股票可出现在多个行业的 `stock_codes` 中；无成分股的行业必须以空 `stock_codes` 持久化，不得阻断完整快照发布。
- **AC-CORE-007**：公共数据写入中途失败时，最近成功版本仍可查询，新批次不被标记为完整。
- **AC-CORE-008**：公共数据版本记录预期数、实际数、缺失数和完整性状态。

### 8.4 数据源约束

- **AC-SRC-000**：同花顺市场数据客户端只访问已批准的 REST 端点：`/api/meta/tickers/list`、`/api/a-share/calendar/trading-days` 和 `/api/a-share/prices/historical`；请求使用 `X-api-key`，密钥仅从根目录 `.env` 的 `HITHINK_FINANCE_API_KEY` 读取。
- **AC-SRC-000A**：日线同步先分页取得 A 股股票表，再逐股票请求最近一年 `interval=1d`、`adjust=forward` 历史数据；客户端具有可配置低并发、请求间隔和有限退避。
- **AC-SRC-000B**：行业—股票同步以开盘啦行业 → 行业股票列表链路为权威来源；端点、参数、分页、超时、重试与可选 `KPL_*` 凭据均从 `.env` 读取。三项凭据任何一项为空时，请求不得发送该字段。
- **AC-SRC-000C**：北交所行业归属由同花顺行业目录与成分股接口**增量补齐**（`HITHINK_INDUSTRY_BACKFILL_ENABLED`，默认开启）：只往开盘啦已有的行业追加它缺少的成员，不删除、不替换开盘啦的任何成员或行业；只补同花顺也存在对应行业、且存在于本地 `core_stock` 的股票；关闭开关时不同花顺发起任何请求且同步正常完成；补齐失败时整次同步失败，不得静默发布"北交所无归属"的快照。补齐数量以 `backfilled_stock_count` 记录。

- **AC-SRC-001**：代码扫描和测试证明个股数据路径不包含上交所/深交所下载、Baostock、个股爬虫或浏览器自动化；同花顺 REST HTTP 只允许存在于 `core` 的受控适配层。
- **AC-SRC-002**：同花顺凭据和配置只从根目录 `.env` 读取，仓库中没有真实值。
- **AC-SRC-003**：开盘啦使用批准的板块资金流以及行业—股票 URL、分页参数和凭据规则，所有可变值来自 `.env`；`KPL_DEVICE_ID`、`KPL_USER_ID`、`KPL_TOKEN` 非空时附带，空值时省略。
- **AC-SRC-005**：日志和 API 响应不包含 API Key、Token、Device ID 或完整敏感请求参数。
- **AC-SRC-006**：模拟上游限流时，系统最多执行配置允许的有限尝试，并返回旧数据或稳定错误。
- **AC-SRC-007**：股票主数据同步在写入前校验本次结果的行数下界——低于「当前活跃股票数 × `STOCK_MASTER_MIN_COVERAGE_RATIO`（默认 0.9）」时整体失败（版本标记为失败、任何股票都不被停用）；首次同步（库中无活跃股票）不做该校验；`--dry-run` 同样执行校验。

### 8.5 板块资金流

- **AC-FLOW-001**：单日接口返回固定交易时间轴、板块序列、实际业务日期和 `stale` 状态。
- **AC-FLOW-002**：`inflow_top`、`outflow_top` 小于 0 或大于 30 时返回 `400`。
- **AC-FLOW-003**：历史接口只接受 1、5、10、20 个交易日窗口。
- **AC-FLOW-004**：多日汇总严格使用交易日历和每日 15:00 快照。
- **AC-FLOW-005**：窗口内某日缺少 15:00 数据时，响应能识别缺失，不把其他时间快照冒充 15:00。
- **AC-FLOW-006**：开盘啦任一必要分页失败时，不发布完整快照。
- **AC-FLOW-009**：同一交易日内切换曲线选择后重新渲染不会重置选择；切换交易日会恢复默认前5。

### 8.6 大涨跌幅与大成交量个股

- **AC-MOVE-001**：涨幅恰好 `8.00%` 且成交额恰好 `8亿元` 的股票被纳入上涨组。
- **AC-MOVE-002**：跌幅恰好 `-8.00%` 且成交额恰好 `8亿元` 的股票被纳入下跌组。
- **AC-MOVE-003**：不满足涨跌幅或成交额任一阈值的股票不被纳入。
- **AC-MOVE-004**：结果按市场（上证/深证/北交所）和方向（上涨/下跌）分为六组，排序符合规格。
- **AC-MOVE-005**：六组数量和全部去重股票数量与明细一致。
- **AC-MOVE-006**：复制全部得到当日全部去重股票代码，以英文逗号分隔且顺序与页面看板一致（上证涨/跌 → 深证涨/跌 → 北交所涨/跌）；复制失败时页面不显示成功。
- **AC-MOVE-007**：一组为空时返回空数组和数量0，不返回整个接口错误。
- **AC-MOVE-008**：北京证券交易所股票不被归入上证/深证四组，而是作为独立的 `bse_rise`/`bse_fall` 两组返回，并计入 `stock_codes` 与 `distinct_stock_count`；不再返回“已排除 N 只”这类排除数量警告。
- **AC-MOVE-009**：个股结果如带行业标签，只返回开盘啦行业标签；前端不展示股票代码，行业标签通过悬浮提示呈现。
- **AC-MOVE-010**：北交所上涨组按涨幅降序、下跌组按涨幅升序，同涨幅按代码升序；该行两侧均为空时页面不渲染该行，其余两组市场不受影响。
- **AC-MOVE-011**：每个交易所半区内的胶囊固定为 3 列（`repeat(3, minmax(0, 1fr))`），**所有胶囊等宽**（网格项铺满轨道）且文字在框内左对齐，右括号不与右边框重合；`≤80rem` 退回 2 列、`≤40rem` 退回 1 列。复制按钮无边框无底色，图标渲染在"全部复制"文字之后。

### 8.7 板块动量

- **AC-MOM-001**：涨幅大于 `5%` 的口径不包含恰好 `5.00%` 的股票。
- **AC-MOM-002**：全市场涨幅前5%按 `max(1, floor(当日有效股票数 × 5%))` 取样；同涨幅边界使用稳定次级排序，结果可重复。
- **AC-MOM-003**：综合评分等于“股票数量 × 平均涨幅 × 行业成交额占全市场成交额比例”。
- **AC-MOM-004**：每个口径最多返回评分前10行业，按评分降序。
- **AC-MOM-005**：行业股票明细、股票数量和聚合值一致。
- **AC-MOM-006**：缺少开盘啦行业—股票映射的股票不被错误分组，响应包含未映射数量；存在多个行业时分别计入每个所属行业。
- **AC-MOM-007**：业务结果记录公共日行情版本和行业映射版本。
- **AC-MOM-008**：行业动量排行、图表和股票明细只使用并返回开盘啦行业。
- **AC-MOM-009**：柱状图为竖排分组柱，类目轴按名次从左到右排列（评分最高在最左）；每个行业三根子柱依次表示股票个数、平均涨幅、成交占比，并各占一根数值轴。展开明细在一行内列出该行业全部入选个股，写作「股票名称（涨幅，成交额）」，不展示股票代码。
- **AC-MOM-010**：两种口径并排一行展示；窄屏（宽度不超过 64rem）回到单列。

### 8.8 百日新高新低

- **AC-HD-001**：目标日收盘价不参与前99个全市场交易日位置的最大/最小值计算。
- **AC-HD-002**：目标日收盘价大于或等于前99日最大值时标记新高。
- **AC-HD-003**：目标日收盘价小于或等于前99日最小值时标记新低。
- **AC-HD-004**：目标日无有效行情的股票不标记新高或新低。
- **AC-HD-005**：历史停牌日和上市前缺失值在滚动窗口中填 `0`，但目标日缺失值不填充；回归结果与旧项目算法一致。
- **AC-HD-006**：行业聚合数量与股票级标志数量一致；一个股票属于多个行业时分别贡献给每个所属行业。
- **AC-HD-007**：每日占比等于当日标志数量除以当日有效股票数，分母为0时返回空值而不是除零错误。
- **AC-HD-008**：结构化趋势数据能够由前端渲染，不依赖服务器生成 Base64 图片才能使用。
- **AC-HD-009**：业务结果记录公共日行情版本和行业映射版本。
- **AC-HD-010**：百日新高新低的行业排行和股票明细只使用并返回开盘啦行业。
- **AC-HD-011**：展开的股票明细按当日涨跌幅排序 —— 新高行业排行降序（涨幅大的在前），新低行业排行升序（**跌得多的在前**，如 -18.33% 排在 -8.37% 之前）；两个排行都写作"名称（涨幅，成交额）"，当日无行情的股票（`change_percent` 为空）排在最后且不被丢弃，同涨跌幅按代码升序保证顺序稳定。

### 8.9 缓存、兜底和性能边界

- **AC-FALL-001**：缓存命中时不访问数据库和远程数据源。
- **AC-FALL-002**：缓存损坏时自动回退数据库并重建缓存，不返回500。
- **AC-FALL-003**：缓存缺失而数据库有数据时，从数据库返回并写入版本化缓存。
- **AC-FALL-004**：数据库缺失但有可用旧缓存时，返回旧数据并设置 `stale=true`。
- **AC-FALL-005**：远程同步修复最多一次远程尝试，默认硬超时不超过5秒。
- **AC-FALL-006**：预计写入超过1,000行或需要全市场同步时，不在 HTTP 请求中执行远程同步，返回 `202 DATA_PREPARING` 或旧数据；**该限制只针对远程同步，不适用于仅读本地公共数据的派生结果生成**（见 5.8(a)）。
- **AC-FALL-007**：管理命令失败后，最近成功缓存或数据库版本仍可通过 API 访问。
- **AC-FALL-008**：新数据未完成数据库提交前，旧缓存不失效。
- **AC-FALL-009**：同一数据集并发到达时只有一个获得锁，其他请求返回旧数据、`202` 或 `409`。
- **AC-FALL-010**：请求某日期时若本地已有该日完整公共数据但缺派生结果，当场生成该日期结果并返回，不发起上游请求。
- **AC-FALL-011**：未指定日期的请求以最新完整公共日行情日期为读取目标；该日无法生成且存在任何旧结果时，返回旧结果并设置 `stale=true`。
- **AC-FALL-012**：显式指定日期时不得返回其他业务日期的结果；无本地公共数据即返回 `404 DATA_NOT_AVAILABLE`。

### 8.10 时间边界

- **AC-TIME-001**：所有日期和收盘判断使用 `Asia/Shanghai`。
- **AC-TIME-002**：交易日 14:59:59 请求当天盘后模块（显式带当天日期）时，不生成当天结果，返回 `202 DATA_PREPARING`；未指定日期的默认入口此时解析到上一个交易日，除非当天已有盘中刷新发布的 complete 公共版本。
- **AC-TIME-003**：交易日 15:00:00 后，只有公共数据完整时才允许生成当天结果。
- **AC-TIME-004**：15:00 后上游尚未提供完整数据时返回旧数据或准备中，不发布空的完整版本。
- **AC-TIME-005**：周末或休市日默认展示最近完整交易日并明确实际业务日期。

### 8.11 API 契约

- **AC-API-001**：所有业务 API 路径均以 `/api/` 开头并按 App 子路径分发。
- **AC-API-002**：所有业务响应包含统一外壳字段，业务正文位于 `data`。
- **AC-API-003**：无效日期格式返回 `400 INVALID_DATE`，不静默回退。
- **AC-API-004**：未登录访问业务 API 返回 `401 AUTH_REQUIRED`。
- **AC-API-005**：数据准备中且无旧数据时返回 `202 DATA_PREPARING`。
- **AC-API-006**：返回旧数据时 HTTP 可为200，但必须设置 `stale=true` 并包含警告。
- **AC-API-007**：`business_date` 始终等于正文数据的实际日期。
- **AC-API-008**：禁用模块后其 API 不挂载，不能通过猜测 URL 访问。

### 8.12 安全与部署

- **AC-SEC-001**：生产配置检查证明 `DEBUG=False`、`ALLOWED_HOSTS` 非空且 `SECRET_KEY` 来自 `.env`。
- **AC-SEC-002**：所有修改状态的 Session API 通过 CSRF 测试。
- **AC-SEC-003**：非管理员无法访问 Django 管理后台和详细运行错误。
- **AC-SEC-004**：仓库扫描不包含真实凭据、SQLite、缓存、日志、`.env`、虚拟环境或构建产物。
- **AC-SEC-005**：恶意日期、超大整数、未知枚举和脚本字符串不会导致 SQL 注入、路径访问或 HTML 注入。
- **AC-SEC-006**：本地和阿里云环境只通过 `.env` 切换，不需要修改源代码。

### 8.13 状态中心

- **AC-OPS-001**：管理员可在 Django 管理后台查看公共数据和每个启用模块的最新状态。
- **AC-OPS-002**：状态包含业务日期、最近成功时间、运行状态、完整性、版本、旧数据标志、连续失败次数和错误摘要。
- **AC-OPS-003**：命令成功后连续失败次数清零；失败时递增且旧成功版本保留。
- **AC-OPS-004**：状态中心不发送任何外部通知。
- **AC-OPS-005**：本期不存在自动备份、自动归档或定时清理任务。
- **AC-OPS-006**：数据集锁记录持有者（主机、PID、创建时间、唯一令牌）。获取失败时：同主机且持有者进程已不存在即回收该锁；无法判定持有者（跨主机、主机名缺失、锁文件损坏或只写了一半）时，锁文件超过 `LOCK_STALE_SECONDS` 才回收；同主机且持有者进程仍存活时一律不回收。回收必须原子（两个进程同时判定为陈旧时只有一个取得回收权），释放时校验令牌，不得删除已被他人重建的锁。回收记 `dataset_lock_reaped` 警告日志。

## 9. 规格边界：Always / Ask First / Never

### Always

- 始终先写 SQLite 成功并通过完整性检查，再发布数据版本和更新缓存。
- 始终从根目录 `.env` 读取配置。
- 始终使用同花顺 REST API 获取个股公共数据，并使用开盘啦接口获取行业—股票公共数据。
- 始终保持四个业务 App 的代码、数据库和运行失败相互隔离。
- 始终在 API 中返回实际业务日期、数据版本和过期状态。
- 始终使用 `Asia/Shanghai` 判断交易日和15:00边界。
- 始终为错误、空数据、旧数据和警告提供可区分状态（`partial` 由告警列表体现，不再另外用 chip 标注）。

### Ask First

出现以下情况必须先更新规格或询问用户：

- 同花顺 REST API 无法在额度内支持最近一年逐股票前复权日线初始化。
- 开盘啦接口无法提供可验证的行业或股票列表。
- 需要将个股数据改用爬虫或浏览器自动化。
- 需要改变已批准的 REST 或开盘啦数据源。
- 需要引入 Redis、Celery、消息队列或替换 SQLite。
- 需要让一个业务 App 调用另一个业务 App。
- 需要改变大涨跌幅、成交额、板块动量或百日新高新低算法口径。
- 需要保留旧 API、旧上传接口或旧18:00行为作为兼容层。
- 需要增加自动备份、自动清理或外部通知。

### Never

- 永不把真实凭据、Token、Device ID 或 `.env` 提交到仓库。
- 永不从 Web 请求启动无边界的全市场采集或历史重算（**只读本地公共数据、生成单个交易日派生结果的本地计算不属于此列**，见 5.8(a)）。
- 永不把不完整数据标记为完整版本。
- 永不跨业务 App 导入模型、服务或查询数据库。
- 永不伪造上游未提供的字段或用0替代未知数据。
- 永不因一个业务模块失败而使其他模块 API 不可用。
- 永不将同花顺 REST 行业目录或成分接口作为行业—股票关系的**正式来源**；它只被允许用于 §5.2.3 定义的北交所归属**增量补齐**（只增不删、开盘啦仍是权威、可由 `HITHINK_INDUSTRY_BACKFILL_ENABLED` 关闭）。
