# A 股市场复盘系统整合实施计划

**计划状态：** 已批准；T01 已完成，后续任务仍须按依赖顺序和增量实现要求执行\
**日期：** 2026-09-08  
**依据规格：** `docs/specs/integration-spec.md`  
**详细任务清单：** `tasks/todo.md`

## 1. 计划目标

在当前仓库中，将 `fundflow` 的开盘啦板块资金流能力与 `fupan` 的三个盘后分析能力整合为一个统一产品，同时建立不可删除的 `core` 和四个可独立启停、独立数据库、彼此零依赖的业务 App。

本计划只拆解工作，不修改应用代码。计划已获批准；后续实施仍必须按任务依赖、增量实现和测试驱动要求执行。

## 2. 实施假设（批准计划时一并确认）

1. 目标技术栈沿用现有项目方向：Django 6.1 后端 + React + Vite 前端；依赖版本在 T02 中锁定。**后端未引入 Django REST Framework** —— API 由 Django 原生视图返回 JSON，认证、Session 与 CSRF 全部使用 Django 自带能力；本节早期写法的"DRF"已按实际实现更正，`backend/requirements.txt` 是唯一依赖清单。
2. “每个 App 有自己的 `python manage.py` 命令”解释为：共用 `backend/manage.py` 入口，但命令实现和归属位于各 App 的 `management/commands/` 下，不为每个 App 复制一份 `manage.py`。
3. 本期不迁移旧项目的 SQLite 历史数据；首次部署且公共日行情为空时，手动执行一次 `init_stock_daily_prices --years 1`，通过同花顺 REST API 初始化最近一年行情。之后日常 crontab 只运行 `sync_stock_daily_prices --date YYYY-MM-DD` 同步当天，Web API 不得触发初始化或全量同步。板块资金流和派生结果通过新命令重新生成。若需要迁移旧数据库，应另增规格和任务。
4. `core.sqlite3` 作为 Django 的 `default` 数据库，承载认证、Session、公共数据和状态；另外四个数据库使用各自别名。
5. 模块启用开关是部署时静态配置，改变后重启服务生效；不实现在线插件安装或热加载。
6. 自动测试使用模拟 REST 传输/上游响应，不依赖真实凭据。真实同花顺 REST 与开盘啦链路能力已在 T01 完成最小验证；实际额度在实现和运行中持续受限观测。
7. 浏览器或真实 Web API 验收执行前，必须先询问用户是否已有可用服务及地址；没有时不得自行启动服务。

## 4. 架构与依赖顺序

```text
T01 外部 REST 与开盘啦链路可行性门槛
  └─ T02~T05 项目配置、数据库路由、模块装配
       └─ T06~T13 core 数据、缓存、API、状态契约
            └─ T14~T18 同花顺 REST 与开盘啦公共数据链路
                 ├─ T19~T23 kaipanla
                 ├─ T24~T26 stock_moves
                 ├─ T27~T29 sector_momentum
                 └─ T30~T33 hundred_day
                      └─ T34~T42 统一前端
                           └─ T43~T44 隔离、安全、部署和最终验收
```

约束：

- T19~T33 的四个业务模块可以在公共契约稳定后分支并行，但同一模块内部按任务号顺序执行。
- T39、T40、T41 可并行。
- 数据库迁移、共享响应外壳、模块注册表和前端共享组件属于协调点，不应由多个实施分支同时修改。
- 每个任务控制在 1~5 个主要文件；若实施时超过 5 个文件或需要超过一个专注工作时段，先拆分任务再继续。

## 6. 检查点策略

`tasks/todo.md` 在每 2~3 个任务后设置检查点。每个检查点至少确认：

- 对应聚焦测试通过；
- `python manage.py check` 或前端构建仍通过；
- 没有引入跨业务 App 依赖；
- 未完成任务没有被顺带实现；
- 高风险外部条件未通过时停止后续依赖任务。
- 行业快照直接保存每个行业的股票列表；同一股票可属于多个行业。

## 7. 全局完成定义

除每个任务自己的验收标准外，最终还需满足：

1. 规格中的 AC-UI、AC-MOD、AC-CORE、AC-SRC、AC-FLOW、AC-MOVE、AC-MOM、AC-HD、AC-FALL、AC-TIME、AC-API、AC-SEC、AC-OPS 全部有自动测试或明确人工证据。
2. 后端通过 `python manage.py check`、`python manage.py makemigrations --check --dry-run`、`python manage.py test`。
3. 前端通过 `npm run test`、`npm run lint`、`npm run build`。
4. `git diff --check` 通过，仓库不包含 `.env`、SQLite、缓存、日志、凭据、构建产物或虚拟环境。
5. 四种“`core` + 单一业务 App”配置均能独立检查、迁移、dry-run、测试和解析自己的 API URL。
6. 真实网页/API 检查仅在用户确认已有服务地址后执行，并记录实际地址、日期和结果；否则标为待用户环境验收，不能伪称已完成。

## 8. 主要风险与缓解

| 风险 | 影响 | 缓解策略 |
|---|---|---|
| 同花顺 REST 权限、额度或开盘啦行业—股票快照链路不能满足规格 | 高 | T01 已完成最小能力验证；实现中继续用低频、有限退避和旧版本保留控制风险。若能力不足，停止并回到规格评审，绝不静默改用未批准数据源。 |
| Django 多 SQLite 与认证表路由错误 | 高 | T03 先用路由单测和迁移矩阵验证；禁止跨库外键和跨库 JOIN |
| 旧 `fundflow` 中资金流模块存在复制代码和隐含耦合 | 中 | 只抽取无业务语义的 `core` 工具；两个 App 保留各自采集、模型和查询服务 |
| 旧 `fupan` 算法与新同花顺字段语义不一致 | 高 | T14 验证字段单位；T25/T28/T31 先使用合成回归样例锁定阈值和公式 |
| 百日算法的缺失填 0 口径容易被“修正” | 高 | T31 单独完成并以边界测试锁定 `shift(1).rolling(99)`，不得顺带优化 |
| Web 请求兜底演变为重采集 | 高 | T09/T10/T23/T26/T29/T33 统一检查 3秒/5秒/1000行/一次尝试预算 |
| 缓存提前失效导致命令失败后无旧数据 | 高 | 所有发布任务执行“事务提交与完整性通过 → 发布版本 → 失效旧缓存”的顺序 |
| 模块开关仅隐藏导航但 API 仍可访问 | 高 | T05 同时控制 `INSTALLED_APPS`、根 URL 和前端注册；T43 做删除/禁用矩阵测试 |
| 快速切换页面时旧响应覆盖新状态 | 中 | T42 使用取消请求或请求序号测试，不依赖人工观察 |
| 任务数量较多导致跨任务顺手重构 | 中 | 严格按文件范围实施；每个检查点审查 diff，超出范围先拆任务 |
